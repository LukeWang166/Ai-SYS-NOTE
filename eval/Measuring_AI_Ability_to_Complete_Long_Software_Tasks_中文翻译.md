## 摘要

尽管 AI 在各类基准测试上进展迅速，但基准分数的**现实含义**依然不清晰。为了让 AI 系统的能力可以用**人类能力**来量化和对照，我们提出了一个新指标：**50% 任务完成时间视界（50%-task-completion time horizon）**——即"AI 模型能以 50% 成功率完成的那些任务，人类通常要花多长时间"。

我们首先对具有相关领域专长的人类进行计时，任务集由 RE-Bench、HCAST 以及 66 个新设计的较短任务组合而成。在这些任务上，当前前沿 AI 模型（如 o3）的 50% 时间视界约为 **110 分钟**。此外，自 2019 年以来，前沿 AI 的时间视界大约每 **7 个月翻一番**，不过该趋势在 2024 年之后可能有所加速。

AI 模型时间视界的增长似乎主要由以下因素驱动：**更高的可靠性**、**适应/纠正错误的能力**，以及更强的**逻辑推理**与**工具使用**能力。

我们讨论了该结果的局限性（包括其外部有效性的程度），以及自主性提升对危险能力的影响。如果这些结果能推广到真实世界的软件任务，那么按该趋势外推可预测：**在 5 年之内，AI 系统将有能力自动化大量目前需要人类花费一个月才能完成的软件任务。**

## 1 引言

过去五年里，前沿 AI 系统经历了能力上的剧变：从基本的文本生成 [37]，进化到能自主执行需要数小时的复杂机器学习研究项目 [46]。能力足够强的 AI 可能执行危险的、高度复杂的行动，例如自主开发化学、生物、放射性或核武器（CBRN），以及在人类控制之外进行自我复制与适应 [34]。理解 AI 的能力有助于在系统日益强大时制定安全护栏。特别是，许多前沿 AI 开发者已承诺：**用对特定 AI 能力的度量，来决定其前沿系统需要哪些风险缓解措施。** 因此，能够准确追踪和预测 AI 能力的稳健基准，构成了负责任 AI 治理与风险缓解的基础。

然而，现有基准存在几个关键局限：

- **第一**，它们往往由人为设计的任务构成，而非具有经济价值的任务。
- **第二**，基准常常是**对抗性筛选**出来的——专门挑当前模型相对于人类表现较差的任务。¹

  > ¹ 例如 HellaSwag [50] 和 Humanity's Last Exam [33]，二者都是通过对抗性地、用当时最强的语言模型过滤题目而生成的，这使得与人类表现的对比产生偏差。

- **最关键的是**，单个基准饱和得越来越快 [24]，而我们缺少一种更通用、直观、可量化的方式去**跨基准比较**。²

  > ² SWE-bench Verified [7] 确实附带了人类估计的任务完成时间。我们在第 4.1 节使用 SWE-bench Verified 的任务及其时间估计来验证我们的主要结果。

  这使得能力差异极大的模型（例如 GPT-2 与 Claude 3.7）之间无法进行有意义的比较。结果是：虽然过去几年 AI 在许多单个基准上的表现大幅提升，但要理解 AI 能力的**总体进展**，我们只能靠定性估计"AI 系统最新能通过的基准有多难"。

我们提出用**任务完成时间视界（task completion time horizon）**来随时间追踪 AI 进展：即模型能够以某个成功概率完成的任务的持续时间，它提供了一个相对于人类而言直观的真实能力度量。由于模型未必能可靠地完成某一给定长度的所有任务，我们将其操作化为 **X%-(任务完成)时间视界**——模型大约能以 X% 的概率完成的任务长度。

我们用三个数据集来原型化这套方法，它们旨在覆盖研究或软件工程所需的技能（第 2.1 节），合计 **170 个任务**，难度跨度很大：HCAST [38]、RE-Bench [46]，以及 **Software Atomic Actions（SWAA）**——一套新的较短软件任务，可用于衡量 2023 年之前的模型（附录 B.1.3）。我们使用熟练的人类基线员（baseliner），估计一个**具备领域知识但没有任务特定上下文**的人完成这些任务所需的时间（第 2.2 节）。我们评估了 2019 至 2025 年间发布的 **12 个前沿模型（以及 4 个接近前沿的模型）** 在这些任务上的表现（第 2.3 节）。随后，借鉴人类心理测量学的方法，我们估计模型能以 50% 成功率完成的任务时长，即 **50% 时间视界**（第 3.1 节）。

我们发现，在这些任务上，50% 时间视界从 2019 到 2025 年呈**指数增长**，倍增时间约为 **7 个月**（图 1）。我们将主要结果与"不含 SWAA 的任务"上的探索性结果做对比，发现 2023–2025 年的视界增长率比 2019–2025 年的整体增长率快约 20%（附录 F.1）。我们也测量了模型的 **80% 时间视界**（图 17），发现趋势相似，但视界大约短 **5 倍**。这一进展看起来由几个关键因素驱动：更强的逻辑推理、更好的工具使用，以及任务执行中更高的可靠性和自我觉察（第 3.3 节）。我们还指出当前系统的若干局限——特别是，在结构化程度较低、"更混乱（messier）"的任务上表现明显更差（附录 F.2）。

由于我们的任务并不能完美代表研究者与软件工程师所从事的智力劳动的"平均片段"，这就引出了**外部有效性（external validity）**问题（第 4 节）：这条指数趋势在真实世界任务上是否成立？我们包含三个补充的外部有效性实验，结果几乎没有证据表明在我们测试的、稍微更真实的任务上性能趋势更慢；但也不能排除"在自动化软件工程师工作所需的任务分布上，趋势明显更慢"这一可能性。我们还发现，AI agent 的时间视界会**因任务领域和参照人群的不同而相差很大倍数**。

最后我们讨论了对 AI 能力预测的含义（第 5 节）。朴素地外推视界长度的趋势意味着：AI 将在 **2028 年中期到 2031 年中期之间**达到 >1 个月（167 个工作小时）的时间视界（图 6）。但外推同时受外部有效性担忧和未来趋势变化的影响。

> **图 2 | 我们测量 AI agent 时间视界的方法流程。** 三步：① 构建一个包含 170 个任务的多样化任务集；② 让人类和 AI agent（= 一个 AI 模型 + 一套 scaffold/脚手架）都去尝试这些任务，记录成功人类所花的时间，以及 AI agent 的成功率；③ 拟合一个 logistic 模型，找出每个 AI agent 有 50% 成功概率时所对应的时间视界，并将其对照模型的发布日期作图。

### 1.1 相关工作

这里简要讨论相关工作，扩展版讨论见附录 A。

**Agentic AI 能力基准。** 近期许多基准旨在衡量 AI 系统作为通用 agent 的能力，包括 AgentBench [22]、ToolBench [13]、GAIA [26]、TheAgentCompany [47]、Berkeley Function Calling Leaderboard [48]。在本工作中，我们研究 AI agent 在 RE-Bench [46]、HCAST [38] 和 SWE-Bench Verified [7] 上的表现，它们聚焦于机器学习与软件工程任务。其他类似的基准还有 MLAgentBench [17]、MLEBench [5]、DSBench [20]。在同期工作中，Miserendino 等人 [27] 构建了 SWE-Lancer 基准，包含 1400 个从 Upwork 收集的自由职业软件工程任务，真实薪酬总额超过 100 万美元。

**AI 能力预测。** 本工作建立在先前对 AI 系统能力随时间演化的预测努力之上，包括借助人类专家来为基准表现提供情境的工作（Phuong 等 [34]；Murray 等 [28]），以及针对特定基准预测性能的工作（Owen [31]；Pimpale 等 [35]）。用人类时间视界来为 AI 能力提供情境，由 Ngo [29] 提出，类似概念在 Carlsmith [4] 和 Cotra [9] 中也有讨论。

**人类心理测量学方法。** 我们的方法受到人类心理测量学测试的启发，尤其是项目反应理论（Item Response Theory, IRT）[3; 10; 23]。

## 2 在真实任务上测量 AI agent 的性能

### 2.1 任务集 / 数据集

我们的任务由三个不同的任务子集构成：

1. **HCAST [38] 的一个子集**：97 个多样化的软件任务，长度从 1 分钟到 30 小时不等。³
   > ³ 我们的结果中还包含 1 个来自 GAIA [26] 的任务，以及 5 个涉及编写"能抵御对抗者"的代码的任务。
2. **RE-Bench [46]**：7 个困难的 ML 研究工程任务，全部为 8 小时时长。

### 2.2 人类基线（Baselining）

为了让 AI agent 的表现有一个锚点，我们也在大多数任务上测量了多名人类"基线员"的表现，并记录他们尝试所花的时间。总计我们使用了 **800 多次基线**，累计 **2,529 小时**：其中 558 次（286 次成功）来自 HCAST 和 RE-Bench，249 次（236 次成功）来自较短的 SWAA 任务。169 个任务中有 148 个拥有人类基线，HCAST 中的 21 个任务依赖研究人员估计。

我们的基线员是软件工程、机器学习和网络安全领域的熟练专业人士，其中大多数毕业于世界排名前 100 的大学。他们平均拥有约 **5 年**相关经验，其中软件工程基线员的经验多于 ML 或网络安全基线员。更多基线细节见附录 C.1。

## 3 时间视界（Time horizon）

### 3.1 计算时间视界

为了把 agent 的运行数据转换为任务完成时间视界，我们首先把 agent 在每个任务上的表现转换为二值（成功/失败）。许多任务天然就是二值的，包括所有 SWAA 任务。**连续评分的任务**通过一个**任务特定的阈值**二值化，该阈值被选来代表人类表现：对 HCAST，任务特定阈值就是人类基线员试图达到的那个"目标分数"，我们也用它来筛选成功的运行；RE-Bench 任务的人类时长固定为 8 小时，因此其任务特定阈值取"用时 7–9 小时的人类运行"的平均分数。

一旦我们有了每个任务的 agent 成功率和时间评级，就通过如下 logistic 回归来拟合时间视界⁵：

$$p_{\text{success}}(\text{agent}, \text{task}) = \sigma\big((\log h_{\text{agent}} - \log t_{\text{task}}) \cdot \beta_{\text{agent}}\big)$$

其中 $t_{\text{task}}$ 是成功的人类基线所用时间的**几何平均**，$h_{\text{agent}}$ 和 $\beta_{\text{agent}}$ 是学习出的参数，$h_{\text{agent}}$ 即代表 **50% 时间视界**。

> ⁵ 可与项目反应理论（IRT）[3] 对照。与 IRT 相同的是，我们用 logistic 回归找出 agent 有 50% 成功概率所对应的任务难度；不同的是，我们的难度评级**直接基于人类基线时间**，而不是从 agent 表现中学出的评级。进一步的细节及与标准 IRT 方法的对比见附录 C.4。

> **图 4 | 所有模型在测试集上的成功率，展示"时间视界 = 预测成功率 50% 处对应的时间"这一计算方式。** 横轴为人类完成任务的时间（对数刻度，从秒到小时），纵轴为成功率；每条曲线是一个模型的 logistic 拟合。整体拟合相当好，但在"<1 分钟的 SWAA 任务"与">1 分钟的 HCAST 任务"之间存在一个成功率上的跃变（jump）。

### 3.2 时间视界 vs. 发布日期

在图 1 中，我们把每个模型的时间视界对照其**发布日期**作图——发布日期指实验室首次公开宣布该前沿模型的日期⁶。此外，我们做线性回归⁷，把 $\log(\text{时间视界})$ 对发布日期回归，发现**时间视界每 207 天翻一番**，95% 自助抽样置信区间为 **166–240 天**（约 ±19%）。误差棒通过对"任务家族 → 任务 → 运行"三层分层自助抽样取 10,000 个样本计算得到。

> ⁶ 大多数情况下，我们评估的前沿模型与其发布日期对应的模型是同一个。但 GPT-3（davinci）和 GPT-3.5（code-davinci-002 和 text-davinci-002）是闭源的、已无法通过 API 访问，因此我们对"最接近的可用模型"使用它们的发布日期——OpenAI 宣称这些可用模型性能相当：davinci-002 用 GPT-3 的发布日期，gpt3.5-turbo-instruct 用 GPT-3.5 的发布日期。

> ⁷ 具体地，我们对 $\log(\text{model\_horizon}) = \alpha + \beta \cdot \text{release\_date}$ 做普通最小二乘（OLS）回归。附录 H 讨论了其他曲线拟合方法，结论是拟合结果对正则化、任务加权、WLS vs. OLS 等各种超参数都不敏感。

虽然每个单独模型的时间视界长度误差棒很宽，但这些误差在模型之间**高度相关**。这是因为：人类时长评级相同的任务，对模型来说难度差异很大；抽样到偏易（或偏难）的任务，会让**所有**模型的视界估计一起变高（或变低）。因此，**我们对时间视界趋势斜率的信心，要高于对任一特定模型时间视界的信心。** 拟合对正则化、任务加权、WLS vs. OLS 等各种超参数都不敏感（见图 6）。

从 2019 年到 2025 年初的整个时间段内，视界长度大幅增长：GPT-2 的 50% 时间视界只有 **2 秒**，而 o3 的时间视界为 **110 分钟**，并且能在若干超过 4 小时的任务上成功。此外，**o3 位于长期趋势线之上（p = 0.006）**；这一结论对方法学消融（例如使用连续评分，见附录 H）是稳健的，这可能意味着 2024 年和 2025 年初的趋势更快。

#### 3.2.1 50% 成功率与 80% 成功率下的时间视界

为了检验"选择 50% 成功率"是否影响长期趋势，我们也计算了 AI agent 以 **80% 成功率**完成任务所对应的时间视界，见图 17。80% 时间视界的倍增时间（**204 天**）与 50% 时间视界的倍增时间（207 天）相近，在误差范围内。但模型的 80% 时间视界要短 **4–6 倍**，这说明：**即便是那些偶尔能完成困难且多样任务的模型，也无法可靠地完成中等长度的任务。** 受数据集规模限制，我们无法有把握地测量极高成功率（例如 95%）下的时间视界，见第 E.3 节。

### 3.3 定性分析

通过检视 31 个随机抽样的 **GPT-4 1106** agent 失败运行和 32 个 **o1** 失败运行的轨迹（transcript），我们观察到：模型在**工具使用**能力上似乎进步巨大，表现出明显更强的**适应错误**的能力（而不是重复不成功的动作），并且在需要**逻辑推理**或**代码生成**的任务环节上表现好得多。不过我们注意到，AI agent 在直觉上"更混乱"的环境中似乎仍然吃力——具体来说，是那些**没有清晰反馈回路**的环境，或**需要 agent 主动去寻找相关信息**的环境。

## 4 外部有效性与鲁棒性

我们检查了"不含 SWAA 数据集的 2023–2025 趋势"能否**回测（retrodict）**出 2019 年以来的趋势，发现两者一致。我们还做了三个实验来检验外部有效性。

**第一**，我们在 **SWE-bench Verified** 上复现了我们的方法。我们发现指数趋势依然成立（图 5），尽管倍增时间更短——可能的原因是：SWE-bench Verified 的难度标注意在代表"高上下文的维护者时间"，因而可能**不成比例地低估**了人类承包商完成较简单 SWE-bench 任务所需的时间。

**第二**，我们用一个包含 **16 项"混乱度（messiness）"因子**的清单，对 HCAST 和 RE-Bench 任务打分，这些因子旨在捕捉本研究中的任务与困难的"真实世界"任务之间的某些系统性差异（例如任务是否资源受限、是否新颖、是否涉及动态环境等，见第 H.6 节）。在控制任务长度后，我们发现：**模型在混乱度得分更高的任务上表现更差。** 值得注意的是，AI agent 性能随时间的趋势，在这些任务的"低混乱度"子集和"高混乱度"子集上是相似的（见图 12）。特别是，我们没有发现任何证据表明高混乱度子集存在特有的性能平台期。

**第三**，我们在一小批**未被污染的内部 Pull Request（PR）**上测量了 AI agent 的表现（第 C.2 节）。我们发现不同人类群体完成内部 PR 任务的速度差异很大——**承包商修复问题所需的时间是仓库维护者的 5–18 倍**。我们还发现，若用"维护者完成时间"作为任务长度的度量，AI agent 的表现会差于预测值；但若用"承包商完成时间"来度量，则与预测一致。

SWE-bench Verified 的相关信息见下文；回测与混乱度分析的细节见附录 F，内部 PR 实验的细节见 C.2。

### 4.1 SWE-bench Verified

为了检验在其他基准上是否能观察到类似的性能趋势，我们把方法应用到 **SWE-bench Verified**——一个评估语言模型软件工程能力的行业标准基准 [30]。SWE-bench Verified 数据集中的所有任务都采集自大型开源仓库（如 matplotlib、django），并经过筛选以确保可自动检查且定义良好 [19]。

> **图 5 | 使用已报告的 SWE-bench Verified 结果得到的前沿 AI 模型表现（第 4.1 节）。** 我们观察到与图 1 类似的指数趋势，但斜率更陡。横轴为发布日期（2023 年末至 2024 年），纵轴为时间视界（对数刻度）。

由 SWE-bench Verified 任务计算出的模型时间视界，从 2023 年末到 2024 年似乎也遵循指数趋势。然而，用 2024 年模型在 HCAST + SWAA + RE-Bench 上预测的倍增时间是 **143 天**，而 SWE-bench Verified 结果上的倍增时间更短——约 **70 天**。

SWE-bench Verified 的时间标注基于"一位有几小时时间熟悉代码库的工程师"解决该问题所需的预期时间 [19]。我们发现，**标注者的时间估计不成比例地低估了我们的合同基线员完成最简单的 SWE-bench Verified 任务所需的时间**。结果是：我们使用标注者时间的 SWE-bench Verified 时间视界估计，很可能相对于承包商时间**低估了能力较弱模型的时间视界**，进而缩短了倍增时间。更多细节见附录 H.5。

## 5 外推（Extrapolation）

### 向"一个月视界"的 AI 外推

为了预测 AI 系统何时可能有能力自主产生巨大的经济价值、以及潜在的灾难性行为，我们选择 **一个月**（为与人类做公平比较，取约 **167 个工作小时**，因为人类无法 7×24 工作）作为目标，原因有二：

- **第一**，Ngo [29] 写道：一个"1 个月 AGI"（定义为在给定 1 个月工作小时、即 167 小时的条件下，表现优于大多数具备相关知识的人类的 AI），必然会在有经济价值的事业上超越人类表现，例如编写大型软件应用、创办初创公司、做出新颖的科学发现。⁸
- **第二**，一个月大致是**公司新员工完成入职培训并开始产生经济价值**的周期。⁹ 因此，拥有 1 个月视界的 AI 可能像人类员工一样获取上下文，从而能够完成高上下文任务以及低上下文任务。我们不能排除：一个能以 50% 可靠性完成 1 个月时长任务的系统，可能对社会产生变革性影响，甚至可能包括造成灾难性伤害的能力。

> ⁸ 注意：我们的预测是关于"在软件任务上有 1 个月视界的 AI"，而不是"1 个月 AGI"，因为我们只在软件和研究任务上评估模型。尽管如此，鉴于 AI 各领域表现之间的历史相关性，具有 1 个月（167 小时）时间视界的 AI 可能具备相当强的通用能力。

> ⁹ 入职"可能持续几周到一年以上" [52]，而员工通常在入职过程中期就开始产生经济价值。

> **图 6 | 对外推得出的"前沿 AI 系统达到 1 个月视界"日期的敏感性分析。** 每一行代表一种噪声来源：我们对数据施加 10,000 次随机扰动，并找出被扰动数据所隐含的"1 个月 AI"日期分布。箱体两端为第 25 与第 75 百分位数，须线为第 10 与第 90 百分位数（未显示离群点）。图中各行大致包括：Bootstrap（任务）、Bootstrap（运行）、Bootstrap（模型）、加权/正则化、IID 基线噪声、2024–2025 趋势等。注意：该图**没有考虑未来趋势的变化或外部有效性问题**，而后者正是我们不确定性的主要来源。

**敏感性分析。** 图 6 展示了我们的结果在各种噪声来源下的敏感性分析。"Bootstrap（tasks）"、"Bootstrap（runs）"、"Bootstrap（models）"分别表示任务数量有限、运行间方差、模型数量有限；"Weighting/regularization"表示方法学选择，该扰动包含 10 组超参数组合，有无任务多样性加权，logistic 回归正则化参数在 0.01 到 0.2 之间；"IID Baseline Noise"则根据基线时间的经验分布，给每个任务时长乘上一个随机因子。注意：我们对"仅用 2024–2025 年趋势"的信心较低，因为该时间跨度内只有 7 个前沿模型。

由于我们的分析认为"在我们的任务上，时间视界增长率显著慢于每 8 个月翻一番"的概率很低，因此外推出的"1 个月 AI"日期的不确定性相当小（**80% 置信区间宽度约 2 年，中心估计为 2029 年中期**）。如果未来的进展遵循 2024–2025 年的趋势，1 个月 AI 会更早到来——一半的概率落在 2027 年，甚至 2026 年末。

系统性的偏差和替代方法学可能对预测有更大影响，我们在附录 H 中讨论这些。此外，由于预测未来本身的固有困难，真实的预测误差会比这种朴素外推更大，我们在下文讨论。

### 任务分布的局限

我们在附录 B.2 中指出了该任务集与真实任务之间的若干差异：简而言之，**真实任务很少有自动评分**，并且常常需要处理其他 agent、资源约束、动态环境以及高可靠性要求。这些差异让人怀疑：在该任务集（以及其他基准）上看到的快速性能改进能否泛化。有可能 HCAST 和 SWE-Bench Verified 这类基准不足以预测真实世界的 AI 能力，而准确的预测需要有意识地构建不存在这些局限的、更真实的基准。

### 时间视界趋势的未来变化

时间视界趋势在未来可能发生显著变化，影响因素包括 **agentic 训练（agency training）**、**算力规模化（compute scaling）**以及 **AI 研发自动化**。其中，agentic 训练和最终的 AI 研发自动化更可能**加速**趋势；而算力规模化可能**减缓**趋势（但会被算法改进部分抵消）；未来的通用人工智能（AGI）在技术上可以拥有无限的时间视界。详见附录 E。

## 6 讨论

**总结。** 在本文中，我们提出了一个直观、可量化的 AI 能力指标：**任务完成时间视界**，它把 AI 在任务上的表现与人类专家完成该任务所需的典型时长联系起来。我们构建了一个包含 66 个较短 SWAA 任务的数据集，将其与现有基准合并，并进行了基线测试以估计其难度。为了测量时间视界的趋势，我们在该数据集上评测了 2019 至 2025 年间发布的 11 个前沿 AI 模型，发现（第 3 节）在这些任务上的 50% 任务完成时间视界从 2019 到 2025 年呈指数增长，倍增时间约为 **7 个月**（图 1）。我们还指出了当前系统的重要局限，特别是它们在结构化程度较低、"更混乱"的任务上表现更差（附录 F.2）。

最后，我们尝试把在这些任务上的趋势外推到"一个月（167 小时）AI"（第 5 节），发现：如果趋势延续，且观察到的性能趋势能泛化到真实世界任务，那么"能完成 1 个月时长软件任务的 AI"的发布日期的 **80% 置信区间为 2028 年中期到 2030 年中期**（第 5 节）——如果 2024–2025 年的趋势延续，甚至可能早到 2027 年初。

**局限与未来工作。** 尽管我们相信这条指数趋势是稳健的，但我们提醒：时间视界总是相对于**特定领域、任务分布、以及人类基线员的技能水平与上下文**来衡量的，并且在实践中可能难以测量，尤其是对于较长视界或接近 100% 的成功率。我们在附录 E.3 中讨论了解读时间视界的细微之处。最后，在附录 E.4 中，我们讨论了扩展或改进本结果的方式，例如研究多个领域、更多模型、更好的能力激发（elicitation）、推理时算力规模化，或其他统计方法。

## 附录 A 扩展版相关工作

### A.1 Agent 与能力基准

AI 能力评估已从单任务基准显著演化为复杂的多步评估，用以衡量类 agent 的行为。GLUE、SuperGLUE、MMLU 等传统基准提供了关于语言模型表现的宝贵洞察，但它们主要衡量**静态知识**，而非真实应用所必需的**动态问题解决能力**。

近期工作开发了更复杂的 agent 基准：AgentBench 在网页浏览、编码、游戏等多种环境中评估 agent；MLAgentBench 与 MLEBench 专门聚焦机器学习研究任务；ToolBench 评估工具使用能力；新近的 ZeroBench 包含困难的推理，但场景是视觉谜题而非有经济价值的任务。其他值得一提的还有 GAIA（跨模态推理）和 BIG-bench（数百个多样化任务，许多需要多步推理）。

**软件工程**已成为评估 AI 能力信息量特别大的一个领域：HumanEval 和 MBPP 提供不同复杂度的编程挑战；SWE-bench 和 APPS 测试更复杂的编程能力；我们使用 SWE-bench Verified 的人类时间估计；RE-Bench 在可能需要数小时人力投入的复杂研究工程任务上评估模型，并与人类 ML 工程师对比；SWE-Lancer 则生成了大量带真实报酬的任务。

> **译者点评**：这些基准各自提供了对特定能力的宝贵洞察，但普遍缺少一个**统一指标**，用于随时间追踪进展、并比较能力差异极大的模型。我们的"时间视界"方法正是为了填补这一空白——提供一个连续指标，可跨能力层级衡量进展。

### A.2 AI 进展预测

对 AI 进展的定量预测采用了多种路径，通常始于"AI 训练所用算力随时间急剧增长"这一观察。Amodei 和 Hernandez [2018] 观察到训练算力呈指数增长，2012–2018 年间约每 **3.4 个月**翻一番；Epoch AI [2024] 加入了更新的数据以及训练数据集规模和能耗的趋势。

另一些工作研究了 AI 性能如何随时间提升，把基准表现与发布日期、算力使用及其他投入关联起来。Sevilla 等 [2022] 发现算力使用增长率在 2010 年"深度学习时代"开始时上升，与性能提升相吻合。更近期地，Owen [2024] 和 Pimpale 等 [2025] 用算力等指标预测未来的基准表现。

有若干工作致力于为 AI 基准表现提供情境：年度 AI Index Report 追踪各基准表现，包括模型达到人类水平表现的日期；Murray 等 [2025] 让网络安全专家把 AI 在 Cybench 上的表现与自主开发恶意软件的能力联系起来；Phuong 等 [2024] 委托专业预测者，以基准表现为条件预测"到 2030 年 AI 是否会位列公众最关切问题之列"。这些工作通常缺少用于跨基准比较的统一定量指标。

Carlsmith [2020] 和 Cotra [2020] 开发了 "bio-anchors" 框架，把训练 AI 模型的算力与"AI 产生变革性影响所需的有效视界长度（effective horizon length）"联系起来。Ngo [2023] 提出用"AI 系统在大多数任务上超越大多数人类专家的时间视界"来衡量通用 AI 能力。**在本工作中，我们实证地评估任务时长与 AI agent 成功率之间的关系，并将其转换为 AI agent 表现的定量指标。**

### A.3 心理测量学方法与项目反应理论

我们的方法借鉴自心理测量学测试，尤其是项目反应理论（IRT）——它建模潜在特质（如能力）与对测试题目的观测反应之间的关系。在传统 IRT 中，**题目难度**是 logistic 模型中的一个参数，用于基于被试能力预测作答正确与否。**我们的方法把这个关系反了过来**：用任务完成时间（作为难度的代理）来预测 AI 的表现。我们的方法还与教育测试中的难度估计技术相关——那里会用包括完成时间在内的多种指标来估计任务难度。IRT 已被 Martínez-Plumed 等 [2019] 应用于机器学习分类器，并被 Song 和 Flach [2021] 用于设计高效的基准。

## 附录 B 任务集细节

与大多数基准一样，我们研究的三个任务集都被设计成"隔离出一个可在时限内可靠完成的特定工作单元"。这通常意味着：**这些任务所需的上下文远少于一个大型项目中途的平均任务**。¹⁰

> ¹⁰ 我们把**上下文（context）**定义为：有经验的员工用来完成任务、但既不在任务描述中、也不为大多数外部专家所拥有的信息。例如，修复一个软件包中的 bug 时，该包的维护者可能会利用自己对该包过往 bug 的经验来猜测成因，利用对代码库的熟悉来定位 bug，并利用对组织优先级的了解来决定是打一个快速补丁还是做一次彻底修复。我们在第 4 节讨论上下文可能造成的影响。

我们通过"让人类在每个任务上至少成功完成一次"来确认所有任务在给定指令下是可完成的。¹¹

> ¹¹ 由于这些尝试中有许多是由内部员工完成的，或使用的方法不同，我们把这些尝试排除在人类基线数字之外。

### B.1 任务子集

HCAST 和 SWAA 集被划分为**任务家族（task families）**，即彼此相似的任务组。例如 "crossword" 家族包含"创建 3×3 填字游戏"、"创建 5×5 填字游戏"等任务。我们划分家族有两个原因：家族内表现是相关的；同时我们对任务多的家族做降权以保证多样性。

#### B.1.1 HCAST 子集

我们使用 HCAST 中来自 **46 个任务家族的 97 个任务**——一个涵盖网络安全、机器学习、软件工程和通用推理的多样化挑战集。

该集中的任务跨度很大：从人类只需几分钟的简单任务（例如在维基百科上查一个基本的事实问题），到需要人类专家数小时的任务（例如编写 CUDA kernel，或修复 PyTorch 中一个微妙的 bug）。由于现代前沿 AI 系统相对更擅长基于文本的任务，这些任务中的大多数不需要视觉/多模态能力，且全部可通过 bash shell 中的文本编辑来解决。

与许多近期基准相比，HCAST 中的任务**并非**被设计成"对人类领域专家或当前 AI 系统尽可能困难"。相反，大多数任务被设计成**真实的**——做好这些任务需要我们预期具有经济价值的技能。因此，我们预期这些任务中的大多数可以被拥有几年相关领域专业经验的人类解决。

任务由**指令**、**起始资源**和**算法化评分函数**定义。任务指令是字符串，通常 1–2 句话到几段话，可以引用作为起始资源提供的或互联网上外部可得的其他信息源。起始资源通常包括代码、数据和文档。每个任务的自动评分在 0 到 1 之间，分数越高表现越好。许多任务只返回 0 或 1，但对连续评分的任务，我们手工定义一个成功阈值分数，用于在部分分析中二值化 agent 分数。¹²

> ¹² 这些任务中的一小部分可按要求提供。（我们不公开大多数任务的内容，以降低 AI 系统意外或有意地在它们上面训练的可能性。）

#### B.1.2 RE-Bench 子集

RE-Bench 由 7 个具有挑战性的开放式 ML 研究工程环境组成，每个环境预期需要人类专家约 **8 小时**完成。详见 Wijk 等 [2024]。

#### B.1.3 Software Atomic Actions（SWAA）子集

HCAST 被设计成一个多样化的任务集，但**最短的任务也在 1 分钟左右**，这限制了在更短任务上衡量 AI agent 表现时的代表性和可达分辨率。为了填补这一空白，我们注意到：现实世界中的智力劳动，有一部分是由**短于 1 分钟的可测量单步动作**构成的。因此我们创建了 SWAA 任务集，包含 66 个小任务，对应软件工程工作中常见的 <1 分钟原子动作。SWAA 子集同时包含选择题和补全题。

> 示例：*"哪个文件最可能包含密码？"* 选项：1. `credentials.txt`　2. `installation_notes.txt`　3. `main.py`　4. `launcher_win.exe`

与 LAMBADA 或 GSM8K 等其他简单基准不同（它们测试的技能与软件工程无直接关联），**SWAA 代表的是软件工程工作以及我们所研究的更长任务中都需要的动作**。SWAA 由 5 个任务家族构成：三个代表常见决策，一个代码补全，一个数学。

SWAA 任务的开发对 AI agent 表现是**盲态（blind）**的：所有任务都在看到 AI 尝试之前写好，能力激发（用于评估的 few-shot prompt 的开发）则在一个独立的开发任务集上进行。

> **图 7 | 按难度评级的任务堆叠直方图。** HCAST 主要包含长于 4 分钟的任务，而我们用 SWAA 聚焦 2 秒到 15 秒区间，以便测量 GPT-2 和 GPT-3。二者之间存在一个缺口（gap），限制了我们在该区间测量时间视界的能力。

SWAA 的五个任务家族：

**决策（多选）**
- **文件选择**：哪个文件具有某种属性，或在某情境下适合读取？
- **告警分诊（Alert triage）**：公司里哪个团队应该去调查这条告警？
- **请求路由（Request routing）**：响应某个请求需要采取哪个动作？

**填空（Fill-in-the-blank）**
- **代码补全**：补全代码中的一个单词。
- **数学**：解简单的算术题，可以是独立的，也可以是软件工程主题的应用题。

在开发 SWAA 任务时，我们试图通过"让任务作者对模型表现盲态"来避免结果偏差：初步的 71 个任务在开发期间没有跑过任何模型。之后通过排除"有一名以上基线员失败"的任务，筛选出最终的 66 个。

> **图 8 | 7 个原始 RE-Bench 任务。**（包括 Restricted MLM、cuda_backtesting 等；其中 Restricted MLM 任务禁止使用某些 PyTorch 方法，当前模型有时会以间接方式使用这些被禁方法，导致作弊无法被自动检测，但模型作弊不会实质影响我们的结果。）

### B.2 任务集的局限

我们用来给 AI 能力打基准的任务，与真实任务存在系统性差异。这些差异可能导致我们在这些任务上观察到的趋势无法泛化到真实世界任务。例如，所有 SWAA、HCAST 和 RE-Bench 任务都在以下方面与真实任务不同：

- **自动评分**：我们使用的所有任务都可自动评分，即由任务环境中运行的一段代码决定最终分数。这对解的格式等施加了约束，往往会降低任务的开放性和做出合理价值判断的需求。
- **不与其他 agent 交互**：没有任何任务涉及与其他自主 agent 交互。与其他 agent 协调或竞争似乎会增加任务难度——例如，它会提升战略决策、实时协调和预测其他复杂 agent 行为的重要性。
- **资源约束宽松**：SWAA 中没有任务、HCAST 中也很少有任务显著涉及"高效利用有限资源"——而这恰是真实世界任务中的常见约束。
- **不惩罚失误（Unpunishing）**：同样地，很少有任务会对单次失误施以重罚。¹³

  > ¹³ 唯一的例外是在 HCAST 任务上过早提交答案。这部分是为了降低收集人类基线的预期成本。真实世界任务往往更具惩罚性，例如当任务涉及与其他 agent 竞争时——一局象棋中的一次失误可能大幅降低获胜概率。

- **静态环境**：本任务集中的任务通常使用"除非 agent 直接作用、否则不会显著变化"的环境。相比之下，真实任务往往发生在不断变化的环境中。

我们试图在第 F.2 节中衡量这些系统性差异会如何影响 AI agent 表现，把上述属性作为"混乱度"因子纳入。我们发现：**虽然在"更混乱"任务上的绝对表现更低，但性能提升的趋势与不那么混乱的任务相似。**

### C.1 人类基线

#### C.1.1 HCAST 任务

我们使用作为 HCAST 一部分收集的现有基线。这些基线来自在软件工程、ML 和网络安全方面具备相关经验的领域专业人士。基线员在与 agent **相同的环境**中工作，使用 Vivaria（一个用于语言模型 agent 评测的开源平台），并对其屏幕和音频进行录制以供人工复核，以防止作弊。他们被激励以奖金鼓励成功完成任务、以及比其他基线员更快完成任务。在剔除"不在我们 HCAST 子集上的尝试"、失败尝试以及有问题的尝试（例如使用了不允许的 AI 工具）之后，我们从约 460 次总尝试中保留了 **286 次成功基线**。任务时长用成功基线的**几何平均**计算，对缺少成功基线的任务使用人工估计。¹⁴

> ¹⁴ 非基线的估计依据包括：未遵循严格基线条件的 QA 运行的时长，以及具有成功基线的相似任务的时长。

#### C.1.2 RE-Bench 基线

对于 RE-Bench，我们使用 Wijk 等 [2024] 的基线。由于基线员被指示"为每个任务取得最好的表现"，我们把这 6 个任务的任务时长都视为 **8 小时**，转而用"用时在 7 到 9 小时之间的基线员的平均得分"来把原始分数转换为成功阈值。

RE-Bench 的基线使用与 HCAST 相同的基线员池与激励，但有几点不同：基线员不是被要求达到某个阈值分数，而是被给予固定的 8 小时时限并被指示最大化分数；阈值基于基线员的平均表现设定。**RE-Bench 基线员可以使用 AI 工具**，因此这些任务上的人类分数可能被高估。

#### C.1.3 SWAA 基线

与 HCAST 和 RE-Bench（由外部承包商做基线）不同，**SWAA 由具备相关专长的内部员工做基线**，使用一个自研 web 应用以便更精确地计时。由于这些任务意在成为单步动作、且排除上下文获取，SWAA 任务的计时器**在用户选择回答的瞬间就停止**。对于决策类任务，只允许选择一次以避免随机猜测；对于填空类任务，基线员可以多次尝试直到答对或选择跳过。我们对每个决策类任务做 4 次基线，对每个填空类任务做 3 次基线。

具体而言，SWAA 计时器在阅读完通用指令后开始、在用户选择回答时结束，因此基线时间只包括"阅读问题本身"和"选择答案"。用我们常规设置做基线有几秒到几十秒的计时开销，这对时长短于 2 秒的单步任务来说高得不可接受。

#### C.1.4 基线成功率

我们通过取**成功基线运行时间的几何平均**，把人类基线时间聚合为任务长度评级。之所以用几何平均而非算术平均，是因为基线时间大致呈对数正态分布，几何平均对模型表现更具预测力。

我们选择只筛选成功的运行，有两条理由——一条实际的、一条原则性的：**其一**，要为每个任务收集足够多的基线以估计"时间 vs. 成功率"曲线，在实践中很困难。**其二**，我们希望排除那些"人类因不适用于模型的原因而失败"的情形。相当一部分人类失败似乎属于这一类——包括人类对任务缺乏足够的专业知识，或因不明原因放弃任务（可能是被打断或感到无聊）。特别是，由于我们在优化"获得成功基线"，我们的付费方案会激励承包商快速猜测或早早放弃，以便转向预期收益更高的其他任务。

然而，**以成功为条件会使任务长度评级偏短，从而低估模型表现**。如果许多人类失败源于对模型同样相关的问题（例如某些任务需要猜测），这种情况尤其明显。这种偏差在较长任务上最显著——这些任务的基线员成功率常常低于 50%；因此我们对这些较长任务的难度评级信心较低，并预期它们可能是低估的。若果真如此，**我们可能低估了模型改进的速度**。

**人类时间视界。** 另一种做法是用与模型相同的方法计算人类的时间视界。时间视界的一个自然解释是："一个被给予 x 小时的人类"的时间视界就是 x 小时。由于我们的基线员是按"每任务最多 8 小时"付费的，我们会预期他们的时间视界约为 8 小时。然而实际上它低得多，只有约 **1.5 小时**（这将意味着最好的模型将在不到 7 个月内超越人类）。如上所述，我们认为这个数字被人为压低了，因为许多人类失败似乎是我们激励机制的产物。

> **图 9 | 人类基线员的成功率与时间视界。** 横轴为任务长度，纵轴为成功率。注意：该时间视界与 ML 模型的时间视界**不可直接比较**（见 C.1.4）。

#### C.1.5 基线时间分析

我们人工观看并标注了 50 条基线的录像，以了解基线员如何花时间。基于这一小规模调查：

1. 在短任务（5–15 分钟）上，相当大一部分时间（**25%–75%**）花在阅读指令或理解如何正确提交上。特别是对于短任务，我们的时间估计可能难以解释，因为"阅读指令"存在某种固定开销，它与实际执行任务本身的难度无关。
2. 我们的任务被设计成需要相对较少的上下文，但基线员仍有超过 **25%** 的时间用于回忆相关信息（例如怎么做端口转发）。

### C.2 内部 PR 任务

**摘要。** 我们在一个内部仓库的 5 个未被污染的问题上运行了 GPT-4o、Claude 3.5 Sonnet (New) 和 o1。解决这些问题是内部员工完成的真实工作，因此我们可能预期这些任务上的结果比典型基准任务更能代表"在有经济价值的真实任务上的表现"。

我们发现：**我们的合同基线员解决问题所需的时间是仓库维护者的 5–18 倍**。此外，如果用承包商完成时间来衡量任务长度，AI agent 在这些 issue 上的表现与从 HCAST、SWAA 和 RE-Bench 推导出的 AI agent 成功率曲线并不矛盾。但我们的合同基线员完成这些任务所需的时间远长于仓库维护者。这表明：**时间视界可能更对应于"低上下文人类"的劳动，而不是"高上下文人类"的劳动。**

**方法。** 我们从一个内部仓库收集了 5 个真实的、近期的、未被污染的问题，然后在这些问题上运行 GPT-4o、Claude 3.5 Sonnet (New) 和 o1。我们记录了仓库维护者解决这些问题所花的时间，也让外部基线员尝试修复。**与 SWE-bench Verified 不同，我们没有做任何筛选来要求这些问题可自动验证**；相反，相关仓库的维护者像审阅 PR 一样，对模型和基线员的方案进行人工打分：

1. **0** —— PR 不正确且需要根本性重构；
2. **0.25** —— 合并前必须做少量修改；
3. **0.75** —— 有一些小瑕疵（nits）但 PR 仍可合并；
4. **1.0** —— PR 可以按原样合并。

**示例问题。** 我们给出两个示例——一个简单的（Issue 1）和一个更具挑战性的（Issue 8）。Issue 8 展示了对代码库的上下文如何在基线员与仓库维护者之间造成巨大的人类完成时间差异。

**人工评分方法与结果。** 维护者、基线员和模型的方案都像 PR 一样被人工打分。我们尝试过让承包商打分，也尝试过让不同的仓库维护者打分。实际上，**仓库维护者打分的一致性远高于承包商**：承包商之间的相关性在 50%–60% 之间，而仓库维护者之间在 **88%–91%** 之间。

**评分耗时。** 要让模型在真实工作上有成本竞争力，其完成一个 PR 的总成本必须低于仓库维护者自己实现该 PR 的成本（外加评审者时间等附属成本）。因此我们也跟踪了给模型方案打分所花的时间：仓库维护者打分比承包商快得多（承包商平均每次运行 8 分钟，维护者平均 3.5 分钟），但这个比例不如"完成时间"那么悬殊。不同 issue 的平均打分时间不同，简单的 issue 通常打分快得多，且所有 issue 的打分都快于完成它。未来我们计划创建一个综合成本指标，把评分工作量、模型成本和模型成功率都考虑进去。

**合同基线员 vs. 仓库维护者。** 模型的成功率与"由合同基线员时间预测的成功率"相当一致。实际上，基线员在简单任务上的表现也比有经验的维护者差很多。例如 Issue 11 花了基线员 1.5 小时以上才完成，因此我们不会预期模型能稳定完成该任务。

**定性印象。** 朴素地与 HCAST + SWAA + RE-bench 上"按时间分桶的成功率"相比，**仓库维护者的完成时间并不是这些任务上模型表现的良好预测器**。例如，Issue 11 对维护者而言是最简单的任务——它需要在 10 个 Python 文件中写简单注释，维护者花了不到 5 分钟；但模型在 30 次运行中没有成功完成过一次。也有一些任务模型确实成功了，正如我们按其他任务的时间分桶成功率所预期的那样——例如，模型始终能够在一个数据管道的某个阶段加上缺失的"创建文件夹"步骤。

> **虽然基线员和模型相对于仓库维护者都吃力，但他们吃力的方式不同**：基线员常常缺乏对代码库中所用工具和技术的知识（例如"DVC 是什么？"、"bootstrapping 又是什么？"）；而当前的 AI 模型则始终表现出对工具和技术的了解，但似乎在"在真实代码库中工作所需的更大上下文"上吃力。

| o1-preview | duet |

所有模型都通过 Anthropic 或 OpenAI 的 API，使用 agent scaffold 运行。我们在整个评测集上使用**相同的 agent scaffold**，没有任务特定的 prompt 或 scaffold——唯一例外是 SWAA 任务，它使用一个简单的 prompt scaffold。所有 agent 都被提供了与人类基线员相同的可用工具（affordances）。

**GPT-2 由于上下文长度太短，与我们的 scaffold 不兼容**，因此我们对 GPT-2 在 RE-Bench 和 HCAST 所有任务上填补（impute）了 0 分。我们认为这是合理的，因为能力强得多的 davinci-002（GPT-3）在这个集合上也得 0 分。移除这些填补的 GPT-2 零分，对本文所有后续结果的影响可忽略。

#### C.3.1 Scaffold 与平台细节

大多数 AI 模型用 **modular-public**——一个基础 agent scaffold——评估。该 scaffold 为模型提供 Python 和 Bash 命令，以及一些非常简单的上下文管理，以把输入保持在 LM 的上下文窗口长度之内。我们对 o1-preview 和 o1 使用了略有不同的 scaffold，因为它们似乎在工具使用、响应环境反馈以及一般性地充当 agent 方面比较吃力。

对人类基线和 AI agent 运行，我们的实验都使用开源平台 **Vivaria**。CPU 和 GPU 资源根据任务的资源规格，在安全 VM 内部提供。

modular-public 和 triframe/duet 都吸收了 **ReAct 框架** [Yao 等, 2023] 的原则，即把推理轨迹与动作交错。这些 agent 是在**一个留出（held-out）的开发任务集**上开发的，不包含在 HCAST 中，以降低对这些任务过拟合的可能性。

两种 scaffold 都允许 agent 在调用一组工具之前，通过**思维链推理**做规划。agent 主要通过运行 Python 代码和 Bash 命令与任务环境交互。

- **Modular**：模型生成一条待执行的命令，scaffold 执行该函数调用并返回环境的相关信息（如 STDOUT/STDERR）。该过程重复，直到模型判定答案可以提交，或系统达到预设的使用阈值。
- **Triframe**：为了决定执行哪条命令，模型先生成一个建议的计划，然后基于该计划生成三条可能的待执行命令，再生成三条**忽略该计划**的建议命令（以使其生成的想法多样化）。接着，模型为这 6 个提议动作各生成两个 -2 到 2 之间的分数，scaffold 执行两次打分平均后得分最高的那个函数调用。

#### C.3.2 算力使用

使用的总算力包括：RE-Bench 环境约 **2,000 H100-小时**，其他环境约 **50,000 CPU 小时**（在云和内部机器组合上），加上内部或来自 API 提供商的约 **50,000 H100-小时当量**用于推理。这包括用于初步实验的算力。用于数据分析的算力极少。

### C.4 与项目反应理论（IRT）的对比

IRT 是一组统计技术，用于基于个体的能力水平预测其答对某题的概率。标准的 IRT 两参数 logistic（2PL）模型为（简化自 Cai 等）：

$$T_i(1|\eta_{\text{agent}}) = \sigma\big((\eta_{\text{agent}} - \alpha_{\text{task}}) \cdot \beta_{\text{task}}\big)$$

其中 $T_i(1|\eta_{\text{agent}})$ 表示能力水平为 $\eta_{\text{agent}}$ 的人答对该题的概率。¹⁵

> ¹⁵ 在三参数 logistic 模型中，会加入一个参数 $\gamma_{\text{task}}$，代表猜对该题的概率。在 2PL 模型和我们的方法中，$\gamma_{\text{task}} = 0$。这对大多数任务实际上是成立的，但某些 SWAA 任务是四选一，有 25% 的猜对概率。这一选择只影响 GPT-2 和 GPT-3 的时间视界，不会实质影响我们的结果。

IRT 通常同时对题目难度和能力水平做回归；**相反，我们把题目难度定义为人类基线时间的对数，因此只对能力水平做回归。** 具体地，我们的模型为：

$$T_i(1|h_{\text{agent}}) = \sigma\big((\log h_{\text{agent}} - \log t_{\text{task}}) \cdot \beta_{\text{agent}}\big) \qquad (1)$$

注意相对 2PL 模型的以下变化：

1. $\alpha_{\text{task}} = \log t_{\text{task}}$，其中 $t_{\text{task}}$ 是成功的人类基线时间的几何平均；
2. $\eta_{\text{agent}}$ 现在可以被解释为 $\log h_{\text{agent}}$，其中 $h_{\text{agent}}$ 是 agent 的 **50% 时间视界**，而不是一个抽象的能力参数。这是因为当 $h_{\text{agent}} = t_{\text{task}}$ 时，我们的模型预测成功概率为 $\sigma(0 \cdot \beta_{\text{agent}}) = \sigma(0) = 0.5$；
3. $\beta_{\text{agent}}$ 是一个**依赖 agent** 的学习参数，而不是依赖任务的。

为了拟合式 (1)，我们按多样性给任务加权，使得来自规模为 $n$ 的家族的任务获得权重 $1/\sqrt{n}$。然后用 logistic 回归为每个模型拟合时间视界 $h_{\text{agent}}$ 和斜率 $\beta_{\text{agent}}$。例如，按此方法 **o1 的时间视界约为 39 分钟**（见图 4）。

这些改动使我们能在避开 IRT 若干复杂性的前提下计算出一个可解释的时间视界：

- **第一**，IRT 有一个初始的校准/联合优化阶段，从所有 agent 的分数中估计题目难度，因此一个 agent 的能力分数可能依赖于其他 agent 的表现；而我们的方法为每个 agent 单独计算时间视界。
- **第二**，IRT 输出的是"能力分数"，之后还需要转换为时间视界估计；我们的方法通过直接估计视界省掉了这一步。
- **第三**，2PL 模型对每个任务用一个斜率参数，而我们对每个 agent 用一个斜率参数。在我们的设定中 agent 数远少于任务数，这减少了总参数量。

作为交换，我们放弃了使用 IRT 中为测试设计而生的指标（例如单个题目的 Fisher 信息函数，见 Kipnis 等 [2025]）。未来改进的方法可以把这些指标纳入，以设计基于人类数据的、样本高效的基准与评测。

## 附录 D 定性分析

### D.1 失败类别

为了更好理解当前与较早期 AI agent 失败的差异，我们分别抽样了 **31 次 GPT-4 1106** 的失败运行和 **32 次 o1** 的失败运行，并按以下互斥类别手工标注：

- **规划与工具选择不当**：agent 生成的高层计划本身就似乎行不通，或为计划挑选的工具无法实现预期目的。
- **心算或推理错误**：agent 在关键步骤上做了错误的心算或逻辑推理，导致运行失败。
- **过早放弃任务**：agent 在尝试中途放弃任务，要么提交一个荒谬的答案，要么提交一个未经正确性检查的方案。这类失败常常源于 agent 在查看完所有得出正确解所需的代码或信息之前就提交了答案。
- **重复失败动作**：agent 重复同样的、对问题没有推进的行为，例如一遍又一遍地运行一条导致错误的命令，而不尝试其他方法。

结果见表 2。我们发现：**GPT-4 的失败中有超过三分之一源于重复失败动作**，而 o1 只有 2/32——我们将其视为"模型在适应错误的能力上似乎有所提升"这一论断的定量证据。**o1 的失败中有一半源于过早放弃任务**，而 GPT-4 只有四分之一——这可能是因为 o1 的失败发生在质性上更困难的任务上，也可能反映了 o1 的某些特性。

### D.2 较新模型的特定技能

为了更好地为"模型性能提升"这一观察到的趋势提供情境，我们检视了那些"早期模型（如 GPT-4）明显比当前模型差"的任务的轨迹。具体地，我们把所有任务家族按所需专长类型分类，并注意到：当前模型在涉及 **ML 训练**、**逆向工程编译后的软件二进制文件**和**网络安全 CTF** 的任务上，往往大幅超越早期模型。此外，我们注意到 agent 在需要"对 AI agent 自身局限有情境觉察（situational awareness）"或"击败对抗策略"的任务上进步巨大。这给了我们五组任务家族去检视。

对这五组任务家族中的每一组，我们让承包商人工阅读所有模型在该家族所有任务上的全部运行，识别出 AI agent 表现提升的可能解释，以及潜在的局限。

#### D.2.1 较新的模型哪些方面做得更好？

**对错误的鲁棒性更强。** 模型随时间的推移变得越来越鲁棒，尤其似乎能够避免重复失败动作。早期模型往往连微不足道的错误都无法纠正，反而陷入循环行为或引入额外错误。然而，**从 GPT-4o 开始**，模型表现出更强的从错误中恢复和纠偏的能力——这种能力在 pico_ctf 任务的困难变体、或其他需要迭代的编码相关任务中尤其宝贵。以一个"调试少量 Python 代码"的任务为例：

1. 在一次运行中，`gpt-4-turbo-2024-04-09` 在一个 Python 文件中引入了与"反斜杠字符放错位置"有关的语法错误，尽管尝试了很多次，仍无法理解或修复该问题，最终放弃。
2. **Claude 3.5 Sonnet (New)** 先把代码加在了错误的位置，然后多次尝试用 CLI 工具 `sed` 把代码加到正确的文件，期间遇到 `IndentationError` 和方法重复。最后它成功地转向"从头重写整个文件"。

   > *"抱歉造成了困惑。看来我们之前的尝试没有完全移除旧的 `save` 方法。让我们再试一次来修复 `base_model.py` 文件……"* → *"抱歉，这个问题持续存在。看来我们之前的尝试没有彻底解决问题。让我们再试一次，通过完全重写文件内容来修复 `base_model.py`："*

**工具使用。** 早期模型如 davinci-002（GPT-3）在语法正确的工具使用上都很吃力，而后来的模型在其 prompt 中提供了清晰的解释和示例后有所改进。当前前沿模型一般可以无碍地使用我们 scaffold 提供的工具。例如我们注意到：当任务需要编辑 Python 脚本时，**GPT-3 即便被给予明确指令也难以处理格式**；**GPT-4o 有时会用 bash 中的 echo 命令一行一行地写脚本**；而 **o1-preview 则始终高效地编辑文件**。

> 反例（GPT-3）：*"上一条消息中没有包含函数调用。请在下一条消息中使用 `<[tool_name]> [args] </[tool_name]>` 语法包含一个函数调用。"* → 随后它输出了一串 `bash> touch test.txt`、`python> import time` 之类格式错误的命令。
> 反例（GPT-4o）：*"我将使用 echo 命令，一次一行地把脚本内容直接写入脚本文件。"* → `echo 'def read_nth_line(file_path, n):' >> update_test_txt.py`、`echo ' with open(file_path, "r") as file:' >> update_test_txt.py`……

**逻辑与编程问题解决能力改善。** 与编码和推理基准上表现的提升一致，我们看到模型编写语法和语义正确代码的能力逐步增强。这使模型能更可靠地正确理解任务指令，并用代码找到正确答案。

> 例如，在 `interpret_data` 任务上，GPT-4o 在一次运行中失败，因为它把"找出 1972 年世界上最高的建筑"错误理解为"找出**建于** 1972 年的世界上最高的建筑"，而不是常识理解（"1972 年时世界上最高的建筑"）。它写出的代码是：
> `tallest_building_1972 = data[data['completion_year'] == 1972]['height_m'].max()`
> 相比之下，**o1-preview 正确地把该请求理解为"找出在 1972 年或之前建成的世界上最高的建筑"**。

#### D.2.2 它们哪些方面仍然做得不好？

尽管有改进，即便是当前的前沿模型仍在若干重要方面吃力。总的来说，我们的观察表明：**agent 在质性上"更混乱"的任务上表现往往更差**（我们在第 F.2 节进一步研究这一论断）。

**AI agent 在没有清晰反馈时吃力。** 在缺乏清晰反馈或低成本验证手段（如单元测试或答案检查脚本）的情况下，我们测试的所有模型都常常难以判断自己的解是否正确。例如，在各自时间桶中对模型最难的两个任务是 `blackbox` 和 `symbolic regression`——两者都涉及"在探测信息有代价的约束下猜测一个隐藏函数"。

**AI agent 常常不能主动寻找相关信息。** 我们还观察到，所有模型在"理解自身局限"或"主动寻找有用信息"方面仍有不足；相反，模型倾向于假定自己已经知道如何完成任务，只有在失败之后才重新评估。

> 例如，在一个"试验某个 API 接口"的任务中，agent 被告知可以在本地的一个 markdown 文档里读到更多关于该 API 的信息。但即便 agent 最终成功了，它们通常也是**先幻觉或猜测 API 端点**，只有在从任务环境中遇到错误后才去读那个 API 文档。
> 在一个夺旗（CTF）任务中，agent 需要用 python 打开一个编码未知的文件，常常因为指定了错误的编码而在第一次尝试时失败。即便是最好的模型，其反应也是在 python 脚本里逐个试不同的编码——既低效又浪费 token。我们从未见过有 agent 运行能直接识别出所需编码的 bash `file` 命令。

## 附录 E 进一步讨论

### E.1 常数因子 vs. 斜率变化

虽然外推总是不完美的，但**对 AI 时间视界做远期预测，对"倍增速率的变化"远比对"时间视界的常数因子"敏感**。例如，基于 o1 的 39 分钟时间视界和过去 218 天（约每年 3.2 倍）的倍增时间做朴素外推，预测 AI 将在 o1 发布日期之后约 **4.8 年**达到 1 个月的 50% 时间视界（大约相当于相对 o1 再翻 8 番）。倍增时间增加 2 倍会把"1 个月"这个点再推迟 **4.8 年**；但时间视界上 2 倍的常数因子下降只会把它推迟 **0.6 年**。

### E.2 可能改变时间视界斜率的重要因素

**Agentic 训练（agency training）。** 2024 年以来视界的增长——可能快于长期趋势——可以用"研究者用基于结果的 RL 对模型做后训练，使其更具 agentic（即能够朝着完成任务采取许多连续行动）"来解释。让模型具备能力和 agentic 的研究很可能继续。未来的 agentic 训练可能快于长期趋势（因为在提升视界长度上，后训练可能比预训练更具算力效率）。但 2024–2025 年的 agentic 训练也可能只是"摘低垂果实"带来的一次性提升，一旦这些收益耗尽，视界增长就会放缓。**总的来说，我们认为 agentic 训练更可能提升（相对于 2019–2024 年趋势的）时间视界增长率。**

**算力规模化（compute scaling）。** 从 GPT-2 发布至今，用于训练最令人印象深刻的前沿语言模型的算力至少增长了 **10,000 倍**（Epoch AI [2024]），训练算力使用每 6–10 个月翻一番（Sevilla 等 [2022]）。更近期地，o1 和 o3 等模型开始在推理时使用更多算力。目前不清楚在未来 5 年内是否有足够的能力把训练或推理算力再扩展许多个数量级。然而，**算法改进**——历史上它降低了固定性能水平所需的算力（Erdil & Besiroglu [2023]；Ho 等 [2024]）——可以替代算力限制。我们认为，算力规模化的限制会在一定程度上减缓 AI agent 时间视界的增长，但会被对算法改进的更多投入部分补偿。

**AI 研发自动化。** AI 研发的主要投入是算力和研究者时间。如果未来的 AI 系统能够替代人类研究工程师、和/或提高训练的算力效率，AI 进展的速率就会提高。我们认为：**一旦前沿 AI 的时间视界达到数十小时，就很可能出现大量的 AI 研发自动化**，从而缩短从那时到"1 个月视界 AI"的时间。

**AGI 将拥有"无限"时间视界。** 无限的时间视界并不意味着一个能力任意强的 AI，而只是意味着**能够完成人类需要任意长时间才能完成的任务**。如果一个通用人工智能（AGI）能够以至少 X% 的成功率完成专家人类所能完成的所有任务，那么它的 X% 时间视界必然是无限的。因此，如果这样的系统被开发出来，时间视界的长期趋势将**快于指数**——并在 AGI 部署的日期处有一条渐近线。

### E.3 如何解读时间视界

虽然时间视界是衡量 AI agent 能力的直观指标，但测量它需要一个带有"人类时间"标注的大规模数据集，而且**时间视界总是相对于某个任务分布、以及基线员的上下文与技能水平来衡量的**。

**上下文与技能效应。** 在真实公司里，初级软件工程师新员工常常需要数周的入职培训才能开始贡献经济价值。而决定大多数任务长度的人类基线员，其上下文远少于普通员工，这可能**增大了测量到的任务长度**。我们的任务被设计成需要最少的上下文，这在一定程度上缓解了这个问题；我们的内部 PR（第 C.2 节）并非如此设计，因此基线员花的时间是员工的许多倍。然而，**高技能的基线员完成任务也可能远快于普通员工**——我们的专家基线员可能比普通软件工程师技能高得多，这可能**减小了测量到的任务长度**。（两种效应方向相反。）

**任务分布效应。** 图 3 显示，AI agent 的成功率并不能被人类完成时间完美预测，这意味着还有其他因素显著影响任务难度。当模型在研究数学、计算生物学或法律等不同智力劳动领域被测量时，我们预期它们的时间视界会不同。

**测量极端时间视界。** 要准确测量一个 AI agent 的 X% 时间视界约为 $t$ 分钟，需要**许多**人类长度为 $t$、且该 AI agent 以约 X% 成功率完成的任务。这有两个含义：**其一**，准确测量非常长的时间视界需要一个带有长人类基线运行的困难任务数据集，而这构建起来可能不切实际，尤其是因为现实困难任务的成功标准往往复杂到需要人工评分；**其二**，在极高成功率（95%、98% 或更高）下测量时间视界，需要规模非常大、标签噪声近乎为零、且能覆盖其意图代表的任务总体的数据集。

**人类时间视界的测量。** 理论上，人们也可以测量一个人类或人类群体的时间视界。但这样做存在理论和实践上的双重困难，我们在附录 C.1.4 中有更多讨论。

### E.4 局限与未来工作

我们认为本工作有若干可以改进之处。

**更多模型 + 更好的能力激发。** 一般来说，我们发现**恰当地激发（elicit）模型可以对其表现产生非常大的差异**。¹⁶ 我们在激发模型以在我们的任务上取得好成绩方面投入有限，因此虽然我们的结果是一个合理的下界，某些模型可能拥有比我们所展示的更强的能力。投入最多的是 o1 和最初的 Claude 3.5 Sonnet，各自约有 **2–3 个工程师周**的迭代开发。所有其他模型使用相同 scaffold，最多做微小改动。未来工作可以在更充分地激发前沿模型全部能力的前提下复现我们的结果。

> ¹⁶ 这是一个常见的观察；参见例如 AIDE [Jiang 等, 2025] 带来的软件开发能力提升，或近期关于 KernelBench 的工作 [METR, 2025]。

**更严格的人类基线。** 我们逐任务的人类时间估计可能因样本量较小而噪声较大，还可能以各种方式系统性偏斜。最显著的是：**我们只选择任务的成功完成**，并鼓励基线员放弃那些他们可能无法在合理时间内完成的任务。我们基线员的技能差异也很大，而这些任务涉及的相关技能范围很广。虽然我们试图把基线员匹配到合适的任务，这个过程不太可能完美。从对基线尝试的人工复核中，我们还观察到：人类有时即便在任务看似在其能力范围内时也直接放弃，而这"对成功时间的分布产生了什么样的选择效应"并不清楚。关于人类基线时间偏差如何影响我们的结果，详见附录 C.1.4。未来工作可以用更严格的人类基线员挑选来复现我们的结果，或探索结果对"人类基线相关方法学选择"的敏感性。

**更自然、更多样的任务。** 有理由相信我们的任务分布与有经济价值的工作分布存在系统性差异（也许还与风险模型相关任务的分布存在系统性差异）。我们在第 4 节探索了其中一些原因，但仍有不少差异我们没有探索。例如，这些任务中的交互模态也相对狭窄——**没有任何任务需要使用鼠标**；**没有任何任务需要与其他人类或 agent 合作或竞争**¹⁷，而真实的软件工程或 ML 研究涉及与管理者、其他工程师或研究者沟通协调；许多真实任务需要非常高的可靠性，而由于在这些任务上测量模型的难度，它们在我们的数据集中代表性不足。**最重要的是，我们研究的任务严重偏向软件工程和 ML 研究。** 未来工作可以探索 AI agent 的能力在其他领域如何进展。

> ¹⁷ 参见 Xu 等 [2024]，一个需要在相对真实设定下进行多 agent 交互的近期基准示例。

**更多地使用推理算力。** 我们的 scaffold 对推理时算力的使用相对有限。在假设人类专家按 **$143.61/小时**（Google L4 工程师平均年薪除以 2,000 小时）计酬时，**超过 80% 的成功运行成本低于人类完成同一任务成本的 10%**（图 14）。这意味着：如果推理时计算可以用来提升性能，那么在保持与人类专家相比仍有经济竞争力的前提下，还有很大的空间可用。先前研究发现，best-of-k 等技术可以在这些任务的一个子集上大幅提升表现（Wijk 等 [2024]），更好地利用推理时算力可能导致显著不同的分数。

**数据分析。** 2024–2025 年的趋势看起来快于 2019–2025 年的趋势，但由于模型数量少，不清楚这是否只是噪声。未来工作应包含假设检验以检测可能的 2024 年斜率变化，并用更复杂的统计方法为整体预测构建可信区间。此外，我们在多个估计阶段（基线数据 → 任务难度评级、时间视界计算、线性回归求趋势）中损失了一些信息，**端到端的方法可能更具数据效率**。

### F.1 用 2023–2025 数据做回测

作为本文探索性工作的一部分，我们**仅使用 HCAST 和 RE-Bench 两个子集**，测量了 2023 和 2024 年发布的 9 个前沿及接近前沿模型的时间视界。这条趋势（加上 Claude 3.7 Sonnet 和 o3）见图 10：时间视界大约每 **6 个月**翻一番。由于我们只有两个 2023 年模型（GPT-4 0314 和 GPT-4 1106），且数据范围小（发布日期跨度 2 年，时间视界跨度 5 个倍增），误差棒非常宽。此外，把数据进一步限制为"仅 2024 年模型"会得到一条不同的趋势——时间视界约每 **3 个月**翻一番——因此任何向未来的外推都不会稳健。

为了解决这些问题，我们收集了更多数据以把趋势线向过去延伸：开发了 **SWAA** 子集，把任务集的最短人类时间从 1 分钟降到 2 秒以下，从而能在合并后的任务集上测量 GPT-2、davinci-002（GPT-3）和 GPT-3.5-turbo-instruct。

**2023–2025 年的趋势可能快于更长期的趋势**（图 11）。整个 2019–2025 六年期间测得的倍增时间为 **207 天**，比基于"非 SWAA 任务 + 2023–2025 模型"得到的 172 天趋势更平缓。不过，这一差异仍在误差范围内。

### F.2 混乱度（messiness）因子

真实世界的智力劳动常常包含基准通常不会包含的混乱细节，例如：定义不清或范围不明、反馈回路或成功标准模糊、或需要实时协调多条工作流。我们普遍观察到 **agent 在具有这些"混乱"细节的任务上更吃力**（第 3.3 节）。一个自然的问题是：agent 在"较不混乱"和"较混乱"任务上是否表现出相似的改进速率？

我们按 **16 项属性**给 HCAST 和 RE-Bench 任务打分，这些属性我们预期（1）能代表真实世界任务可能比我们研究的任务系统性更难的方式，且（2）与 AI agent 表现相关。一些示例因子包括：任务是否涉及新颖情境、是否受有限资源约束、是否涉及实时协调、是否源自真实世界环境。我们对 RE-Bench 和 HCAST 任务标注这 16 项混乱度因子的存在与否，然后加总得到一个 **0 到 16 的"混乱度分数"**。因子定义见附录 H.6。

HCAST 和 RE-Bench 任务的平均混乱度分数为 **3.2/16**，**没有任何任务的分数高于 8/16**。作为对比，像"写一篇好的研究论文"这样的任务，根据具体情形会得分 **9/16 到 15/16**。

在 HCAST 任务上，**AI agent 在更混乱的任务上表现确实差于仅从任务长度预测的水平**（$b = -0.081$，$R^2 = 0.251$），见图 13。任务混乱度每增加 1 分，平均成功率大约下降 **8.1%**。¹⁸

> ¹⁸ 这里用线性近似是为了以一种直观的方式粗略量化该效应的大小。

然而，**AI agent 性能随时间的趋势，在任务集的低混乱度和高混乱度子集上是相似的**。例如，在 1 小时以内的任务上，从 2023 年 1 月到 2025 年 5 月，高混乱度分组和低混乱度分组的成功率都提高了 **40 个百分点**（图 12）。特别是，我们没有发现任何证据表明高混乱度子集存在"明显更慢的性能趋势"或"平台期"。

## 附录 H 更多消融与鲁棒性检查

由于我们用这些分析来指导方法学选择，这些消融是相对于最终报告中略有不同版本的流水线进行的。具体来说，它们包含一组略有不同的基线，以及不同的任务成功筛选方式。消融项包括：

2. 把任务集重新归一化为 log-uniform 之外的其他分布

### H.1 替代的曲线拟合

> **图 15 | 2019 年以来模型时间视界的线性、双曲和指数拟合。**

在我们的主要结果中，我们拟合一条**指数曲线**（在 log y 轴下为线性），因为拟合非常好（$R^2 \geq 0.96$，取决于具体数据和方法学）。线性和双曲曲线拟合很差（图 15）。由于我们研究的时间跨度内只有 12 个前沿模型，而指数拟合仅用两个参数就达到如此高的 $R^2$，我们认为应用参数更多的拟合更可能过拟合、而不是给出准确预测。我们特别考虑过：

- **双指数函数** $\log(\text{horizon}) \sim a + b\exp(c \cdot (\text{release\_date} + d))$，它严格比指数更具表达力（因为当 $x$ 小时 $\exp(x) \approx x$，当 $c$ 小时二者等价）；
- 同样地，任何饱和 logistic 函数 $\text{horizon} \sim a \cdot \sigma(\text{release\_date} + d)$ 的初始部分看起来都非常像指数，而**在没有任何证据表明 AI 视界正在趋平的情况下（按我们的指标），本质上不可能预测它是否、何时、以及会持续多久地进入平台期**；
- 渐近于无穷的复杂随机模型往往有很大的不确定性（参见 Roodman [2020]，他把一个超指数扩散模型应用于经济数据）。正如我们在第 5 节讨论的，在构建长期预测的预测区间时，较大的不确定性可能是恰当的；但对我们提到的这些因素做定量建模超出了本文范围，因此我们选择定性地讨论它们。

> **图 16 | 使用连续（未二值化）评分的时间视界。** Claude 3.7 Sonnet 的 50% 时间视界接近 2 小时。我们认为该方法从 8 小时的 RE-Bench 任务中捕获了更多信号，但**高估了近期模型的时间视界**——因为在大多数任务上取得 0.5 的平均分，要比"50% 的情况下达到人类表现"更容易。斜率也很可能被高估，因为较长的任务往往是连续评分的。

### H.5 SWE-bench Verified

**数据收集。** 我们从官方 SWE-bench 评测结果仓库收集了前沿模型的"逐模型、逐任务"结果：Claude 3 Opus、Claude 3.5 Sonnet (Old)、Claude 3.5 Sonnet (New)、GPT-4 1106、GPT-4o 和 o1。注意这只是我们主要结果中 11 个模型里的 6 个。

**时间估计。** SWE-bench Verified 包含由承包商创建的时间估计，把任务分成四个桶：<15 分钟修复、15 分钟–1 小时、1 小时–4 小时、>4 小时。这些估计基于"一位有几小时时间熟悉代码库的工程师"解决该问题所需的预期时间。

我们通过跑 7 条基线、跨 6 个 SWE-bench Verified 任务来验证标注者的时间桶。我们在"<15 分钟修复"桶中做了 4 个任务的基线，发现我们的基线员分别花了 **8、26、67 和 84 分钟**。我们在"1 小时–4 小时"桶中做了 2 个任务的基线，两位基线员都花了 **2–3 小时**。

**分析方法。** 我们把标注者的时间范围估计转换为逐任务的时间估计：取时间桶起止时间的**几何平均**。我们为 SWE-bench Verified 任务选择 **16 小时**作为上限，但该时间桶中只有 3 个任务，不会对结果产生实质影响。然后我们应用与第 3 节相同的方法，把逐模型、逐任务的结果和任务时间估计转换为模型时间视界。为减少相似任务的影响，我们把"属于同一仓库的 issue"视为同一任务家族，并按同一家族中任务数量的平方根对任务贡献做降权。

### H.6 混乱度因子

混乱度因子标签由 2 名内部承包商和 1 名研究员收集。完整的 16 项混乱度因子及定义见表 10 和表 11（此处给出因子名与要点释义）：

**表 10 | 混乱度因子定义 1–8**

| 因子 | 定义要点 |
| --- | --- |
| **真实来源**（Real life source） | 该任务是否意图代表某个真实的端到端任务，或源自真实问题；**且**没有被有意简化为更小更简单的子任务 |
| **资源受限**（Resource limited） | 是否需要使用某种有限的一次性消耗资源，且"明智地使用该资源"比"明智地使用默认资源限制（时间/token/成本）"更关系到成败；资源在任务内不易补充（如对验证器的查询次数有限、猜测次数有永久计数器扣分） |
| **不易重置**（Not easily resettable） | 在没有采取明显糟糕动作的前提下，agent 是否难以把与成败相关的状态重置回初始状态；"容易重置"应能在无需事先规划的情况下完成，但可以基于到此为止的动作历史做回溯 |
| **不可逆转的失误可能性**（Irreversible mistake availability） | 是否有超过 20% 的可能，一个第 20 百分位水平的人（具备该领域背景但无此任务特定上下文）会在前 50% 时间里犯一个永久性、不可逆地降低其可得分数的错误 |
| **动态环境**（Dynamic environment） | 任务是否涉及"即便 agent 不采取任何行动也会变化"、且对成败重要的环境交互（只要在任务的重要部分成立即可） |
| **困难的反事实归因**（Difficult counterfactuals） | 是否存在显著的、与成败相关的部分，使 agent 难以判断某个效果应归因于自己的（不）行动还是其他因素（例如分布式系统中的偶发级联故障、加日志会改变被观察系统的行为） |
| **非纯自动评分**（Not purely automatic scoring） | 任务是否**不**具有完全自动的评分函数；包括评分函数存在返回 None 的分支并提供人工评分说明，或存在"未被自动评分实际检查的规则条款" |
| **需要隐式泛化**（Implicit generalizability required） | 是否显著可能以"满足字面成功条件但违背任务精神/产物对隐含目的无用"的方式通过；即 agent 是否必须对**未**在任务提示中明确说明的软约束做出合理判断，且这些隐式要求在评分中被检查 |

**表 11 | 混乱度因子定义 9–16**

| 因子 | 定义要点 |
| --- | --- |
| **评分描述不明确**（Non explicit scoring description） | （a）评分所依据的约束并非全部明确说明，**或**（b）评分的描述方式使评分中仍存在显著隐藏信息；**且**（c）这种关于评分的信息缺失在任务内产生了与行动选择相关的不确定性（例如两个被优化因素在评分中的确切权重不确定） |
| **次优行为被利用**（Is suboptimal behavior exploited） | 任务是否涉及与其他会主动利用 agent 弱点或次优行为（或其产出）的 agent/程序竞争 |
| **未提供验证机制**（No provided verification mechanisms） | 任务没有提供让 agent 在运行中检查自己答案或分数的方式，需要 agent 做非平凡的工作才能检查答案 |
| **实时协调**（Real-time coordination） | 是否需要与其他 agent 或服务实时协调，或需要熟练地并行编排多个实时进程（仅在任务要求并行跑多个训练时才算） |
| **需要自我修改**（Self modification required） | 是否需要 agent 修改自身的一部分、用于与环境交互的代码、为自己创建新工具，或创建可用于此的数据 |
| **需要自我改进**（Self improvement required） | 是否需要 agent 以某种**永久提升其在广泛任务分布上表现**的方式改进自己（例如生成能提升自身通用 agent 能力的微调数据；仅提升某个狭窄任务则不算，而算"自我修改"） |
| **需要信息搜寻**（Information seeking required） | 任务是否需要收集 agent 事先不会知道的信息（例如探测一个新系统的行为） |
| **新颖情境**（Novel situation） | 任务是否具有某种不寻常的约束或属性——若没有它任务会显著更容易或更机械，且它是任务难度的重要来源 |

在图 20 中，我们把 HCAST 任务的混乱度分数对人类完成时间的对数作图。我们发现：**混乱度与任务长度相关**，而且我们几乎没有"短但高混乱度"的任务。我们还按模型表现给每个点上色：**人类耗时长且高混乱度的任务往往成功率低**，反之，较短、较低混乱度的任务成功率高。

> **图 20 | 更混乱的任务往往更长。**
> **图 21 | 模型在 HCAST + RE-Bench 任务上按混乱度评分分组的成功率。** 模型在较不混乱的任务上成功率更高，但两个子集随时间的改进速率相似。davinci-002 和 gpt-3.5-turbo-instruct 在"高混乱度的 HCAST + RE-Bench 子集"上都得 0 分。

我们混乱度因子的一个局限是：它们**至少在某种程度上是针对当前模型做对抗性挑选的**。这是两个因素叠加的结果——我们挑选"被认为与模型表现相关"的因子，且所有这些因子都被预期会让任务更难。因此，我们可能预期模型表现与我们任务混乱度指标的负相关程度**强于其应有水平**——并且基于混乱度的预测性调整，对远早于或远晚于本次分析时间发布的模型效果会更差。

### H.7 随机化文件名

为了更好地理解混乱度对 agent 和人类表现的影响，我们修改了一个现有的 HCAST 任务——该任务要求在本地的 LaTeX 和 PDF 文件中查找某条特定信息——做法是随机化文件名和文件夹名，并提供更少的关于"要搜什么"的信息。

**方法。** 被修改的具体 HCAST 任务叫 **Local Research TeX**。未修改版本把 agent 环境初始化为一组嵌套的文件夹和内容，然后提示用户找到某条特定信息，例如："根据 AR 报告，表现最好的 agent 完成了多少个任务？"agent（或人类）随后必须搜索本地文件夹和内容，找到该问题的具体答案（本例中是"four"）。我们的修改包括：

1. 把提示从"According to the AR report"改为"在 `/home/agent/resources/` 中的某个资源里找到下列问题的答案"；
2. 把所有文件夹名改为随机整数，把所有文件名改为像 `final`、`my_file` 这样无意义的名称。

然后我们在该任务的原始版本和修改版本上各跑了约一百次 agent 运行，比较各自的成功率，并用我们的标准基线方法计算人类完成时间。

**结果。** 出人意料的是：**o1 在更混乱的报告变体上的平均表现更好，而人类基线员的表现则差得多。**

| 任务变体 | 成功率 | 基线员时间 |
| --- | --- | --- |
| `local_research_tex/ar_report` | 34% | 24 分钟 |
| `local_research_tex/ar_report_scrambled_files` | 50% | 53 分钟 |

定性地看，o1 在文件名被打乱的变体上做得更好，是因为**它的提示里没有被给予 "AR report" 这个术语**。实践中，o1 常常决定去 grep "AR report" 这个词却找不到（因为实际报告名为 "ARA report"），然后就开始猜测。相反，当被告知去某个资源里找时，o1 会执行更通用的搜索，（更经常地）找到它要找的报告。

虽然这只是一个有限的例子，但我们相信它进一步说明了**量化和预测"任务的哪些方面会如何影响 agent 表现"是困难的**——事实上，让人类在某些任务上变差的因素，确实可能提升 agent 的表现。

### H.8 agent 之间的表现相关性

## 术语与背景速览（译者整理）

| 术语 | 含义 |
| --- | --- |
| **时间视界（time horizon）** | 模型能以给定成功率完成的"任务时长"（以人类完成时间来刻度）。X% 时间视界 = 成功率降到 X% 时对应的任务长度 |
| **50% 时间视界** | 本文主指标。o3 ≈ 110 分钟；GPT-2 ≈ 2 秒 |
| **HCAST** | METR 的多样化软件/安全/ML 任务集（本文用 97 个任务，1 分钟–30 小时） |
| **RE-Bench** | 7 个 8 小时量级的 ML 研究工程任务 |
| **SWAA** | Software Atomic Actions，66 个 1–30 秒的单步动作任务，用于把趋势线延伸到 2019 年（测 GPT-2/GPT-3） |
| **Baseliner** | 人类基线员，具领域专长但无任务特定上下文；用于给任务打"人类时长"标签 |
| **Messiness（混乱度）** | 16 项因子打分（0–16），刻画真实任务比基准任务"更难"的系统性维度（动态环境、资源受限、需实时协调等） |
| **Excess success rate** | $(S_{obs} - S_{pred}) / S_{pred}$，剔除"任务长度 + 模型能力"后仍残存的表现差异 |
| **Scaffold / agent** | 模型 + 工具外壳。本文主要用 `modular-public`（ReAct 风格），o1 用 `triframe`，o1-preview 用 `duet` |
| **Elicitation** | 能力激发：prompt/scaffold 调优以让模型发挥真实水平。本文承认投入有限，结果是"下界" |
| **IRT / 2PL** | 项目反应理论两参数 logistic 模型。本文把"题目难度"固定为人类基线时间的对数，只回归能力，从而直接得到可解释的视界 |
| **Vivaria** | METR 开源的 LM agent 评测平台，人类基线与模型运行都在其中进行 |
| **External validity** | 外部有效性：基准上观察到的趋势能否推广到真实世界经济任务 |
| **Agency training** | 用基于结果的 RL 对模型做后训练，使其更会"连续行动"，被认为是 2024 年后趋势加速的主因之一 |

**核心数字速记**

- **任务集**：170 个任务（HCAST 97 + RE-Bench 7 + SWAA 66）；人类基线 800+ 次、累计 **2,529 小时**；148/169 个任务有真实人类基线
- **基线员画像**：软件工程 / ML / 网络安全专业人士，平均约 **5 年**经验，多数来自世界前 100 大学
- **主结果（2019–2025）**：50% 时间视界每 **207 天**翻一番，95% CI **166–240 天**（≈7 个月）
- **两端锚点**：GPT-2 = **2 秒**；o3 = **110 分钟**（且 o3 显著高于长期趋势线，p = 0.006）
- **80% 时间视界**：倍增时间 **204 天**（与 50% 无显著差异），但绝对视界短 **4–6 倍**
- **SWE-bench Verified 交叉验证**：倍增时间约 **70 天**（比本文任务集的 143 天更陡，疑因标注者低估简单任务时长）
- **混乱度效应**：混乱度每 +1 分，平均成功率 −8.1%（$b=-0.081$，$R^2=0.251$）；但高/低混乱度子集的**改进速率相同**（2023-01→2025-05，1 小时内任务成功率均 +40 个百分点）
- **内部 PR 实验**：承包商比仓库维护者慢 **5–18 倍**；模型表现与"承包商时间"一致，与"维护者时间"不一致 → 视界对应的是**低上下文人类**
- **成本**：假设人类专家 $143.61/小时，>80% 的成功运行成本 < 人类成本的 10%
- **外推**：1 个月（167 工作小时）AI 的 80% CI ≈ **2028 年中 – 2030 年中**，中心估计 **2029 年中**；若按 2024–2025 趋势，一半概率落在 **2027 年**、甚至 **2026 年末**
- **算力**：RE-Bench 环境约 2,000 H100-小时 + 其他环境 50,000 CPU 小时 + 推理约 50,000 H100-小时当量
- **失败模式迁移**（GPT-4 1106 → o1）：重复失败动作 12/31 → 2/32；过早放弃 8/31 → 16/32
