## 摘要

推理时技术（inference-time techniques），例如重复采样（repeated sampling）或迭代式修改（iterative revisions），正在成为在测试阶段增强大语言模型（LLM）能力的强有力手段。然而，如何构建把多种技术组合在一起的系统，目前仍缺乏成熟的最佳实践，原因有三：我们对每种技术在不同模型、不同任务上的效用理解有限；我们对技术之间的相互作用理解有限；以及组合这些技术所带来的巨大搜索空间。

为应对这些挑战，我们提出 **Archon**——一个模块化、自动化的框架，用于优化推理时技术与 LLM 的**选择与组合**过程。给定一个算力预算（compute budget）和一组可用的 LLM，Archon 会在一个庞大的设计空间中探索，为目标基准（benchmark）发现量身定制的优化配置。它既可以设计**任务专用（custom）**架构，也可以设计**通用（general-purpose）**架构，并把「准确率 vs. 最大 token 预算」的帕累托前沿（Pareto frontier）相对当前最强基线向前推进。

在指令跟随（instruction-following）、推理（reasoning）与编码（coding）三类任务上，我们证明 Archon 能够利用额外的推理算力预算，设计出平均超越 OpenAI o1、GPT-4o、Claude 3.5 Sonnet 等前沿模型 **15.1%** 的系统。

## 1 引言

> **图 1 | Archon 的性能随推理预算增长而有效扩展。**图中横轴为最大 token 预算（对数刻度），纵轴为各基准上的平均性能；Archon 的曲线随预算增长持续抬升，且在同一预算下始终位于基线之上。逐数据集的分析见图 8。

推理时技术——即在模型推理阶段投入额外算力的策略——正作为提升模型能力的有效手段获得越来越多的关注。OpenAI 的 o1 [30]、QwQ [39]、Sky-T1 [38] 等 LLM 正是利用这类技术，把额外的推理算力转化为在广泛任务上更好的表现。典型技术包括**生成集成（generation ensembling）、排序（ranking）与融合（fusion）**：集成中的多个模型被并行查询，它们的回答被排序，然后最优的若干回答被融合成一个更高质量的输出 [20, 42]。另一类推理时技术则基于对单个 LLM 的连续查询（即重复采样），并通过投票策略或单元测试来挑选最优生成结果 [6, 7, 22]。

近期工作已经在构建稳健的**推理时架构**（inference-time architectures，即由一个或多个 LLM 组成、并利用推理时技术的系统）方面取得了进展，代表性工作包括 Mixture-of-Agents（MoA）[42]、LLM-Blender [20]，以及单模型系统 ADAS [17] 与 AFlow [46]。然而，我们的实验表明，这些目前最强的基线在**算力利用率**与**任务泛化性**两方面都存在局限（见 4.2 节）。我们认为，设计高效且可泛化的推理时架构需要满足以下几点：

> **图 2 | Archon 框架总览。**左侧为搜索算法的四类输入：目标基准、推理调用预算、可用 LLM、可用推理时技术；中间是搜索算法用贝叶斯优化 [36] 构造并评估不同的 Archon 配置；右侧输出针对目标基准优化后的 Archon 架构（见 3.3 节）。

- **理解推理时技术的效用（Utilities）：** 推理时架构通常把额外的推理预算投向更多的模型采样调用 [7, 6]，这对数学与编码任务是有效的。而另一些任务（如指令跟随与推理）已被证明能从排序、融合等额外技术中获益 [42, 20]。这些方法都有价值，但关键是要识别出：对**不同任务类别**，哪些推理时技术最有效。

- **理解推理时技术之间的相互作用（Interactions）：** 已有研究大多单独分析某项技术（例如 Chen 等人 [7] 对生成采样的分析），而我们需要的是更综合地理解不同推理时技术在不同任务上的相互关系（例如：多用几个模型更好，还是对每个模型多采样几次更好？）。

- **高效、自动地搜索庞大的推理时架构设计空间：** 给定一组可用 LLM 与目标任务，目前并不存在一种「通吃」的推理时架构能在所有任务上最大化下游准确率（表 1）。推理时架构的搜索空间极其庞大，实践者必须做出若干关键配置决策：用哪些 LLM、每个模型采样多少次、如何组合与过滤候选生成结果。这些都催生了对**自动化、自适应架构搜索**方法的需求。

在我们的工作中，我们逐一回应了上述挑战。

**第一**，我们评估了一套覆盖「已有 + 我们提出」的推理时技术，在指令跟随、推理与编码三类任务上的效用。结合开源与闭源模型，我们考察了集成、融合、排序、批判（critiquing）、验证（verification）以及基于模型的单元测试生成/评估等一系列技术（3.1 节与 3.2 节）。我们发现：**没有任何单一技术能在所有任务上完全占优**，不同任务适合不同的方法。

**第二**，我们分析了推理时技术之间的相互作用，并分别探索了「增加新模型」与「增加新技术」带来的收益。我们发现：把生成集成与批判、验证、融合组合起来，其最终回答质量能够**超过单个（未融合）回答中的 oracle 最优候选**，这一点在指令跟随与推理任务上尤为明显（图 4、图 7、表 5）。我们还证明了：当我们**把推理时技术的层数堆叠起来**、并把多种方法组合在一起时，性能会持续提升，这使我们能够发现有效的新技术组合（3.2 节、4.2 节、附录 A.3）。组合多种策略能显著提升任务表现，但**确定具体该组合哪些**依然困难——它需要人工去试遍模型、推理时技术、架构设计、推理预算等等。

**第三**，基于上述对推理时技术的分析，我们提出 **Archon**：一个开源的模块化框架，用于自动设计由已有（或新增）推理时技术构成的 LLM 系统，让实践者能够针对自己关心的目标函数（准确率、延迟、成本）进行优化（3.1 节、3.3 节）。与那些在**单个** LM 上做提示工程与工具调用的系统不同 [21, 45, 17, 46]，我们的方法把**多个 LM 集成进单一架构**，并把提示选择规约为一组核心组件。Archon 框架利用自动架构搜索算法来最大化给定任务上的生成质量，其贝叶斯优化 [36, 28] 技术受到神经架构搜索（NAS）[48, 35] 的启发，用于快速遍历潜在的推理架构空间（3.3 节）。

我们在一组多样化的指令跟随、推理与编码基准上评估 Archon 架构（表 1）：MT-Bench、Arena-Hard-Auto、AlpacaEval 2.0、MixEval、MATH 与 CodeContests [47, 23, 24, 29, 15, 25]。我们最好的 Archon 架构同时超越了前沿模型（OpenAI o1、GPT-4o、Claude-3.5 Sonnet）与先前最强的推理时架构（ADAS、AFlow、MoA），把 SOTA 性能平均提升了 **15.1%**。此外，Archon 在达到 SOTA 性能的同时，比同类推理时架构少用了 **20.0% 的推理调用次数、15.1% 的输入 token、13.5% 的输出 token**（图 1、表 1、图 8）。即便**只使用开源 LLM**，Archon 架构平均也能超过 SOTA LLM **11.2%**。

总体而言，我们把 Archon 作为一个开源的推理时框架呈现出来，通过友好的用户接口，它可以被轻松扩展到新的推理时技术、模型与任务上。

## 2 相关工作

尽管推理时架构已经取得了不少进展，许多架构仍把重心放在「增加生成次数」上 [20, 7, 10]，这对推理任务是有效的 [6]。然而，对于指令跟随与推理这类任务，融合与排序等技术才是提升表现的有效手段 [42, 20]。先前研究只探索了配置的有限侧面，且往往聚焦于特定基准 [20, 42, 7, 22]。

高效开发推理时架构至关重要，因为最优配置会随基准、可用模型与推理算力上限而变化（4.2 节）。此外，诸如 DSPy [21] 这类 LM 编排框架，只能针对**单个 LM 优化单个提示**，它借助有监督数据让模型更擅长使用工具，但依然无法并行或串行地利用多种推理时技术。

上述方法都是**人工**选取现有技术的一个子集，而 Archon 则把可用的推理时技术**统一**起来，并通过搜索算法**自动化**架构构建，从而简化了针对每组任务进行模型与组件选择的过程（3.1 节与 3.3 节）。

> *（译者注）Archon 的直接对话对象是三类工作：(1) 多模型集成类，如 MoA、LLM-Blender；(2) 单模型 Agent 工作流搜索类，如 ADAS、AFlow；(3) 提示/流水线编译类，如 DSPy、TextGrad。Archon 的差异化在于把「组件类型」和「组件排布」都纳入了可搜索空间。*

## 3 Archon 中的推理时技术

随着推理时技术的大量涌现，Archon 引入了一个系统化的框架，用于理解并把这些方法统一为推理时架构。下面我们先详细说明每种推理时技术的结构、输入与输出（表 3），然后讨论如何把不同技术组合成推理时架构（3.2 节），最后探索自动构建推理时架构的方法（3.3 节）。

### 3.1 Archon 的 LLM 组件

在本节中，我们讨论 Archon 的 LLM 组件——即执行某种特定推理时技术的 LLM。我们受近期工作启发，测试了一系列不同的组件，既包含用于生成、排序与融合候选回答的方法 [42, 20]，也包含通过批判、验证与单元测试来提升候选回答质量的方法 [5, 47]。这些组件及其提示词汇总在表 3 与附录 A.2 中。我们还在指令跟随、推理与编码基准上对这些 Archon 组件做了大量消融实验，以更好地理解各自的效用以及在不同任务上的最优组合（附录 A.3）。

**生成器（Generator）**：接收指令提示并输出候选回答的 LLM。生成器可以被并行调用以执行生成集成（即并行调用多个 LLM）[42]，也可以被重复采样多次 [6]。模型数量、采样次数与生成温度都可以调节。

我们发现，**增加模型采样次数**能显著提升性能（图 6），对编码任务尤其明显（表 1）。模型集成也呈现类似规律：从更多模型中采样会带来持续的性能增长（假设模型是按该任务上的表现从好到坏依次加入的）（图 7）。

**融合器（Fuser）**：给定指令提示与一组候选回答，把这些回答合并成一个或多个质量更高的融合回答的 LLM。

在我们探索的**每一个**基准上，融合器模块都显著提升了性能（平均 **8.9%**）（图 6、图 7、图 4）。此外，在 Archon 框架中叠加**多层融合器**也观察到了类似的收益（图 4）。提升性能所需的融合层数因任务而异（图 12）：有些任务从增加层数中获益有限（MixEval 只提升 1–2 个点的准确率），而另一些任务在 3–4 层甚至更多融合层时收益显著（MT-Bench 与 AlpacaEval 2.0 的胜率提升 10–15 个点）。

**排序器（Ranker）**：给定指令提示与一组候选回答，按质量对候选生成结果排序并输出有序列表的 LLM。该排序随后被用于把候选集合过滤到指定的 Top-$K$。

从表 5、图 6、图 7 的结果来看，排序器对**指令跟随与推理任务**最为有效，因为它采用的是聚焦于**风格与提示遵循度**的两两比较（pair-wise comparison）。我们发现在 MT-Bench 与 Arena-Hard-Auto 上，排序器相对随机挑选把输出质量提升了 **10.8%**，并且与 oracle 选择只差 **2.7%**。

**批判器（Critic）**：给定指令提示与一组候选回答，为每个回答生成一份优点/缺点列表，该列表随后被用于提升最终回答的质量（3.2 节、图 4）。

批判器模块在图 4 与表 5 中我们探索的**每一个**任务上都有效。在我们「10 个 70B+ 模型生成器集成 + 融合器」的 Archon 配置下，加入批判器后各基准的平均性能提升了 **11.5 个百分点**。

**验证器（Verifier）**：验证某个候选回答是否针对给定指令提示给出了恰当推理的 LLM。它分两阶段进行：阶段 1 接收指令提示与候选回答，输出「该候选回答为何正确」的推理；阶段 2 接收指令提示、候选回答以及前一步产出的推理，然后输出推理以及一个结论（即二元的 [Correct] 正确 或 [Incorrect] 不正确）。只有通过验证的回答才会被传递到下一层 Archon。

验证器在表 5 中探索的**推理类基准**上最为有效，为 MixEval、MixEval-Hard 与 MATH 带来了 **8.4%** 的性能提升。当 70B+ 生成器集成在生成之后**只**接一个验证器模块时，该 Archon 配置在所有基准上平均落后于「集成 + 融合器」配置 **1.5%**，这说明验证器在与其他推理时技术组合使用时才是最有效的。

**单元测试生成器（Unit Test Generator）与单元测试评估器（Unit Test Evaluator）**：系统中互补的一对 LLM 组件。单元测试生成器接收指令提示，产出 5–10 条简洁的测试语句（4.2 节；示例见表 22），用于评估回答的准确性与相关性；评估器则接收指令提示、候选回答以及这些测试，按测试通过情况对候选回答排序。评估器会对每个候选给出判定理由并汇总各条测试的结论，为推理与编码任务上的每个回答打分，**只有通过了全部测试的回答**才会进入下一层 Archon。这一方法通过可配置的测试数量，把「基于测试的评估」从编码扩展到了各类任务。

单元测试生成器与评估器在**推理与编码任务**上最为有效，在需要更多验证步骤的基准上提升了 **7.4%**（表 5）。当 70B+ 生成器集成只与单元测试组合时，它对 Arena-Hard-Auto 与 MixEval 这类推理任务效果较差，比「集成 + 融合器」配置落后 **3.1%**。然而，当我们在 CodeContests 上增加生成采样并加入单元测试生成/评估后，观察到 Pass@1 性能提升了 **56%**（表 1），从 17.9 提升到 29.3 Pass@1。

### 3.2 组合 LLM 组件

**来自「扩展推理时技术」的性能增益：** 我们探索各个 Archon 组件的效用，并评估不同推理时技术的组合能否构建出「大于各部分之和」的 LM 系统。分析中我们考察了覆盖指令跟随、推理、数学与编码的七个数据集：MT-Bench [47]、AlpacaEval 2.0 [24]、Arena-Hard-Auto [23]、MixEval [29]、MixEval-Hard、MATH [15] 与 CodeContests [25]。我们同时在当前 SOTA 的开源与闭源 LM 上进行测试（表 34、表 35）。对每种推理时技术，我们的分析聚焦于：(1) 在不同基准上测试它；(2) 单独扩展它的使用规模；(3) 在随机固定另一种技术的同时扩展它；(4) 改变它在不同组件之间的位置。这些消融实验收录在 A.3 节，其中表 5 给出 Archon 组件组合，表 6 与表 9 给出组合中使用的模型类型。

从分析中我们发现若干跨架构组合的趋势（标记为 T）：

- **T1：重复模型采样与增加集成模型数量都会带来可观增益**，分别带来 **9.3%** 与 **18.5%** 的提升（图 11、图 7）。
- **T2：堆叠推理时技术的层数**能显著提升指令跟随、推理与编码任务的性能，例如「总是在最后加一层融合器」（图 4）。
- **T3：扩展所包含的推理时技术的多样性**同样能提升任务表现，其中「批判器 + 排序器放在融合器之前」的效果尤为突出（图 4、图 11）。
- **T4：在推理任务中，把验证器与单元测试生成器/评估器与融合器一起使用**，可以通过过滤掉有缺陷的回答来提升性能，在 MixEval 与 CodeContests 等任务上贡献了显著增益（表 5、A.9 节）。

**框架总览：**

基于我们对推理时组件的分析，我们提出 Archon——一个用于自动设计由已有（或新增）推理时技术构成的 LLM 系统的框架。

受神经网络结构启发 [16]，Archon 由**若干层 LLM 组件**构成（图 2、3.1 节）。每一层由一组**并行调用**的 LLM 组件构成。这些组件对「初始指令提示」与「上一层传来的候选回答」执行一次文本到文本的操作。进一步地，**与神经网络类似**：某些层执行的是对字符串列表的**变换**（如生成器与融合器），把一串字符串转换成另一串字符串（候选数量可以变化）；另一些组件则为 Archon 结构引入**非线性**，即对字符串列表执行**过滤**（如排序器与验证器）。最终，每一层的输入与输出**始终是一个字符串列表**——无论它是指令提示（即单个字符串）还是候选回答列表。如果在 Archon 结构的最后一层输出的是字符串列表，则返回列表中的第一个字符串。

**与经典神经网络不同**，LLM 组件之间以及层与层之间**没有可学习的权重**；因此 Archon 架构可以**开箱即用、无需任何微调**。此外，有**单一状态**从输入层被顺序变换到最终输出；这个状态就是「初始指令提示 + 当前的候选回答集合」（示例架构见图 3）。

> **图 3 | Archon 架构示例。**该架构以十个生成器模型开始（每个采样一次），随后依次是一个批判器模型、一个排序器模型、一层包含六个融合器模型的融合层、一个验证器模型，最后以一个融合器模型收尾。图中可以看到候选回答的数量随层数推进而逐级收窄——这正是 Archon 典型的「漏斗（funneling）」形态。

**构建规则：** 3.1 节中的 LLM 组件只能按特定顺序摆放（表 4）。虽然其他组合与排序在技术上也是可行的，但在我们对七个基准、两类模型（开源与闭源）进行组件消融研究之后，我们发现下述排序是最优的（附录 A.3）：

1. 任意一层中只允许出现**一种**类型的组件。
2. 生成器组件只能放在 Archon 的**第一层**；可以放置一个或多个生成器。
3. 批判器**必须**排在排序器或融合器之前。否则，生成的优点/缺点无法被纳入生成结果的排序或融合中。
4. 排序器、批判器、验证器以及单元测试生成器/评估器所在的层可以放在 Archon 中除第一层之外的任何位置。对这几类组件而言，**它们的层里只能有它们自己这一个模块**。
5. 融合器组件可以放在 Archon 中除第一层之外的任何位置。一层中可以放**多个**融合器。
6. 单元测试生成器与评估器必须放在**连续的两层**中，且单元测试生成器始终在前。

> **图 4 | 通过堆叠推理时技术层数提升性能。**在控制推理预算的前提下，对 8 个不同的 70B LLM 做生成集成 + 融合，通常比只对表现最好的那个模型做重复采样更有效。此外，加入批判层与融合层平均带来了 **18.8%** 的任务性能提升。然而，最优的推理时架构因任务而异（例如 MixEval 与 CodeContests 就不同，见 4.3 节），这启发我们去为 Archon 开发架构搜索技术（3.3 节）。

### 3.3 架构搜索算法

**搜索超参数：** 在本节中，我们探索如何通过 Archon 的架构搜索算法，为目标任务自动设计推理时架构。在 3.2 节所发现趋势的指导下，我们为搜索空间确立了**六个超参数维度**：

1. **集成用的 Top-$K$ 生成器**：初始生成器集成中使用的 Top-$K$ 个模型，取值范围 1 到 10（对应 T1）。Top-$K$ 模型是依据各模型在目标任务上的单独表现**贪心**选出的（表 35）。
2. **Top-$K$ 生成采样数**：从集成中每个生成器采集的样本数（所有模型相同），取值范围 1 到 5（对应 T1）。对 CodeContests，我们探索了高采样设定：$[1, 10, 100, 500, 1000]$。
3. **融合层数**：取值范围 1 到 4。**最后一个融合层始终只含一个融合器**（对应 T2）。
4. **Top-$K$ 融合器**：每个融合层使用的模型数量，从 2 到 10、步长为 2（对应 T2、T3）。
5. **批判器与排序器层**：我们在每个融合层之前加入批判层与排序层，因为我们发现它们在所考察的基准上都带来了额外收益（对应 T3）（3.2 节、图 4、图 7）。
6. **评估层**：可选地在最后一个融合层之前加入验证器、单元测试生成/评估器，或两者都不加（对应 T4）。

虽然还可以进一步扩张潜在 Archon 架构的搜索空间（例如为生成类 LLM 组件设置不同温度、为每个组件换不同提示、为 Archon 增加新的 LLM 组件等），但 3.2 节识别出的趋势已经把配置空间合理地约束到了最具影响力的那批超参数上。我们的搜索空间**总计包含 9,576 种配置**——这是把全部超参数组合起来、再剔除无效配置（例如初始生成数量超出融合器上下文窗口的配置）之后得到的。

**搜索方法：** Archon 的搜索方法接收四个输入：目标基准、推理调用预算、可用 LLM 集合，以及用于构建的推理时技术（图 2）。输出是一个优化后的 Archon 架构。我们使用每个目标数据集的 **20% 作为开发集**来引导架构搜索。我们探索了三种 Archon 架构搜索方案：

- **随机搜索（random search）**：在搜索空间中随机测试潜在架构；
- **贪心搜索（greedy search）**：从一个随机的初始架构出发，一次贪心地优化单个超参数；
- **贝叶斯优化（Bayesian Optimization）** [36]：基于高斯过程的全局超参数优化。

贝叶斯优化的输入是一个向量，指定生成器方面的配置选择（即模型数量与采样数）、融合器层数、每层融合器数量，以及最终的验证器/单元测试器（3.2 节）。贝叶斯优化首先采样**指定数量**的随机 Archon 架构来标定其代理模型（surrogate model）；这些被采样架构的任务表现用于指导后续更明智的架构建议。算法重复如下循环——评估每个被建议的架构，并用其表现来改进后续建议——直到发现最优 Archon 配置，或推理调用预算被耗尽。有关我们开源贝叶斯优化实现的更多细节，以及如何使用**延迟**等替代优化目标，请参见附录 A.4。

贝叶斯优化在 **96.0%** 的搜索中找到了最优架构，并且相比贪心搜索需要的架构评估次数减少 **88.5%**，相比随机搜索减少 **90.4%**（图 10）。贝叶斯优化的有效性随初始随机采样架构数量的增加而提高，直到大约 **230–240** 个样本为止；超过这个点之后，更多的测试预算应当被投放到配置搜索上（表 26）。在推理调用预算很有限时（$<20$ 次调用），贝叶斯优化效果较差，贪心搜索等传统方法可能表现相当（表 27）。

**添加搜索约束：** 为了在架构搜索期间施加算力约束，我们把任何会超出**推理调用次数、输入 token 数或输出 token 数**预算的 Archon 架构从搜索空间中排除。可以同时添加多个约束。例如，你可以过滤掉推理调用超过 20 次、或输入 token 超过 20,000 的架构。这使得我们的贝叶斯优化算法在架构搜索中**根本不会考虑**这些无效架构，从而让我们能够在算力匹配的条件下把 Archon 与 ADAS、AFlow 等替代推理时框架做对比（图 8、图 5）。

### 4.2 Archon 对比闭源 LLM 与其他推理时架构

**任务表现：** 我们首先在一组指令跟随、推理与编码任务上，把 Archon 架构与现有 SOTA 闭源 LLM 及推理时架构做对比。根据表 1 的结果，我们发现 Archon 架构在所考察的所有基准上都持续地匹配或超越现有方法。

- 使用开源模型的 Archon 架构，相对 SOTA 开源方法平均提升 **11.2%**；即使在表现最差的情况下，我们的开源 Archon 架构在 AlpacaEval 2.0 上仍比 SOTA 开源方法高 **3.1%**。
- 使用闭源模型的 Archon 架构在 MT-Bench、Arena-Hard-Auto、MixEval 与 MixEval-Hard 上取得了 SOTA，相对闭源 LM 平均提升 **15.1%**，相对开源推理时框架（MoA、ADAS、AFlow）平均提升 **8.4%**。
- 与 o1 和 o1-mini 相比，Archon 最好的针对性架构在 MT-Bench、AlpacaEval 2.0、Arena-Hard-Auto、MixEval、MixEval-Hard、MATH 与 CodeContests 上平均分别超出它们 **8.1%** 与 **9.7%**。
- 对于同时使用开源与闭源全部可用模型的方法，Archon 相对现有 SOTA 单次调用 LLM 平均提升 **10.9%**，相对现有推理时框架平均提升 **8.6%**。

**算力效率：** 与开源推理时框架（AFlow、ADAS、MoA）相比，Archon 的推理调用效率提升了 **20.0%**，同时在所有测试基准上性能更高（表 1）。我们还发现，我们最好的 Archon 架构相比最强的替代性开源推理时框架，少用了 **15.1% 的输入 token** 与 **13.5% 的输出 token**。当我们用不同的 token 预算运行 Archon 的架构搜索技术时（图 8），我们发现生成的 Archon 架构在**同等预算**下比替代基线性能高 **12.4%**。总体而言，通用型全源 Archon 架构在所有任务上的性能高出 **6.4%**，同时比最好的 LM 系统基线**节省 31% 的 token**（表 1）。此外，与通用型全源 Archon 架构相比，针对性全源 Archon 架构分别多用 **15.5%** 与 **18.6%** 的输入/输出 token，但准确率平均高出 **8.4%**。针对性架构算力开销更大，是因为它们可以把额外的 LM 操作进一步聚焦到某一组特定的任务约束上（附录 A.9）。

**被发现的架构：** 我们在附录 A.9 中给出针对性架构与通用架构（图 13）。表现最好的**全源通用型** Archon 架构，以「我们最好的 10 个生成器」组成的宽阔初始层开始，随后是四层连续的批判与融合，分别使用 Qwen2 72B 与 Claude 3.5 Sonnet。每一后续层的融合器数量递减（即 8、6、4），在生成结果被处理的过程中形成一种「漏斗效应」。最优的针对性架构则因任务而异：

### 4.3 按任务划分的 Archon

**指令跟随与推理：** 在 MT-Bench、AlpacaEval 2.0 与 Arena-Hard-Auto 上，开源 Archon 架构平均超出当前开源基线 **10.5%**，而闭源 Archon 平均超出当前闭源基线 **14.6%**（表 1）。借助 Archon，用于生成器的多个模型以及融合层的深度会为指令跟随任务带来性能提升，既丰富了回答的内容，也允许多轮迭代来逐步遵循指令（表 36）。

对于推理任务，虽然当我们只看 MixEval 与 MixEval-Hard 的聚合分数时，Archon 带来的提升较小，但当我们为 MixEval 与 MixEval-Hard 下的**每个子任务**单独构建推理时架构时，我们确实看到了有意义的性能提升（表 30、表 31）。当我们为每个子任务创建各自的 Archon 架构时，MixEval 与 MixEval-Hard 的准确率平均分别提升了 **3.7** 与 **8.9 个百分点**。这一发现说明：推理任务（例如数学、科学、逻辑）需要更**个性化**的推理时架构。

**编码：** 我们观察到集成、融合与排序技术对 CodeContests 的影响有限（图 4）。例如，当我们把表 28 中的通用全源架构应用到 CodeContests 问题时，Archon 带来的增益很小（见表 1）。一个原因是：与指令跟随/推理任务的分布不同，编码任务中往往存在一两个**表现远好于其他模型**的 LLM（表 35）。然而，当我们加入单元测试生成/评估并扩大采样数量时，Archon 在 CodeContests 上的性能显著提升（表 1），把 GPT-4o 的 Pass@1 提升了 **44.3%**（140 道题中从 40 道提升到 58 道）。对于基于模型的单元测试生成/评估，我们生成 5 条单元测试，并让 LM 依据这些生成的测试评估每个候选回答，从而对不同候选回答排序（细节见 A.2 节）。

### 4.4 讨论

**模型规模的影响：** Archon 框架在使用 **70B+ 参数**的 LLM 时效果最好。当我们用 7B 开源模型构建 Archon 架构时，相对最好的单个 7B LM 平均可以把任务性能提升 **7.5%**（表 38）。跨任务来看，7B 模型适合做排序，但在批判与融合上效果较差。

**延迟与成本：** 由于 Archon 架构需要为不同操作**依次**发起多次 LLM API 调用，它可能比单次 LLM API 调用多花 **5 倍**的时间与金钱（表 39、表 40）。需要注意的是，这些算力成本与延迟的增加换来的是更高质量的回答，并且在科学、编程与复杂 agentic 任务等许多应用领域中是值得的 [33, 27]。此外，LLM 厂商正在快速降低推理成本（表 39）。对于最看重速度的任务，未来工作应探索如何利用**蒸馏**策略 [37, 11] 把 Archon 架构的聚合知识压缩进一个更小的 LM。

**A.3.1 生成器**

*效用：* 我们发现增加模型采样次数能显著提升性能（图 6），对编码任务尤其明显（表 1）。在推理调用预算受限的场景下，**增加模型采样带来的边际收益最大**。模型集成呈现类似规律：从更多模型采样带来持续的性能增长（假设模型按该任务表现从好到坏排序）（图 7）。

**A.3.2 融合器**

*效用：* 在我们考察的每一个基准上，融合器模块都显著提升了性能（图 6、图 7、图 4）。对于「10 个 70B+ 模型、单次生成」的集成，融合器相对单次生成的最好模型平均把下游准确率提升了 **5.2 个点**（图 7）。当与排序器（取 Top-5 候选）配合时，融合器相对「单次采样的最好模型」与「oracle 最优候选回答」分别平均提升 **7.3 个点**与 **3.6 个点**（图 7）。总体而言，我们发现**融合器的效果随提供的候选回答增多而增强**，这说明在有融合器配合时，更多的候选生成可以继续提升推理时架构的性能。

在 MoA [42] 等先前工作中，多层融合器被发现能提升某些指令跟随任务（MT-Bench 与 AlpacaEval 2.0）的性能。在我们考察的所有基准上，Archon 框架中添加多层融合器也观察到了类似收益（图 4）。但根据图 12 的结果，提升性能所需的融合层数因任务而异：有些任务从增加层数中获益有限（MixEval 提升 1–2 个点准确率），有些则在 3–4 层或更多融合层时收益显著（MT-Bench 与 AlpacaEval 2.0 提升 2–5 个点的胜率）。我们把这一差异归因于**任务需求的不同**：聊天与指令跟随任务能从多层融合器带来的多轮修改中获益更多，从而使最终生成更具多样性（表 36）。

*组件相互作用：* 为更好地理解融合器如何与其他 LLM 组件配合，我们以「10 模型生成器集成（单次采样）+ 融合器」为底座，逐个加入批判器、排序器、验证器、单元测试生成器/评估器。在所有基准上，批判器提供的候选回答分析提升了融合器有效合并不同候选的能力，平均带来 **3.1 个百分点**的提升（图 4）。加入排序器后，Archon 架构在「集成 + 批判 + 融合」的基础上再平均提升 **4.8 个百分点**（图 4）。排序器对**风格导向**的任务（如 MT-Bench 与 AlpacaEval 2.0）最有效，因为这些样例的关注点主要是改善对给定提示的指令遵循。加入验证器后（图 4），指令跟随任务的性能提升有限（MT-Bench、AlpacaEval 2.0、Arena-Hard-Auto 平均 1.2 个百分点），但推理任务提升更大（MixEval 与 MixEval-Hard 平均 3.2 个百分点），因为它能在最终融合之前过滤掉无关或有缺陷的答案（图 4）。加入单元测试生成器/评估器对指令跟随与推理任务效果一般，在「集成 + 批判 + 融合」之上平均只带来 **1.5 个百分点**的提升（表 5）；但对**编码任务**，单元测试生成与评估显著提升了性能，在扩大模型采样时带来 **10.7 个百分点**的提升（相对提升 56%）（表 1）。

**A.3.3 批判器**

*效用：* 批判器模块在图 4 与表 5 中我们探索的每一个任务上都有效。在「10 个 70B+ 模型生成器集成 + 融合器」的 Archon 配置下，加入批判器在所考察基准上平均提升 **3.1 个百分点**。

*组件相互作用：* 虽然批判器对大多数 Archon 架构都有用，它产出的优点/缺点在与**融合器**配合时特别有价值，有助于指导单层生成融合，甚至在置于多个融合层之间时也有效（图 4 中跨基准平均 **3.2 个百分点**的提升）。批判器与**排序器**配合也有效，为比较候选回答提供了额外信息（图 6），平均带来 **5.9 个百分点**的提升（表 5）。

**A.3.4 排序器**

*效用：* 根据表 5、图 6 与图 7 的结果，我们发现排序器对**指令跟随任务**最有效，此时对答案的两两比较聚焦于风格与对提示的遵循度。为检验候选排序带来的候选选择改进，我们比较了三种方式：(1) 随机选择候选生成；(2) oracle 选择候选生成；(3) 由排序器选出的排名第一的候选。在 MT-Bench 与 Arena-Hard-Auto 上，排序器相对随机选择把生成输出质量提升了 **3.8%**，且与 oracle 选择的差距在 **2.7%** 以内（图 6）。

*组件相互作用：* 根据表 5 的基准结果，排序器与批判器配合良好——批判提供的优点/缺点有助于指导排序，对指令跟随任务尤其明显，平均提升 **5.9 个百分点**。排序器与融合器配合也有效——过滤后的候选列表帮助融合器产出更好的凝练回答，平均提升 **3.8 个百分点**（图 7）。当与验证器、单元测试生成器配合时，排序器效果中性——性能变化很小，正向或负向都在 1–2 个百分点内（表 5）。

总体而言，我们的发现证明了为指令跟随与推理任务**在融合器之前增加排序器**的价值。我们也发现，当排序器单独与生成器集成配合使用时，其性能平均落后于「10 次采样的最优单模型配置」**3.0 个百分点**（表 5）。此外，我们的发现显示了为数学、编码等更复杂推理任务构建更好排序器的重要性，这也是 [6] 提出的挑战。

### A.4 Archon 的贝叶斯优化

**A.4.1 搜索空间与目标函数**

Archon 的配置空间可以定义为 $\mathcal{X}=\{x_{g},x_{s},x_{f},x_{r},x_{c},x_{v}\}$，其中：

- $x_{g}\in[1,10]$：生成器模型数量；
- $x_{s}\in[1,5]$：每个生成器的采样数（对 CodeContests 扩展到 $[1,1000]$）；
- $x_{f}\in[1,4]$：融合层数，包含最后那层融合层；
- $x_{r}\in[2,10]$：每个融合层的模型数量，从 2 到 10、步长为 2；
- $x_{c}\in\{0,1\}$：是否在每个融合器之前使用批判层与排序层；
- $x_{v}\in\{0,1\}$：是否在最后的融合之前使用验证层。

搜索空间最初共包含 **18,750** 种配置（$10\cdot 5\cdot 5^{(4-1)}\cdot 3=18{,}750$），剔除无效配置后缩减到 **9,576** 种。被剔除的是：1) 初始生成数量超出融合器上下文窗口的配置（24 个候选）；2) 单一融合层中却包含多个融合器的配置（$x_{f}=1$ 而 $x_{r}\geq 2$）。

令 $f(x)$ 为评估 Archon 配置 $x\in\mathcal{X}$ 的目标函数，定义为：

$$f(x)=\text{Performance}(x)-\lambda\cdot\text{Cost}(x) \qquad (1)$$

其中 $\text{Performance}(x)$ 是在目标任务 20% 采样上的准确率，$\text{Cost}(x)$ 表示推理算力使用量。

**A.4.2 优化流程**

我们首先把 $\mathcal{H}$ 定义为「架构及其对应目标函数值」的历史，它在整个优化过程中被不断累积。我们使用**期望改进（Expected Improvement, EI）**作为采集函数（acquisition function），用来决定下一个要搜索的架构配置：

$$\text{EI}(x;\mathcal{H})=\mathbb{E}[\max(0,f(x)-f(x^{+}))] \qquad (2)$$

其中 $f(x^{+})$ 是到目前为止我们观测到的最优目标值，$(x^{+},f(x^{+}))\in\mathcal{H}$。我们使用**高斯过程（Gaussian Process）**模型作为近似 $f(x)$ 的代理模型。

贝叶斯优化流程如下：首先把观测历史初始化为 $\mathcal{H}=\emptyset$。对时间步 $t=1,\dots,T$（$T$ 为最大迭代次数参数），执行：

1. 用采集函数选择架构 $x_{t}=\text{argmax}_{x\in\mathcal{X}}\text{EI}(x;\mathcal{H})$；
2. 评估该架构 $x_{t}$，得到 $f(x_{t})$；
3. 用 $f(x_{t})$ 更新采集函数与代理模型：$H\leftarrow H\cup(x_{t},f(x_{t}))$。

该过程持续进行，直到满足以下任一条件：

- 达到最大迭代次数 $T$；
- 性能收敛：$|f(x_{n+1})-f(x_{n})|<\epsilon$；
- 预算耗尽：$\text{Cost}(x_{1},...,x_{n})>B$。

在 Archon 的实现中，我们用 **230–240 个随机配置**做初始化，这是通过实验测试找到的最优值。超过这个点之后的额外采样收益递减，更好的做法是把预算分配给配置搜索。我们的实现使用了基于高斯过程做全局优化的 Bayesian Optimization Python 包。

这一形式化让 Archon 能够高效探索配置空间：相比贪心搜索需要的评估次数减少 **88.5%**，相比随机搜索减少 **90.4%**，且贝叶斯优化在 **96.0%** 的迭代中找到了最优架构。传统的贪心搜索方法在推理预算很有限时（$<20$ 次调用）可能表现相当，但随着搜索空间与算力预算的增大，贝叶斯优化会变得越来越有效。

> **图 10 | 不同优化算法对 Archon 架构搜索的影响。**在 MT-Bench 与 Arena-Hard-Auto 上，我们对比了三种寻找最优推理时架构的方法：随机搜索、贪心搜索与贝叶斯优化。贝叶斯优化找到最优架构所需的迭代次数比贪心搜索少 88.5%、比随机搜索少 90.4%。

### A.5 贝叶斯优化对比其他方案

**搜索技术：** 在该超参数空间内，我们探索了三种用于自动化开发推理时架构的搜索算法：

1. **随机搜索**：随机选取一组 Archon 架构超参数组合。
2. **贪心搜索**：从一个基础 Archon 配置出发，逐个微调每个超参数并测试是否带来性能提升。若有提升则保留该改动，否则继续下一个超参数。
3. **贝叶斯优化**：通过构建概率代理模型并借助采集函数选择超参数，高效地为 Archon 挑选最有希望的超参数配置 [36, 28]（A.4 节）。

为了得到某基准上的模型排序，我们在搜索的第一阶段，用每个数据集基准的 20% 采样对**每个模型单独测试**。为了得到融合模型的排序，我们用同样的方法，测试每个模型在「由可用集合中随机选出的 10 个模型组成的集成」上的融合性能。从实验中我们发现，最好的生成器模型与融合模型在不同数据集之间差异很大，因此对**新数据集**执行这些排序是有益的（表 35）。搜索时，我们使用与评估生成、融合时相同的那 20% 采样，从而在获得有意义的开发信号的同时提升评估速度。

**搜索算法对比：** 在图 10 中，我们比较了每种搜索算法在所考察基准上的有效性。虽然随机搜索**保证**能找到最优 Archon 配置，但我们发现贝叶斯优化在「找到最优配置」与「最小化被测试配置数量」之间的权衡上最为有效。在图 10 测试的搜索迭代中，有 **96.0%** 的情况下贝叶斯优化在三种搜索算法中持有最优配置。我们的贝叶斯优化架构搜索使用 **230** 个初始采样（A.4 节）。贝叶斯优化找到最优架构配置所需的评估次数比贪心搜索少 **88.5%**、比随机搜索少 **90.4%**。

**贝叶斯优化分析：** 在表 26 中，我们探索了初始测试点数量、探索迭代次数与 Archon 推理调用预算如何影响贝叶斯优化的有效性。更多的初始测试点会持续提升搜索效果，直到 **230–240** 个样本为止；超过之后，测试预算最好被投入到配置搜索上。对于推理调用预算较低的 Archon（例如 $<20$ 次推理调用），由于搜索空间有限，贝叶斯优化的效果较差，表现得与贪心搜索或随机搜索相近（表 27）。因此，**贝叶斯优化在推理调用预算较大（例如 $>20$ 次调用）的开放式 Archon 架构搜索中更有效**，而传统的组件工程方式可能更适合调用预算受限的场景。

## 术语与背景速览（译者整理）

| 术语 | 含义 |
| --- | --- |
| Inference-time technique（推理时技术） | 在推理阶段投入额外算力来提升质量的手段，如重复采样、集成、排序、融合、批判、验证、单元测试 |
| Inference-time architecture（推理时架构） | 由一个或多个 LLM 组成、利用上述技术的系统，如 MoA、ADAS、AFlow、Archon |
| Generator（生成器） | 根据指令生成候选回答的 LLM，只能放在第一层 |
| Fuser（融合器） | 把多个候选回答合成为更优回答的 LLM，可多层堆叠 |
| Ranker（排序器） | 对候选回答排序并过滤到 Top-$K$ 的 LLM，相当于引入「非线性」 |
| Critic（批判器） | 为每个候选生成优点/缺点列表，供排序器与融合器使用 |
| Verifier（验证器） | 两阶段判定候选回答推理是否正确的 LLM，每候选 2 次调用 |
| Unit Test Generator / Evaluator | 由模型生成自然语言「单元测试」并据此给候选打分，把编码领域的测试思路推广到通用任务 |
| Funneling（漏斗效应） | 后续融合层融合器数量逐级递减（如 10→8→6→4→1），候选回答被逐级收窄 |
| Expected Improvement（EI） | 贝叶斯优化的采集函数，衡量「某配置相对当前最优值的期望改进量」 |
| Surrogate model（代理模型） | 用高斯过程近似昂贵的目标函数 $f(x)$，从而少评估、多推断 |
| NAS（神经架构搜索） | Archon 的方法论来源：把「搜索网络结构」换成「搜索 LLM 组件结构」 |
| Pareto frontier（帕累托前沿） | 准确率与 token 预算之间无法再同时改进的最优权衡曲线 |
| Pass@1 | 编码题只提交一次即通过全部测试的比例 |

**核心数字速记**

- **搜索空间**：原始 18,750 种配置 → 剔除无效后 **9,576** 种；六个超参数轴（生成器 Top-$K$、采样数、融合层数、每层融合器数、批判+排序层开关、评估层开关）
- **搜索效率**：贝叶斯优化在 **96.0%** 的搜索中找到最优架构；比贪心搜索少 **88.5%** 次评估、比随机搜索少 **90.4%** 次；初始随机采样 **230–240** 个配置最优；预算 $<20$ 次调用时优势消失
- **性能提升**：相对前沿模型（o1 / GPT-4o / Claude 3.5 Sonnet）平均 **+15.1%**；仅用开源模型平均 **+11.2%**；相对开源推理时框架（MoA / ADAS / AFlow）平均 **+8.4%**；超过 o1 与 o1-mini 分别 **+8.1%** / **+9.7%**
- **算力节省**：推理调用少 **20.0%**、输入 token 少 **15.1%**、输出 token 少 **13.5%**；通用型全源架构比最强 LM 系统基线省 **31%** token 且性能高 **6.4%**
- **组件增益（平均）**：融合器 **+8.9%**；批判器（在 10 模型集成+融合之上）**+11.5 个百分点**；排序器相对随机选择 **+10.8%**、距 oracle 仅差 **2.7%**；验证器在推理任务 **+8.4%**；单元测试在需验证的任务 **+7.4%**
- **扩展趋势**：重复采样 **+9.3%**、增加集成模型 **+18.5%**、叠加批判+融合层 **+18.8%**
- **编码特例**：CodeContests 上通用架构收益小，但加入单元测试 + 大采样后 Pass@1 从 **17.9 → 29.3**（相对 **+56%**）；相对 GPT-4o 的 Pass@1 提升 **44.3%**（140 题中 40 → 58）
- **泛化性**：通用型全源架构在未见过的 GPQA / MMLU / MMLU-Pro 上保留任务专用架构性能的 **91.7% / 93.9% / 94.2%**；ADAS 仅 **73.2% / 73.3% / 66.8%**，AFlow 仅 **70.8% / 73.8% / 67.0%**
- **代价**：延迟与成本约为单次调用的 **5 倍**；7B 模型上相对最优单模型仅 **+7.5%**（70B+ 上则显著更高）
- **关键消融结论**：「集成 + 批判 + 排序 + 融合」只用 **11** 次调用，即可超过调用 **24–25** 次的「集成 + 验证器」类配置——组合质量比堆调用次数更重要
