## 摘要

让大语言模型（LLM, Large Language Model）能够通过**使用更多的测试时计算（test-time computation）**来改进自己的输出，是迈向"通用自我改进智能体"的关键一步——这类智能体需要在开放式自然语言环境中运作。本文研究 LLM 推理时计算的**扩展规律（scaling）**，核心要回答这样一个问题：**如果允许一个 LLM 使用固定但数量可观的推理时算力，它在有挑战性的 prompt 上能提升多少性能？**

回答这个问题不仅关系到 LLM 性能的上限，也关系到 LLM 预训练的未来走向，以及我们应当如何在推理时算力与预训练算力之间做权衡。尽管它如此重要，此前却很少有研究去系统理解各种测试时推理方法的扩展行为；而且现有工作对其中不少策略给出的大多是**负面结果**。

本文分析两种扩展测试时计算的主要机制：

1. **针对稠密的、基于过程的验证器奖励模型（process-based verifier reward model）做搜索**；
2. **在给定 prompt 时，自适应地更新模型对回答的分布**（即改进 proposal distribution）。

我们发现，在这两种机制下，不同测试时算力扩展方法的有效性**关键地依赖于 prompt 的难度**。这一观察促使我们采用一种**"算力最优（compute-optimal）"的扩展策略**：针对每个 prompt 自适应地、最有效地分配测试时算力。使用这种算力最优策略，相比 best-of-N 基线，测试时算力扩展的**效率提升超过 4 倍**。此外，在 **FLOPs 匹配的评测**中我们发现：在那些较小的基座模型已经能取得"还算不错"成功率的问题上，测试时算力可以用来**击败一个参数量大 14 倍的模型**。

## 1 引言

人类在遇到难题时，倾向于**思考更久**，从而可靠地改善自己的决策 [18, 9, 17]。我们能否把类似的能力注入今天的大语言模型？更具体地说：给定一个有挑战性的输入 query，我们能否让语言模型在测试时**最有效地利用额外的计算量**，从而提升其回答的准确率？

从理论上讲，通过在测试时施加额外计算，一个 LLM 应该能够做到比它被训练出来的样子更好。此外，这种测试时的能力还有望在**智能体（agentic）任务与推理任务**上开辟新的路径 [34, 47, 28]。举个例子：如果预训练模型的大小可以和推理时的额外计算相互**兑换（trade off）**，那么就能把 LLM 部署到一些原本无法使用的场景里——比如用**端侧小模型**替代数据中心规模的 LLM。另外，利用额外推理时计算来自动生成改进后的模型输出，也为一条**通用的自我改进算法**提供了路径，使其能在减少人类监督的情况下运作。

> **图 1 | 主要结果总览。**
> **左图**：迭代式自我修正（即 revisions，修订）与搜索两种机制的算力最优扩展曲线。上半部分是比较我们的 PaLM 2-S* 修订模型在"修订"设定下、算力最优扩展策略与各基线的对比；下半部分是 PRM 搜索设定下的对比。可以看到在修订设定下，标准 best-of-N（即"并行"）与算力最优扩展之间的差距**逐渐拉大**，使得算力最优扩展能够用**少 4 倍的测试时算力**达到超越 best-of-N 的效果。类似地，在 PRM 搜索设定下，算力最优扩展在早期就展现出对 best-of-N 的显著优势，某些点上几乎可以用少 4 倍的算力追平 best-of-N。详见第 5、6 节。
> **右图**：测试时算力扩展与模型参数扩展的对比。我们把 PaLM 2-S* 的算力最优测试时扩展性能，与一个**参数量大约大 14 倍**、但不使用额外测试时算力（即贪心采样）的预训练模型做比较。设定是：两个模型都预计会看到 $X$ 个 token 的预训练量、$Y$ 个 token 的推理量；训练更大的模型，等价于把这两项的 FLOPs 需求都乘上一个系数。那么，如果我们用小模型施加额外的测试时算力，使得 FLOPs 需求与大模型匹配，它的准确率相比如何？可以看到：在修订设定（上）中，当 $Y \ll X$ 时，测试时算力往往比额外预训练更划算；但随着推理/预训练 token 之比增大，测试时算力**只在简单题上**仍然更划算，而在难题上，这些设定下预训练反而更优。PRM 搜索（下）也呈现类似趋势。详见第 7 节。

先前研究推理时计算的工作给出的结果是**好坏参半的（mixed）**。一方面，一些工作表明当前的 LLM 确实能利用测试时计算来改进输出 [4, 23, 8, 30, 48]；另一方面，另一些工作表明这些方法在数学推理等更复杂的任务上效果仍然**非常有限** [15, 37, 43]——尽管推理问题通常只要求对已有知识做推断，而不需要新知识。这些相互矛盾的发现，正说明我们需要对不同的测试时算力扩展方法做**系统性分析**。

我们关心的是理解"扩展测试时算力"到底有多大收益。可以说，扩展测试时计算最简单、也被研究得最充分的方法是 **best-of-N 采样**：从基座 LLM "并行地"采样 N 个输出，然后按一个学习得到的验证器（verifier）或奖励模型（reward model）打分，选出分数最高的那个 [7, 22]。但这**并不是**利用测试时算力改进 LLM 的唯一方式。通过以下两种改动，扩展测试时算力的能力可以被大幅提升（我们在本文中会展示这一点）：

- **修改采样回答所用的 proposal distribution**（例如让基座模型"串行地"修订它原本的回答 [28]）；
- **改变验证器的使用方式**（例如训练一个基于过程的稠密验证器 [22, 45]，并针对这个验证器做搜索）。

为了理解扩展测试时计算的收益，我们在有挑战性的 **MATH** [13] 基准上开展实验，所用模型为专门微调过的 **PaLM-2** [3] 系列——分别微调为：① 能够修订错误答案 [28]（即改进 proposal distribution，见第 6 节）；② 能够用**过程奖励模型（PRM, Process Reward Model）**验证答案中每一步的正确性 [22, 45]（见第 5 节）。

> *（译者注）原文脚注 1：由于即使是强大的闭源 LLM 也缺乏"修订"和"验证"能力 [15, 33]，要让基座模型在 MATH 上具备这些能力，必须做**能力特化的微调（capability-specific finetuning）**。但我们预期未来的 LLM 在这两件事上会更强——一方面因为规模更大，另一方面因为训练数据里会加入专门针对这两种能力的数据 [36, 5, 24]。因此，为了推进对"测试时算力扩展"的理解，我们必须使用针对这些能力微调过的模型。话虽如此，我们预期未来的模型会直接在预训练阶段就习得这些能力，从而不再需要这种能力特化的微调。*

在这两种路线下，我们都发现：**某种测试时算力策略是否有效，关键地取决于具体问题的性质以及所用的基座 LLM**。举例来说：

- 在**较简单的问题**上（基座 LLM 本来就已经能给出还不错的回答），让模型**迭代式地精修**它的初始答案——即预测一串 N 次修订（也就是修改 proposal distribution）——可能是比"并行采样 N 个独立回答"更有效的算力用法。
- 而在**较难的问题**上（往往需要搜索许多不同的、高层级的解题思路），独立并行地重新采样新回答，或者针对过程奖励模型部署**树搜索**，则可能是更有效的测试时计算用法。

这一发现说明：我们需要部署一种**自适应的"算力最优（compute-optimal）"策略**来扩展测试时算力——即**根据 prompt 来选择**具体使用测试时算力的方式，以便把额外计算用到刀刃上。我们还展示了：**从基座模型的视角定义的问题难度**（第 4 节）可以用来预测测试时计算的收益，从而让我们能在实际中针对给定 prompt 实例化这个"算力最优"策略。通过这种方式恰当地分配测试时算力，我们能大幅改善测试时算力的扩展效率——在**修订**和**搜索**两种设定下，都能**只用约 1/4 的计算量**就超过 best-of-N 基线的表现（第 5、6 节）。

接着，我们利用改进后的测试时算力扩展策略，去理解：**测试时计算能在多大程度上有效替代额外的预训练**。我们在"小模型 + 额外测试时算力"与"预训练一个大 14 倍的模型"之间做 FLOPs 匹配的比较。我们发现：在**简单题和中等题**上，甚至在**难题**上（取决于预训练与推理负载的具体条件），额外的测试时算力**往往优于扩展预训练**。这一发现表明：与其把注意力纯粹放在扩展预训练上，在某些场景下，更有效的做法是先用更少算力预训练一个更小的模型，然后用测试时算力来改进模型输出。

话虽如此，在**最具挑战性的问题**上，我们观察到扩展测试时算力的收益非常小；相反，我们发现在这些问题上，通过施加额外的预训练算力才能更有效地取得进展。这说明当前的测试时算力扩展方案**并不能与扩展预训练 1:1 地互换**。

总体而言，这表明：**即便采用相当朴素的方法，扩展测试时计算就已经能在某些情形下优于扩展预训练**；而随着测试时策略不断成熟，还能获得更多的改进。更长远地看，这暗示了一个未来——**在预训练上花更少的 FLOPs，在推理上花更多的 FLOPs**。

## 2 一个统一的视角：提议者（Proposer）与验证者（Verifier）

我们首先把使用测试时计算的各种方法统一到一个框架下，然后分析其中若干有代表性的方法。

我们先把"使用额外测试时算力"理解为：**在给定 prompt 的条件下，在测试时自适应地修改模型的预测分布**。理想情况下，测试时计算应当把这个分布修改得比"直接从 LLM 朴素采样"能生成更好的输出。一般来说，有两个旋钮可以诱导 LLM 分布的改变：

1. **在输入层面（input level）**：给给定的 prompt 增补一组额外的 token，让 LLM 以它们为条件，从而得到修改后的分布；
2. **在输出层面（output level）**：从标准 LM 采样多个候选，然后对这些候选做"外科手术式"的改造（surgery）。

换句话说：我们要么直接修改 LLM 自身导出的 **proposal distribution（提议分布）**，使它优于"朴素地以 prompt 为条件"的结果；要么使用一些**事后（post-hoc）验证器或打分器**来对输出做改造。这个过程让人联想到从复杂目标分布中做 **MCMC（马尔可夫链蒙特卡洛）采样** [2]——只不过它是把一个简单的 proposal distribution 与一个 score function 组合起来。**直接修改 proposal distribution**（通过改变输入 token）与**使用验证器**，构成了我们研究中两个相互独立的轴。

### 修改 proposal distribution

改进 proposal distribution 的一种方式是：通过受 RL 启发的微调方法（如 STaR 或 $\text{ReST}^{\text{EM}}$ [50, 35]），针对给定的推理任务直接优化模型。注意，这些技术**不使用任何额外的输入 token**，而是专门微调模型以诱导出一个改进的 proposal distribution。

另一类技术，如 **self-critique（自我批判）** [4, 23, 8, 30]，则让模型**在测试时**自己改进自己的 proposal distribution——通过指示它迭代地批判并修订自己的输出。由于直接 prompt 现成的模型并不足以在测试时产生有效的修订，我们专门**微调模型**，使其能在复杂推理场景中迭代地修订自己的答案。为此，我们采用了 Qu 等人 [28] 的方法：在 **on-policy 数据**上做微调，并用 best-of-N 引导的改进来构造目标回答。

### 优化验证器

在我们的"proposal distribution + verifier"抽象中，验证器被用来**聚合或从 proposal distribution 中挑出最好的答案**。使用验证器最经典的方式是 **best-of-N 采样**：采样 N 个完整解，然后按验证器选出最好的那个 [7]。

不过，这个方法还能进一步改进：训练一个**基于过程的验证器（process-based verifier）**，即**过程奖励模型（PRM）**——它对解中**每一个中间步骤**的正确性给出预测，而不仅仅是对最终答案打分。然后我们可以利用这些**逐步的预测**在解空间上执行**树搜索**，从而提供一种相比朴素 best-of-N 可能**更高效也更有效**的、针对验证器的搜索方式 [48, 10, 6]。

## 3 如何最优地扩展测试时计算

有了上述对各种方法的统一之后，我们现在想知道：如何最有效地利用测试时计算，来提升 LM 在给定 prompt 上的性能。具体地，我们要回答：

> **问题设定**
> 给定一个 prompt，以及一个用于求解该问题的测试时算力预算。在上面的抽象框架下，有多种不同的方式可以使用测试时计算。这些方法中的每一种，其有效性都可能因具体问题而异。那么：
> ① 我们如何针对给定 prompt 确定最有效的测试时算力使用方式？
> ② 这样做与"直接使用一个大得多的预训练模型"相比，效果如何？

当我们在"精修 proposal distribution"或"针对验证器搜索"时，有若干不同的**超参数**可以调整，以决定测试时算力预算该如何分配。举例来说：当我们使用一个"为修订而微调过的模型"作为 proposal distribution、并用一个 ORM 作为验证器时，我们既可以

- 把全部测试时算力预算用于从模型中**并行地**生成 N 个独立样本，然后施加 best-of-N；
- 也可以用修订模型**串行地**采样 N 次修订，然后用 ORM 选出序列中最好的答案；
- 还可以在这两个极端之间取得某种平衡。

直觉上，我们会预期**"更简单"的问题**能从"修订"中获益更多——因为模型的初始样本更有可能"路子是对的"，只是需要进一步的精修；而**有挑战性的问题**可能需要更多地去探索不同的高层解题策略，因此在这种情形下，多次独立并行采样可能更可取。

在验证器这一侧，我们还可以在不同的**搜索算法**之间做选择（例如 beam search 束搜索、lookahead search 前瞻搜索、best-of-N），每种算法依据"当前验证器与 proposal distribution 的质量"，会展现出不同的性质。相比简单得多的 best-of-N 或 majority（多数投票）基线，更复杂的搜索过程可能在更难的问题上更有用。

### 3.1 测试时算力最优的扩展策略

总的来说，我们希望为给定问题**选择测试时算力预算的最优分配方案**。为此，对于任何一种使用测试时算力的方法（本文是"修订"与"针对验证器搜索"，其他工作中还有各种别的方法），我们把**"测试时算力最优的扩展策略（test-time compute-optimal scaling strategy）"**定义为：在测试时、针对给定 prompt，选择与该测试时策略对应的超参数、以获得最大性能收益的策略。

形式化地，定义 $\operatorname{Target}(\theta, N, q)$ 为：模型在给定 prompt $q$、使用测试时计算超参数 $\theta$、算力预算 $N$ 时，所导出的自然语言输出 token 上的分布。我们希望选择能使该目标分布在给定问题上准确率最大的超参数 $\theta$。形式化表达为：

$$\theta^{*}_{q,a^{*}(q)}(N) = \operatorname{argmax}_{\theta}\left(\mathbb{E}_{y \sim \operatorname{Target}(\theta, N, q)}\left[\mathbbm{1}_{y = y^{*}(q)}\right]\right) \tag{1}$$

其中 $y^{*}(q)$ 表示 $q$ 的真实正确回答，$\theta^{*}_{q,y^{*}(q)}(N)$ 表示问题 $q$ 在算力预算 $N$ 下的测试时算力最优扩展策略。

### 3.2 为算力最优扩展估计问题难度

为了有效地分析第 2 节中讨论的各种机制（如 proposal distribution 与验证器）的测试时扩展性质，我们将给出对最优策略 $\theta^{*}_{q,y^{*}(q)}(N)$ 的一种**近似**，把它表示为"给定 prompt 的某个统计量"的函数——这个统计量估计了该 prompt 的**难度**。也就是说，算力最优策略被定义为"该 prompt 难度"的函数。尽管它只是公式 (1) 所示问题的一个近似解，我们发现它仍然能带来显著的性能提升——相对于那种"以临时起意（ad-hoc）或者均匀采样的方式分配推理时算力"的基线策略。

我们对问题难度的估计，是把每个问题分配到**五个难度等级**之一。然后我们可以在验证集上，针对给定的测试时算力预算，用这个离散的难度分类来估计 $\theta^{*}_{q,y^{*}(q)}(N)$，再把这些算力最优策略应用到测试集上。具体地，我们**对每个难度桶（bin）独立地选出表现最好的测试时算力策略**。这样一来，在设计算力最优策略时，**问题难度就充当了问题的一个充分统计量（sufficient statistic）**。

**定义问题的难度。** 沿用 Lightman 等人 [22] 的做法，我们把问题难度定义为**给定基座 LLM 的函数**。具体地：我们先用 2048 个样本估计模型在每个测试题上的 **pass@1 率**，然后把它分箱到**五个分位数（quantile）**中，每一箱对应一个递增的难度等级。我们发现，相比 MATH 数据集中人工标注的难度分箱，这种"**模型特定的难度分箱**"更能预测"使用测试时算力是否有效"。

话虽如此，我们也要指出：上面这种评估问题难度的方式，假设了我们能"神谕式（oracle）"地访问一个真实正确性判定函数——而在实际部署中，我们当然拿不到这个东西，我们只有测试 prompt，而并不知道答案。为了让算力最优扩展策略在实践中可行，它必须**先评估难度，再采用正确的扩展策略**去求解问题。

因此，我们用一个**模型预测的难度概念**来近似问题的难度：它执行**同样的分箱流程**，只是分箱所依据的统计量换成"同一个问题上 2048 个样本的**学习得到的验证器所给出的最终答案平均分数**"（而**不是**真实答案正确性判定）。我们把这种设定称为 **model-predicted difficulty（模型预测难度）**，而把依赖真实正确性的设定称为 **oracle difficulty（神谕难度）**。

虽然模型预测难度消除了"必须知道真实标签"的需求，但用这种方式估计难度仍然会在推理时产生额外的计算开销。不过，这个**一次性的推理开销可以被吸收进"实际运行推理时策略"的成本之中**（例如，当使用验证器时，我们可以把同一份推理计算也用于运行搜索）。更一般地说，这类似于强化学习中的**探索—利用权衡（exploration-exploitation tradeoff）**：在实际部署条件下，我们必须在"花在评估难度上的算力"与"采用最算力最优的方法的算力"之间做平衡。这是未来工作的一个关键方向（见第 8 节）；我们的实验**没有**计入这部分成本，主要是为了简洁——因为我们的目标是首次展示"有效分配测试时算力"究竟能做到什么程度。

为了避免"用同一个测试集既计算难度分箱、又选择算力最优策略"所带来的混淆因素，我们在测试集的每个难度桶上采用**二折交叉验证（two-fold cross validation）**：根据在其中一个折上的表现选择最佳策略，然后在另一个折上用该策略测量性能，反之亦然；最后对两个测试折的结果取平均。

## 4 实验设置

我们首先概述用于开展本分析的实验设置——包含多种验证器设计选择与 proposal distribution；随后各节给出分析结果。

- **数据集（Datasets）**。我们预期：当模型已经具备回答问题所需的全部基础"知识"，而主要挑战在于从这些知识中做（复杂的）**推断**时，测试时算力最有价值。为此，我们聚焦于 **MATH** [13] 基准——它包含高中竞赛水平的数学题，难度跨度较大。在所有实验中，我们使用 Lightman 等人 [22] 所用的数据集划分：12k 训练题 + 500 测试题。

- **模型（Models）**。我们使用 **PaLM 2-S\*** [3]（Codey）基座模型开展分析。我们认为该模型能代表当代许多 LLM 的能力水平，因此我们的发现很可能可以迁移到类似模型上。最重要的一点是：该模型在 MATH 上取得了**不可忽略但远未饱和**的成绩，因此我们预期它可以作为一个很好的试验台。

## 5 通过验证器扩展测试时算力

本节分析：如何通过**尽可能有效地优化验证器**来扩展测试时算力。为此，我们研究用过程验证器（PRM）执行测试时搜索的不同方法，并分析这些不同方法的测试时算力扩展性质。

### 5.1 训练适合搜索的验证器

**PRM 训练。** 最初的 PRM 训练 [42, 22] 使用的是众包人工标注。虽然 Lightman 等人 [22] 开源了他们的 PRM 训练数据（即 PRM800k 数据集），但我们发现这份数据**对我们基本无效**：我们发现，即使是 best-of-N 采样这样朴素的方法，也很容易**利用（exploit）**在它上面训练出来的 PRM。我们猜测，这很可能是因为该数据集中的样本由 GPT-4 生成，与我们的 PaLM 2 模型之间存在**分布偏移（distribution shift）**。

我们没有走"为 PaLM 2 模型收集众包 PRM 标注"这条昂贵的路，而是采用了 Wang 等人 [45] 的方法：**不使用人工标签**来监督 PRM——通过对解中每一步运行**蒙特卡洛 rollout**，得到对"逐步正确性"的估计。因此，我们 PRM 的逐步预测对应于"基座模型采样策略下的 **reward-to-go（未来回报）价值估计**"——与近期工作 [45, 31] 类似。我们也与一个 ORM 基线做了比较（附录 F），发现我们的 PRM 一致地优于 ORM。因此，本节中所有的搜索实验都使用 PRM 模型。PRM 训练的更多细节见附录 D。

**答案聚合（Answer aggregation）。** 在测试时，基于过程的验证器可以对"从基座模型采样得到的一组解"中的**每一步**打分。为了用 PRM 选出 best-of-N 的答案，我们需要一个函数，能把"每个答案的所有逐步分数"聚合起来，从而判定哪个候选是最佳答案。为此，我们分两步：先对每个答案的逐步分数做聚合，得到整个答案的最终分数（**逐步聚合，step-wise aggregation**）；再在答案之间做聚合，确定最佳答案（**答案间聚合，inter-answer aggregation**）。具体地：

- **逐步聚合**。我们**不是**像 [45, 22] 那样用乘积或最小值来聚合逐步分数，而是直接用 **PRM 在最后一步的预测**作为完整答案的分数。在我们研究过的所有聚合方法中，这个做法表现最好（见附录 E）。

- **答案间聚合**。我们沿用 Li 等人 [21] 的做法，使用 **"best-of-N weighted"（加权 best-of-N）** 选择，而不是标准 best-of-N。加权 best-of-N 会把验证器给出的正确性分数在**所有最终答案相同的解上做边际化（marginalize）**，然后选出**总和最大**的那个最终答案。

> *（译者注）这是本文一个很实用的技巧：标准 best-of-N 只看"哪个解得分最高"，而加权 best-of-N 是"把所有指向同一最终答案的解的得分加起来，再比总票数"。这样能显著降低验证器噪声带来的影响。*

### 5.2 针对 PRM 的搜索方法

> **图 2 | 不同 PRM 搜索方法的对比。**
> **左**：**Best-of-N** 采样 N 个完整答案，然后按 PRM 的最终分数选出最佳答案。
> **中**：**Beam search（束搜索）** 在每一步采样 N 个候选，并按 PRM 选出 top M 个继续搜索。
> **右**：**Lookahead search（前瞻搜索）** 把束搜索中的每一步都扩展为使用 k 步前瞻，用以评估哪些步骤该保留、该从哪里继续搜索。因此前瞻搜索需要更多算力。

我们在测试时通过搜索方法来优化 PRM。我们研究三种搜索方法，它们都从**经 few-shot prompt 的基座 LLM** 中采样输出（见附录 G）。示意如图 2。

**Best-of-N weighted。** 从基座 LLM 中独立采样 N 个答案，然后根据 PRM 的最终答案判断选出最佳答案。

**Beam search（束搜索）。** 束搜索通过在其**逐步预测**上搜索来优化 PRM。我们的实现类似于 BFS-V [48, 10]。具体地，我们设定固定的束数量 $N$ 与束宽 $M$，然后执行以下步骤：

1. 为解的第一步采样 $N$ 个初始预测；
2. 按 PRM 预测的"逐步 reward-to-go 估计"给生成的步骤打分（由于该设定下奖励是稀疏的，这也对应于从该前缀出发的总回报）；
3. 只筛选出得分最高的 $N/M$ 个步骤；
4. 然后从每个候选出发，为下一步采样 $M$ 个候选，于是又得到总共 $N/M \times M$ 个候选前缀。接着重复步骤 2–4。

我们一直运行该算法，直到解结束，或者达到束扩展的最大轮数（我们设为 40）。搜索结束时我们得到 N 个最终答案候选，对它们施加上面描述的 **best-of-N weighted** 选择，得出最终答案预测。

**Lookahead search（前瞻搜索）。** 前瞻搜索修改了束搜索评估各个步骤的方式：它使用**前瞻 rollout** 来提高搜索过程中每一步 PRM 价值估计的准确度。具体地，在束搜索的每一步，它**不是**用当前步的 PRM 分数来挑选 top 候选，而是执行一次**模拟（simulation）**：向前 rollout 最多 $k$ 步（如果提前到达解的结尾就停止）。为了减小模拟 rollout 的方差，我们使用**温度 0** 执行 rollout。然后，用这次 rollout 结束时 PRM 的预测来给束搜索中的当前步打分。

换句话说，我们可以把**束搜索看作 $k=0$ 时前瞻搜索的一个特例**。给定一个准确的 PRM，增大 $k$ 应当能提高逐步价值估计的准确度，代价是额外的算力。还要注意：这个版本的前瞻搜索是 **MCTS [38] 的一个特例**——它移除了 MCTS 中那些为促进探索而设计的随机元素，因为 PRM 已经训练好并被冻结了。这些随机元素主要对**学习价值函数**有用（而我们已经用 PRM 学到了它），但在测试时——我们想的是**利用（exploit）而非探索（explore）**——就没什么用了。因此，前瞻搜索在很大程度上代表了**MCTS 类方法在测试时会被如何应用**。

> **图 3 | 左**：针对 PRM 验证器执行搜索的不同方法对比。可以看到，在**低生成预算**下束搜索表现最好，但随着预算进一步扩大，这些改进大幅衰减，甚至**掉到 best-of-N 基线之下**。前瞻搜索在相同生成预算下**普遍不如**其他方法。
> **右**：按难度分箱比较束搜索与 best-of-N。每个难度桶中的**四根柱**对应递增的测试时算力预算（4、16、64、256 次生成）。在**较简单的问题**（桶 1、2）上，束搜索在更高预算下显示出**过度优化（over-optimization）**的迹象，而 best-of-N 没有。在**中等难度问题**（桶 3、4）上，我们看到束搜索相对 best-of-N 展现出**一致的改进**。

### 5.3 分析结果：带验证器搜索的测试时扩展

现在我们给出各种搜索算法的比较结果，并给出一个**依赖 prompt 难度的、用于搜索方法的算力最优扩展策略**。

**比较搜索算法。** 我们首先对若干搜索设定做一次扫描（sweep）。除了标准 best-of-N 之外，我们扫描区分不同树搜索方法的两个主要参数：**束宽 $M$** 与**前瞻步数 $k$**。虽然我们无法穷尽地扫描每一种配置，但我们在最大预算 256 的限制下扫描了以下设定：

1. 束宽设为 $\sqrt{N}$ 的束搜索，其中 $N$ 是生成预算；
2. 束宽固定为 4 的束搜索；
3. 对上述束搜索设定 1) 与 2) 都施加 $k=3$ 的前瞻搜索；
4. 对束搜索设定 1) 施加 $k=1$ 的前瞻搜索。

为了公平地把各搜索方法作为"生成预算"的函数进行比较，我们建立了一套估算每种方法成本的协议：我们把**一次"生成（generation）"**定义为"从基座 LLM 采样一个答案"。对于束搜索与 best-of-N，生成预算分别对应于束的数量与 $N$。然而前瞻搜索使用了额外算力：在搜索的每一步，我们要额外向前采样 $k$ 步。因此我们把前瞻搜索的成本定义为 $N \times (k+1)$ 次采样。

**结果。** 如图 3（左）所示，在较小的生成预算下，束搜索**显著优于** best-of-N。然而，随着预算扩大，这些改进**大幅衰减**，束搜索常常**不如** best-of-N 基线。我们还看到，前瞻搜索在相同生成预算下**普遍不如**其他方法——很可能是由于模拟前瞻 rollout 引入了额外计算。

搜索出现收益递减，很可能源于**对 PRM 预测的过度利用（exploitation）**。例如，我们看到一些实例（如图 29）中，搜索导致模型在解的末尾生成**低信息量的重复步骤**。在另一些情形中，我们发现过度优化搜索会得到**只有 1–2 步的过短解**。这就解释了为什么**最强的搜索方法（即前瞻搜索）反而表现最差**。我们把搜索发现的若干这类样例放在附录 M 中。

**搜索在哪些问题上能带来改进？** 为了理解如何以算力最优的方式扩展搜索方法，我们现在做一次**难度分箱分析**。具体地，我们比较束搜索（$M=4$）与 best-of-N。在图 3（右）中我们看到：虽然在**总体上**、在高生成预算下束搜索与 best-of-N 表现相近，但按难度桶评估它们的有效性，会揭示出**非常不同的趋势**：

- 在**简单问题**（等级 1、2）上，两者中更强的优化器——束搜索——随着生成预算增加而**性能退化**，显示出"利用 PRM 信号"的迹象。
- 相反，在**较难问题**（等级 3、4）上，束搜索**一致地优于** best-of-N。
- 在**最难的问题**（等级 5）上，没有任何方法取得有意义的进展。

这些发现与直觉相符：我们可能预期，在简单问题上，验证器的正确性判断大体是对的，因此再通过束搜索施加进一步优化，只会**进一步放大验证器学到的那些虚假特征（spurious features）**，从而导致性能退化。而在较难的问题上，基座模型一开始就不太可能采样到正确答案，因此搜索可以起到"**引导模型更频繁地产出正确答案**"的作用。

> **图 4 | 带 PRM 搜索时，算力最优的测试时算力分配与基线的对比。** 通过依据问题难度来扩展测试时算力，我们发现几乎可以用**少至 4 倍的测试时算力**（例如 16 次生成 vs 64 次生成）就超过 PRM best-of-N。"**Compute-optimal oracle**"指使用由真实正确性信息导出的神谕难度桶；"**Compute-optimal predicted**"指使用 PRM 的预测来生成难度桶。可以观察到，两种难度桶对应的曲线**基本重合**。

**算力最优的搜索。** 鉴于上述结果，很明显：问题难度可以作为一个有用的统计量，用来预测"在给定算力预算下该使用哪种最优搜索策略"。此外，最优搜索策略的选择会随这个难度统计量**剧烈变化**。因此我们在图 4 中可视化了"**算力最优**"的扩展趋势——即每个难度等级上表现最好的搜索策略。

我们看到，在**低生成预算区间**，无论使用神谕难度还是预测难度，算力最优扩展几乎都能用**少至 4 倍的测试时算力**（如 16 vs 64 次生成）超过 best-of-N。而在**较高预算区间**，使用预测难度时这些收益有所衰减；但使用神谕难度桶时，我们仍能看到最优扩展测试时算力带来**持续的改进**。这一结果展示了"在搜索过程中自适应分配测试时算力"所能获得的性能增益。

> #### 验证器算力最优扩展的要点小结
>
> 我们发现：任何一种验证器搜索方法的有效性，**关键地取决于算力预算和当前问题本身**。具体地，**束搜索在较难的问题上、较低的算力预算下更有效**；而 **best-of-N 在较简单的问题上、较高的预算下更有效**。此外，通过针对"给定问题难度 + 给定测试时算力预算"选择最佳搜索设定，我们几乎可以用**少至 4 倍的测试时算力**超过 best-of-N。

## 6 精修 Proposal Distribution

到目前为止，我们研究的是"针对验证器做搜索"的测试时算力扩展性质。现在我们转向研究**修改 proposal distribution**（第 2 节）的扩展性质。具体地，我们让模型能够**迭代地修订**自己的答案，使模型能够在测试时动态地改进自己的分布。

简单地 prompt 现有 LLM 去纠正自己的错误，在推理问题上取得性能改进的效果**往往很差** [15]。因此，我们沿用 Qu 等人 [28] 给出的配方（recipe），针对我们的场景做了一些修改，并**微调语言模型使其能迭代地修订自己的答案**。我们首先描述：如何训练并使用那些"通过依次以自己先前的尝试为条件、来精修自身 proposal distribution"的模型；然后分析修订模型的推理时扩展性质。

> **图 5 | 并行采样（如 Best-of-N）对比串行修订。**
> **左**：并行采样并行独立地生成 N 个答案；串行修订则依次生成每一个，每一个都以先前的尝试为条件。
> **右**：在串行与并行两种情形下，我们都可以用验证器来选出 best-of-N 的答案（例如施加加权 best-of-N）。我们也可以**把一部分预算分配给并行、一部分分配给串行**，从而有效地实现两种采样策略的组合。在这种情形下，我们**先用验证器在每条串行链内部选出最佳答案，再跨链选出最佳答案**。

### 6.1 设置：训练与使用修订模型

我们微调修订模型的流程与 [28] 类似，但引入了一些**关键的差异**。为了微调，我们需要这样的轨迹（trajectory）：**由一串错误答案、后接一个正确答案**构成，然后我们可以在其上跑 SFT。理想情况下，我们希望正确答案与上下文中提供的那些错误答案**是相关的**——这样才能有效地教会模型"隐式地识别上下文示例中的错误，并通过**做修改（making edits）**来纠正这些错误"，而不是完全无视上下文示例、从头再试一次。

**生成修订数据。** Qu 等人 [28] 那种"on-policy 地获取多轮 rollout"的方法被证明是有效的，但由于运行多轮 rollout 的计算成本，在我们的基础设施上并不完全可行。因此，我们**以更高的温度并行采样 64 个回答，然后事后（post-hoc）从这些独立样本中构造多轮 rollout**。具体地，沿用 [1] 的配方，我们把每个正确答案与"来自该集合的一串错误答案"配对作为上下文，从而构造多轮微调数据。

我们在上下文中**最多包含四个错误答案**，其中上下文中解的具体数量是从 0 到 4 这几个类别上的**均匀分布**中随机采样的。我们使用**字符级编辑距离（character edit distance）**指标，优先挑选那些与最终正确答案**相关性更强**的错误答案（见附录 H）。注意，token 编辑距离并不是相关性的完美度量，但我们发现这个启发式方法**足以**把上下文中的错误答案与正确的目标答案关联起来，从而训练出一个有意义的修订模型——相比之下，随机地把错误回答与正确回答配对，得到的样本是不相关的。

**在推理时使用修订。** 给定一个微调好的修订模型，我们可以在测试时从模型中采样**一串修订**。虽然我们的修订模型在训练时上下文中最多只有四个先前的答案，但我们可以通过**把上下文截断到最近的四次修订回答**来采样更长的链。在图 6（左）中我们看到：随着我们从修订模型中采样更长的链，模型在每一步的 pass@1 **逐步提升**——这表明我们确实有效地教会了模型从"上下文中先前答案所犯的错误"中学习。

> **图 6 | 左**：我们的修订模型在每个修订步骤上的 pass@1。每经过一次修订步骤，pass@1 都会逐步提升，**甚至在超出它训练时的 4 个修订步之后仍在继续提升**。我们通过对测试集中每个问题取 4 条长度为 64 的修订轨迹、并对性能取平均，来估计每一步的 pass@1。
> **右**：从修订模型中串行采样 vs 并行采样。比较"从修订模型并行生成 N 个初始答案"与"用该模型串行生成 N 次修订"的性能。当**同时使用验证器和多数投票**来选答案时，我们看到：用修订模型串行生成答案**略优于**并行生成。

话虽如此，在推理时存在**分布偏移**：模型训练时看到的序列中上下文里只有错误答案，但在测试时，模型可能采样出**正确答案**并被包含进上下文。在这种情况下，它可能在下一个修订步骤里**顺手把正确答案改成了错误答案**。我们发现，确实如 Qu 等人 [28] 所报告的那样，用朴素方法时，我们的修订模型会把大约 **38% 的正确答案重新变回错误答案**。因此，我们采用了一种基于**串行多数投票（sequential majority voting）**或**基于验证器的选择**的机制，从模型做出的一串修订中选出最正确的答案（见图 5），以产出最佳答案。

**比较。** 为了检验"通过修订来修改 proposal distribution"的有效性，我们设置了一个对等的比较：串行采样 N 次修订 vs 并行采样 N 次尝试。我们在图 6（右）中看到，无论是**基于验证器**还是**基于多数投票**的选择机制，串行采样解都优于并行采样。

> **图 7 | 左**：改变分配给"串行修订 vs 并行样本"的生成预算比例。**每条线代表一个固定的生成预算**，横轴是该比例的变化。我们使用验证器来选择答案。可以看到：虽然增加串行修订往往优于更多并行算力，但在**更高的生成预算**下，存在一个**理想的比率**，在两个极端之间取得平衡。
> **右**：在生成预算为 128 时，跨难度桶改变串行/并行比率。使用基于验证器的选择，我们看到：**较简单的问题在完全串行的算力下取得最佳性能**；而在较难的问题上，存在一个理想的串行/并行测试时算力比率。

### 6.2 分析结果：带修订的测试时扩展

我们前面看到，**串行地提出答案优于并行地提出答案**。不过，我们可能预期串行采样与并行采样具有不同的性质：

- **并行采样**可能更像一个**全局搜索（global search）**过程——原则上，它可以覆盖解题的许多**完全不同的思路**，例如不同候选可能采用完全不同的高层方法。
- 而**串行采样**可能更像一个**局部精修（local refinement）**过程——它修订的是那些"路子已经大致正确"的回答。

由于这两者具有**互补的收益**，我们应当在这两个极端之间取得平衡：把一部分推理时预算分配给**并行采样**（例如 $\sqrt{N}$），其余分配给**串行修订**（例如 $\sqrt{N}$）。我们现在将展示：串行与并行采样之间存在一个**算力最优的比率**，并理解它们各自的优劣如何随"给定 prompt 的难度"而变化。

**在串行与并行测试时算力之间权衡。** 为了理解如何最优地分配串行与并行算力，我们对若干不同的比率做了一次扫描。我们在图 7（左）中看到：确实，在给定生成预算下，存在一个**理想的串行/并行比率**能达到最大准确率。我们在图 7（右）中还看到：这个理想比率会**随问题难度而变化**。特别地，**简单问题从串行修订中获益更多**；而**困难问题则最优地在串行与并行计算之间取得某种平衡**。

这一发现支持了如下假设：**串行修订（即改变 proposal distribution）**与**并行采样（即带验证器的搜索）**是扩展测试时算力的**两个互补的轴**，二者在不同 prompt 上各有优势。我们把模型生成的一些样例放在附录 L 中，更多结果见附录 B。

> **图 8 | 使用我们的修订模型时，算力最优的测试时算力分配与并行算力基线的对比。** 通过依据问题难度最优地扩展测试时算力，我们发现可以用**少至 4 倍的测试时算力**（例如 64 个样本 vs 256 个样本）超过 best-of-N。"**Compute-optimal oracle**"指使用由真实正确性信息导出的神谕难度桶；"**Compute-optimal predicted**"指使用 PRM 的预测来产生"模型预测难度"桶。

**算力最优的修订。** 鉴于串行与并行采样的有效性取决于问题难度，我们可以**针对每个难度桶选择理想的串行/并行算力比率**。在图 8 中，我们绘制了使用这种算力最优扩展策略的结果（分别使用神谕难度与预测难度）。在这两种情形下，我们都通过"经由修订改进 proposal distribution"**大幅改善了测试时算力的扩展**。特别是：我们看到在较高的生成预算下，并行采样似乎已经**进入平台期**，而算力最优扩展则展现出**持续的改进**。对于神谕难度桶与预测难度桶，我们都看到算力最优扩展能用**少至 4 倍的测试时算力**（例如 64 个样本 vs 256 个样本）超过 best-of-N。总体而言，这些结果展示了"**按 prompt 调整 proposal distribution**"在改善测试时算力扩展上的潜力。

> #### 通过修订精修 proposal distribution 的算力最优扩展要点
>
> 我们发现：在**串行（如修订）**与**并行（如标准 best-of-N）**测试时计算之间存在一个权衡，而串行/并行测试时算力的理想比率**关键地取决于算力预算和具体问题**。具体地，**较简单的问题从纯串行的测试时算力中获益**；而**较难的问题往往在某个理想的串行/并行算力比率下表现最好**。此外，通过针对"给定问题难度 + 给定测试时算力预算"最优地选择最佳设定，我们能用**少至 4 倍的测试时算力**超过并行 best-of-N 基线。

## 7 综合起来：预训练算力与测试时算力的兑换

到目前为止，我们看到：利用额外的测试时计算，使我们能够**表示比基座 LLM 自身所预测的那个分布更复杂的分布**，从而改善性能。现在我们提出：**这种"表示分布"上增强的灵活性意味着**，我们可以期待额外的测试时算力能够**弥补**"模型容量不够高"或"预训练时没有训练更多 FLOPs"的缺陷。本节研究这在多大程度上是可行的。我们提出如下问题：

> **问题：兑换预训练算力与测试时算力**
> 假设一个模型使用了 $X$ FLOPs 完成预训练。假设我们计划用这个模型运行 $Y$ FLOPs 的推理。如果我们希望通过将总 FLOPs 预算乘以一个因子 $M$（即预训练 + 推理合计 $M(X+Y)$ 总 FLOPs）来提升性能，那么我们应当把 FLOPs 花在**增加预训练算力**上，还是花在**额外的测试时算力**上？

增加预训练 FLOPs 会引入一个额外的设计决策：是把算力分配给"用更多数据训练"，还是"用更多参数训练" [14]。我们聚焦于**扩大模型参数量、固定训练数据量**的设定——这与开源 LLaMA 系列模型 [41] 所采用的做法一致。我们选择这个设定，是因为它代表了扩展预训练算力的一种**典型做法**；而把"数据与参数等比例同时扩展"的预训练算力最优扩展分析 [29] 留给未来工作。

**定义 FLOPs 之间的兑换率。** 现在我们描述如何定义预训练 FLOPs 与推理 FLOPs 之间的兑换率。为了确定预训练 FLOPs，我们使用常见的近似 $X = 6 N D_{\text{pretrain}}$ [14]；对于推理 FLOPs，我们使用 $Y = 2 N D_{\text{inference}}$ [29]。这里 $N$ 表示模型参数量，$D_{\text{pretrain}}$ 是预训练使用的 token 数，$D_{\text{inference}}$ 是推理时生成的总 token 数。

有了这些近似，我们可以看到：如果我们把模型参数乘以因子 $M$，那么预训练 FLOPs 和推理 FLOPs（因为用更大的模型做贪心解码的成本）都会乘以因子 $M$（合计 $M(X+Y)$ 总 FLOPs）。

> **图 9 | 在 FLOPs 匹配的评测中，预训练算力与测试时算力之间的权衡。** 每条线代表在**每个神谕难度桶**中，用我们的算力最优策略扩展测试时算力所得到的性能。左边是修订的结果，右边是搜索的结果。**星号**代表一个"参数量大约多 14 倍"的基座模型在贪心解码下的 pass@1 性能。横轴是测试时算力预算；我们把星号放在横轴上三个不同的位置，每个位置对应于"扩展参数量"与"扩展测试时算力"在三种不同推理算力负载下的 FLOPs 等价比较点（即 $R = \frac{D_{\text{inference}}}{D_{\text{pretrain}}}$）。
> **判读方式**：如果**星号在线条的下方**，说明"使用测试时算力比扩展模型参数更有效"；如果**星号在线条的上方**，说明"扩展参数量更有效"。可以看到：在**简单问题**上、或在**推理负载较低**的设定下（即 $R \ll 1$），测试时算力通常能胜过扩展模型参数。然而，在**较难的问题**上、或在**推理负载较高**的设定下（即 $R \gg 1$），预训练是提升性能的更有效方式。

为了**用小模型 + 测试时算力**来匹配"扩展模型参数量"所对应的 FLOPs，我们可以把小模型的推理算力乘以因子：

$$M + 3\left(\frac{D_{\text{pretrain}}}{D_{\text{inference}}}\right)(M - 1)$$

值得注意的是，我们能用来匹配大模型 FLOPs 的推理算力规模，取决于比值 $\frac{D_{\text{pretrain}}}{D_{\text{inference}}}$。我们把**这个比值的倒数**记作 $R$（即 $R = \frac{D_{\text{inference}}}{D_{\text{pretrain}}}$）。

根据具体的生产设定或用例，我们应当预期 $R$ 会有**非常不同的取值**：

- 特别地，在许多**大规模生产环境**中，我们可能预期推理 token 数**显著多于**预训练 token 数，此时 $R \gg 1$；
- 另一方面，在许多**当代的自我改进（self-improvement）设定**中（即利用测试时算力来改进模型），我们生成的推理 token 数很可能**显著少于**预训练 token 数，此时 $R \ll 1$。

因此，由于我们**能施加的测试时算力规模**取决于这个比值，我们预期在不同设定下会得出不同的结论。

在图 9 中，我们用上述"兑换测试时算力与预训练算力"的方法，把我们的算力最优扩展与"把模型参数扩大约 14 倍"做比较。我们对 3 个不同的 $R$ 值进行比较：0.16（$R \ll 1$）、0.79（$R \sim 1$）和 22（$R \gg 1$），每个比值对应一个推理预算。

> *（译者注）原文此处第三个数值直接写作 "22"（$R \gg 1$），应为作者笔误或排版问题（按"0.16 / 0.79 / 22"的序列看，可能意在表达一个远大于 1 的量级）。这里按原文直录，不做臆改。*

观察可知：如果我们预期**只会遇到非常困难的问题**（例如难度桶 4/5），**或者** $D_{\text{inference}}$ 较大（对应更大的 $R$ 值），那么把预算分配给**预训练**往往更有效（即星号位于线条上方）。反之，如果我们预期遇到的大多是**简单或中等难度的问题**（例如桶 1/2/3，有时也包括桶 4），或者**推理需求较低**（如自我改进流水线中的情况），那么**使用测试时算力更好**。

> #### 预训练算力与测试时算力兑换的要点小结
>
> 测试时算力与预训练算力**不是 1:1"可兑换"的**。在**简单题和中等题**上（即处于模型能力范围之内的问题），或者**推理需求较小**的设定下，测试时算力可以轻松**弥补**额外的预训练。然而，在**超出给定基座模型能力范围**的挑战性问题上，或者**推理需求较高**的设定下，预训练很可能是提升性能的更有效方式。

## 8 讨论与未来工作

在本工作中，我们对若干技术路线的有效性做了详尽分析——这些技术要么是"改进针对验证器的搜索"，要么是"精修 LLM 的 proposal distribution"，目的都是为了在数学推理上扩展测试时算力。总的来说，我们发现：**某种给定方法的有效性，与该问题"从基座 LLM 能力视角看"的难度高度相关**。这促使我们引入"测试时算力的**算力最优（compute-optimal）**扩展"这一概念——它规定了一种**自适应的、依赖 prompt 的策略**，用以在给定测试时算力预算下提升性能。通过应用这种算力最优扩展策略，我们发现可以把测试时算力扩展的**效率提升 2–4 倍**。

在 FLOPs 匹配的设定下比较"额外测试时算力带来的收益"与"额外预训练算力带来的收益"时，我们**首次**展示了：用看似简单的方法（即修订与搜索）来使用测试时计算，**在某些类型的 prompt 上已经能够很好地扩展**，并能提供超过"把这些 FLOPs 花在预训练上"的收益。

话虽如此，我们的研究也存在一些局限，未来工作可以着力解决：

**进一步改进测试时算力扩展。** 本工作聚焦于改进两个主要机制（验证器、以及经由修订的 proposal distribution）的测试时算力扩展。虽然我们在第 6 节中把验证器与修订结合了起来，但我们**没有**实验"PRM 树搜索技术与修订相结合"。我们也没有研究其他技术，如 critique-and-revise（批判后修订）[23]。未来工作应当研究：**如何通过组合这些方法**来进一步改善测试时算力扩展。此外，我们发现这些方案**在难题上普遍只能提供很小的收益**；未来工作应当致力于开发新的测试时算力使用方式，以绕过这一局限。

**快速评估问题难度。** 我们使用"问题难度"这一概念，作为近似算力最优测试时扩展策略的简单**充分统计量**。虽然这个方案是有效的，但**估计我们的难度概念本身就需要施加不可忽略的测试时算力**。未来工作应当考虑更高效的难度估计方式（例如通过预训练或微调模型来**直接预测**问题的难度），或者**在"评估难度"与"尝试解题"之间动态切换**。

**把测试时算力与训练时算力交织起来。** 本工作纯粹聚焦于测试时算力扩展，以及测试时算力能在多大程度上兑换额外的预训练。然而在未来，我们设想：**施加额外测试时算力所得到的输出，可以被蒸馏回基座 LLM**，从而形成一个在开放式自然语言上运作的**迭代式自我改进循环**。为此，未来工作应当扩展我们的发现，研究"如何把施加测试时算力得到的输出用于改进基座 LLM 本身"。

## 术语与背景速览（译者整理）

| 术语 | 含义 |
| --- | --- |
| **Test-time compute / inference-time compute** | 测试时（推理时）算力。指在模型训练完成后，推理阶段额外投入的计算量（多次采样、搜索、多轮修订等） |
| **Proposer / Verifier** | 提议者 / 验证者。本文的统一框架：proposer 生成候选解，verifier 对候选做评分或筛选；两者对应"改进 proposal distribution"和"改进搜索"两个正交的轴 |
| **Proposal distribution** | 提议分布。模型在给定上下文下产生候选解的分布；可通过微调（STaR/ReST-EM）或测试时修订来改进 |
| **PRM（Process Reward Model）** | 过程奖励模型。对解中**每一步**的正确性打分的验证器，区别于只对最终答案打分的 ORM |
| **ORM（Outcome Reward Model）** | 结果奖励模型。只对最终答案是否正确打分的验证器 |
| **Best-of-N / Best-of-N weighted** | 采样 N 个解选最优 / **加权版**：把所有"最终答案相同"的解的验证器分数加总，选总和最大的最终答案（更抗噪） |
| **Beam search（束搜索）** | 逐步骤搜索，每步保留 top $N/M$ 个前缀，每个前缀再扩展 $M$ 个候选 |
| **Lookahead search（前瞻搜索）** | 束搜索每步向前 rollout $k$ 步，用 rollout 终点的 PRM 分数给当前步打分；$k=0$ 时退化为束搜索；是去掉探索随机性的 MCTS 特例 |
| **Compute-optimal scaling（算力最优扩展）** | 本文核心概念：针对每个 prompt（以其难度为充分统计量）和给定算力预算，选择能使准确率最大的测试时策略超参数 $\theta$，即公式 (1) |
| **Oracle difficulty / Predicted difficulty** | 神谕难度：用真实标签算 pass@1 分箱；预测难度：用 PRM 打分均值做同样的分箱（不依赖真实标签，落地可行） |
| **Difficulty bin（难度桶）** | 把题目按基座模型 pass@1 率分到 5 个分位数桶，作为设计算力最优策略的充分统计量 |
| **Sequential vs Parallel** | 串行（多轮修订，局部精修）vs 并行（独立多次采样，全局搜索）。两者互补，存在按难度而变的最优比率 |
| **FLOPs-matched evaluation** | FLOPs 匹配评测：让"小模型 + 测试时算力"与"大模型"消耗相同总 FLOPs 再比性能 |
| **$R = D_{\text{inference}} / D_{\text{pretrain}}$** | 推理 token 数与预训练 token 数之比。$R \ll 1$（自我改进流水线）时测试时算力划算；$R \gg 1$（大规模生产）时预训练划算 |
| **Reward-to-go** | 从当前步骤出发到终止的未来累积回报；本文 PRM 用 MC rollout 估计的就是它（软标签） |
| **Distribution shift** | 分布偏移。本文两处关键：PRM800k（GPT-4 生成）→ PaLM 2 的偏移；PRM（基座输出）→ 修订模型输出的偏移 |
| **ReST-EM / STaR** | 用"采样 + 过滤出正确答案 + 再微调"的简化 RL 方法；本文附录 K 显示 ReST-EM 会损害修订能力（负面结果） |

**核心数字速记**

- **4×**：算力最优扩展相对 best-of-N 的算力效率提升（修订与搜索两条路线都成立；如 16 次生成 vs 64 次生成、64 样本 vs 256 样本）
- **2–4×**：第 8 节对全文给出的效率提升区间
- **14×**：FLOPs 匹配对比中，小模型 + 测试时算力可对比的更大预训练模型的参数量倍数
- **5**：难度桶数量（按基座模型 pass@1 率的五分位数）
- **2048**：估计每题 pass@1 率（oracle）或 PRM 平均分（predicted）所用的样本数
- **256**：搜索实验中最大的生成预算；**4 / 16 / 64 / 256** 是图 3 右图的四档预算
- **40**：束搜索的最大扩展轮数
- **38%**：朴素使用下，修订模型把正确答案改回错误答案的比例
- **16 / 16**：PRM 训练时每题的样本数、每步的 MC rollout 次数
- **64**：生成修订数据时每题的并行采样数；**0–4**：上下文中错误答案数量的均匀采样范围
- **lr 3e-5（PRM）/ 1e-5（修订模型）**，batch 128，AdamW betas (0.9, 0.95)：两组微调超参
- **$R$ 三档**：0.16（$\ll 1$）、0.79（$\sim 1$）、22（$\gg 1$）
- **FLOPs 近似**：$X = 6 N D_{\text{pretrain}}$（预训练）、$Y = 2 N D_{\text{inference}}$（推理）；匹配倍数 $M + 3\frac{D_{\text{pretrain}}}{D_{\text{inference}}}(M-1)$

**一句话结论**

> 测试时算力不是"越大越好"，而是"**按题分配才好**"：难度是决定策略的充分统计量；在模型能力范围内的题上，测试时算力比堆预训练参数更划算，但在超出模型能力的难题上，预训练仍然不可替代。
