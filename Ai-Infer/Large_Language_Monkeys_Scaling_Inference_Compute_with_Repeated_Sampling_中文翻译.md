## 摘要

用更多算力训练语言模型，能显著提升其能力。然而在推理阶段，我们往往只让模型对一个问题尝试一次。

本文把推理算力（inference compute）作为另一条扩展轴来探索，所用技术非常朴素：从模型中反复采样候选解。

在多个任务与多个模型上我们观察到：**覆盖率（coverage）**——被任意一个生成样本解决的问题所占比例——随着采样数量在**四个数量级**范围内持续提升。有意思的是，覆盖率与采样数之间的关系常常是**对数线性的（log-linear）**，可以用**指数化幂律（exponentiated power law）**建模，这暗示存在「推理时缩放律（inference-time scaling laws）」。

在代码和形式化证明这类答案可自动验证的领域，覆盖率的提升会直接转化为性能提升。把重复采样用于 SWE-bench Lite 时，DeepSeek-Coder-V2-Instruct 解决的问题比例从单样本的 15.9% 提升到 250 个样本的 56%，超过单样本 43% 的当前最优（SOTA）。

在没有自动验证器的领域，我们发现常用的「从样本集合中挑答案」的方法（多数投票和奖励模型）在样本数超过几百之后就会进入平台期，无法随样本预算继续扩展。

## 1 引言

过去几年，大语言模型（LLM）在代码、数学及其他推理任务上的能力提升显著 [47, 11, 2, 4]。持续驱动这些进步的是**训练算力的扩展**：更大的模型、更长的预训练、更大的数据集 [27, 37, 28]。

相比之下，对**推理阶段算力**的投入相对有限。更大的模型确实需要更多推理算力；思维链（chain-of-thought）[61] 之类的提示技术也能以更长的输出（因而更贵的计算）换取更好的答案质量。但在与 LLM 交互时，用户和开发者通常只让模型对一个问题尝试一次。

本文把**重复采样（repeated sampling）**（图 1）作为一种扩展推理算力的简单方法来提升推理性能。已有工作给出了不少鼓舞人心的例子，说明重复采样在数学、代码和谜题求解场景中有效 [60, 48, 23]。尤其是 AlphaCode [41]——竞赛编程的 SOTA 系统——发现每道题采样到一百万个解时性能仍在继续提升。我们的目标是**系统地刻画**这种收益在多种任务、模型和采样预算下的规律。

> **图 1｜本文采用的重复采样流程。**（1）以正温度从 LLM 中采样，为给定问题生成大量相互独立的候选解；（2）用领域相关的验证器（例如代码的单元测试）从生成的样本中选出最终答案。
>
> *图意解读*：这条流水线把「生成」和「选择」明确解耦。生成阶段只负责提高覆盖率（能不能撞出对的），选择阶段负责精度（能不能从一堆样本里挑出对的）。后文第 2 节讲扩展生成，第 4 节讲选择为什么是瓶颈。

重复采样的有效性由两个关键性质决定：

1. **覆盖率（Coverage）**：随着样本数增加，我们能用**任意一个**生成的样本解决的问题比例是多少？
2. **精度（Precision）**：我们有多大概率能从生成的样本集合中**识别出**正确的那一个？

两者都必不可少。若有无限样本，任何对每条序列都赋予非零概率的模型都能达到完美覆盖率。但只有能在**可行预算**内提升覆盖率，重复采样才有实用价值。同理，生成大量样本只有在能识别出其中正确样本时才有用。精度问题的难度因任务而异：有些场景下证明检查器（proof checker）和单元测试能自动验证每一个样本；另一些场景（如应用题）则需要其他验证手段。

先看覆盖率。我们发现每道题采样最多 10,000 次，可以显著提升数学与代码任务的覆盖率（第 2 节）。用 Gemma-2B [52] 求解 CodeContests [41] 编程题时，覆盖率提升超过 **300 倍**——从单样本的 0.02% 提升到 10,000 个样本的 7.1%。有意思的是，$\log(\text{coverage})$ 与样本数之间常常近似服从幂律（第 3 节）。对 Llama-3 [3] 和 Gemma 系列模型，这使得覆盖率在数个数量级范围内几乎**对数线性**增长。

在具备自动验证工具的场景，覆盖率的提升**直接**转化为任务性能的提升。把重复采样用于竞赛编程和 Lean 证明写作时，Llama-3-8B-Instruct 这类模型可以超过 GPT-4o [2] 这类强得多的模型的单样本性能。这种「放大弱模型」的能力同样延伸到难度更高的 SWE-bench Lite——真实 GitHub issue 数据集 [32]。该数据集当前的单样本 SOTA 由 GPT-4o 与 Claude 3.5 Sonnet 的组合取得，为 43% [1]。而 DeepSeek-Coder-V2-Instruct [20] 在只用单样本时仅解决 15.9% 的 issue。仅把样本数提到 250，我们就把解决比例提高到 **56%**，比 SOTA 高出 13 个百分点。

除了提升模型质量，重复采样还提供了**降低 LLM 推理成本的新机制**（第 2.3 节）。在固定总推理 FLOPs 的条件下，某些数据集（如 MATH）上「小模型 + 多采样」的覆盖率最高，而另一些（如 CodeContests）上「大模型 + 少采样」更优。我们还比较了 DeepSeek-Coder-V2-Instruct、GPT-4o 和 Claude 3.5 Sonnet 在解决 SWE-bench Lite issue 时的 API 价格。固定 agent 框架（Moatless Tools [67]）后，从更弱更便宜的 DeepSeek 上采样 5 次，解决的 issue 比 Claude 或 GPT 的单样本更多，同时总成本低 3 倍以上。

最后我们说明：**可扩展的验证是充分享受重复采样收益的必要条件**。样本数增加时，覆盖率之所以提升，是因为模型开始能给出它此前解不出的问题的正确解。但这些越来越稀有的正确生成，只有在验证器能够「大海捞针」、从以错误样本为主的集合中把它们找出来时才有价值。在数学应用题场景，我们发现两种常用验证方法（多数投票与奖励模型）并不具备这种能力。用 Llama-3-8B-Instruct 解 MATH [26] 时，覆盖率从 100 个样本的 82.9% 提升到 10,000 个样本的 98.44%；然而用多数投票或奖励模型选答案，同样样本范围内性能最多只从 40.50% 升到 41.41%。样本数越多，覆盖率（即拥有完美验证器时的性能）与这些方法实际性能之间的差距越大（图 7）。

总结起来，我们的主要观察是：

1. 通过重复采样扩展推理算力，能在多种任务和模型上带来覆盖率的巨大提升。这使得「用大量样本放大弱模型、超过强模型的单样本」成为可能，且有时更具成本效益。
2. 覆盖率与样本数的关系常常可以用指数化幂律建模，这暗示存在某种形式**推理时算力的缩放律**。
3. 在没有自动验证器的领域，常用验证方法在约 100 个样本之后即进入平台期，导致其实际性能与覆盖率上界之间的差距不断扩大。

## 2 扩展重复采样

我们聚焦于**通过/不通过（pass-fail）**类任务，即候选解可以被判定为对或错。这类任务的核心指标是**成功率**：我们能解决的问题比例。在重复采样下，模型在试图解决一个问题时可以生成大量候选解。因此成功率同时受两方面影响：能否为许多问题生成正确样本（覆盖率），以及能否识别出这些正确样本（精度）。

精度问题的难度取决于是否有可用的样本验证工具。在 Lean 中证明形式化命题时，证明检查器能快速判定候选解是否正确；类似地，单元测试可以验证代码任务的候选解。这些场景下精度被自动解决，提升覆盖率就直接等于提升成功率。相反，用于验证 GSM8K 和 MATH 数学应用题解答的工具很有限，需要额外的验证方法来从大量（往往相互冲突的）样本中决定唯一最终答案。

我们考察以下五个任务：

1. **GSM8K**：小学难度数学应用题数据集 [18]。我们在 GSM8K 测试集的 128 道随机子集上评测。
2. **MATH**：另一个数学应用题数据集，难度普遍高于 GSM8K [13]。同样在该测试集上取 128 道随机题评测。
3. **MiniF2F-MATH**：已被形式化到证明检查语言中的数学问题数据集 [65]。我们以 Lean4 为语言，在 130 道由 MATH 数据集形式化而来的测试题上评测。
4. **CodeContests**：竞赛编程问题数据集 [41]。每题有文字描述和一组输入输出测试用例（对模型隐藏），可用来验证候选解的正确性。我们要求模型用 Python3 写解。
5. **SWE-bench Lite**：真实世界 GitHub issue 数据集，每题包含一段问题描述和一个代码仓库快照 [32]。解题需要模型修改仓库中的文件（在我们使用的 Lite 子集中只需改动一个文件）。候选解可用仓库自带的单元测试套件自动检查。

其中 MiniF2F-MATH、CodeContests 和 SWE-bench Lite 具备自动验证器（分别是 Lean4 证明检查器、测试用例、单元测试套件）。我们先研究重复采样如何提升模型覆盖率。对具备自动验证器的任务，覆盖率提升直接对应成功率提升；在一般情况下，覆盖率给出成功率的上界。

在代码场景，我们的覆盖率定义等价于常用的 pass@k 指标 [15]，其中 $k$ 表示每题的样本数。在 CodeContests 和 SWE-bench Lite 上我们直接使用该指标。对 MiniF2F 指标类似，只是「通过」由 Lean4 证明检查器定义。对 GSM8K 和 MATH，覆盖率对应一个 oracle 验证器：只要有任何样本输出了正确的最终答案就算通过。为降低覆盖率估计的方差，我们采用 Chen 等人 [15] 的无偏估计公式。每个实验中，我们先为题目索引 $i$ 生成 $N$ 个样本，统计正确样本数 $C_i$，再对每个关心的 $k \le N$ 按下列公式计算 pass@k：

$$
\text{pass@}k = \frac{1}{\text{\# of problems}}\sum_{i=1}^{\text{\# of problems}}\left(1-\frac{\binom{N-C_i}{k}}{\binom{N}{k}}\right) \tag{1}
$$

我们采用 Chen 等人 [15] 建议的数值稳定实现。

数据与代码见 https://scalingintelligence.stanford.edu/pubs/large_language_monkeys/。

### 2.1 重复采样在多项任务上均有效

> **图 2｜在五个任务上，覆盖率（至少一个生成样本解决了的题目比例）随采样数增加而上升。** 值得注意的是，借助重复采样，我们把一个开源方法在 SWE-bench Lite 上的解决率从 15.9% 提升到了 56%。
>
> *图意解读*：横轴是每题样本数（对数刻度，1 → 10000），纵轴是覆盖率。图中五条曲线代表 GSM8K、MATH、MiniF2F-MATH、CodeContests 和 SWE-bench Lite；每张子图里还标注了 GPT-4o 单次尝试的水平线（以及 SWE-bench Lite 的单样本 SOTA 线）。曲线随样本数平滑上升、并逐个穿过这些基线，说明弱模型 + 多采样可以越级超过强模型单次尝试。

这里我们确认重复采样在多个任务、多个采样预算区间上都能提升覆盖率。我们在 CodeContests、MiniF2F、GSM8K、MATH 上评测 Llama-3-8B-Instruct 与 Llama-3-70B-Instruct，每题生成 10,000 个独立样本。对 SWE-bench Lite 我们使用 DeepSeek-Coder-V2-Instruct [20]，因为该任务所需的上下文长度超出 Llama-3 系列的限制。按解 SWE-bench issue 的惯例，我们给 LLM 配了一个软件框架，为模型提供浏览和编辑代码库的工具；本文使用开源的 Moatless Tools 库 [67]。需注意，解一个 SWE-bench issue 是 LLM 与 Moatless Tools 之间的多轮往复，该基准的一次「样本/尝试」指的是**一整条多轮轨迹**。为控制成本，我们把每题的尝试次数限制为 250 次，且所有尝试彼此独立。

结果见图 2。我们还标注了 GPT-4o 在各任务上的单次尝试性能，以及 SWE-bench Lite 的单次尝试 SOTA（CodeStory Aide [1]，使用 GPT-4o 与 Claude 3.5 Sonnet 的组合）。五个任务上，覆盖率都随采样预算增加而平滑上升。当所有 LLM 都只给一次尝试时，GPT-4o 在每个任务上都优于 Llama 和 DeepSeek 模型；但随着样本数增加，三个更弱的模型都超过了 GPT-4o 的单次尝试性能。就 SWE-bench Lite 而言，我们解决了 56% 的问题，超过单次尝试 SOTA 的 43%。

### 2.2 重复采样在不同模型规模与家族上均有效

> **图 3｜通过重复采样扩展推理时算力，在多种模型规模（70M–70B）、多个家族（Llama、Gemma、Pythia）以及不同后训练水平（Base 与 Instruct）上都能带来一致的覆盖率提升。**
>
> *图意解读*：每一簇柱/线代表同一模型在 CODE 与 MATH 两类任务上「1 样本 → 10,000 样本」的覆盖率变化。规模越小的模型，相对提升幅度越陡（典型是把几乎不可能完成的任务从接近 0 拉起来）；而 Pythia 系列在 CodeContests 上始终为 0，形成唯一的例外。

第 2.1 节的结果表明重复采样能提升覆盖率，但只覆盖了三个 8B 以上的近期指令微调模型。现在我们证明这一趋势在其他模型规模、家族和后训练水平上同样成立。扩展后的模型集合包括：

- **Llama 3**：Llama-3-8B、Llama-3-8B-Instruct、Llama-3-70B-Instruct。
- **Gemma**：Gemma-2B、Gemma-7B [52]。
- **Pythia**：Pythia-70M 到 Pythia-12B（共八个模型）[9]。

为控制推理成本，评测只限于 MATH 和 CodeContests 两个数据集，结果见图 3。几乎所有被测模型的覆盖率都上升，其中**小模型的提升往往最陡**。在 CodeContests 上，Gemma-2B 的覆盖率提升超过 300 倍，pass@1 为 0.02%，pass@10k 达到 7.1%。类似地，用 Pythia-160M 解 MATH 时，覆盖率从 pass@1 的 0.27% 提升到 pass@10k 的 57%。

唯一的例外是 Pythia 系列在 CodeContests 上——即使给到 10,000 个样本，所有 Pythia 模型的覆盖率仍为零。我们推测这是因为 Pythia 训练时使用的代码相关数据少于 Llama 和 Gemma。

### 2.3 重复采样有助于平衡性能与成本

2.1 与 2.2 节的一个启示是：重复采样让「放大弱模型并超过强模型单样本」成为可能。这里我们进一步说明，这种放大可以比直接使用更强更贵的模型**更省钱**，为实践者在联合优化性能与成本时提供了一个新的自由度。

先以 FLOPs 作为成本指标，考察 2.1 节的 Llama-3 结果。我们把图 2 重画为「覆盖率 vs. 总推理 FLOPs」（而非采样预算）。由于 Llama-3 是稠密 Transformer，绝大部分参数参与矩阵乘，我们用下式近似推理 FLOPs：

$$
\text{FLOPsPerToken}(\text{ContextLen}) \approx 2*\left(\text{NumParameters}+2*\text{NumLayers}*\text{TokenDim}*\text{ContextLen}\right)
$$

$$
\text{TotalInferenceFLOPs} \approx \left(\sum_{t=1}^{\text{NumPromptTokens}}\text{FLOPsPerToken}(t)\right) + \left(\sum_{t=1}^{\text{NumDecodeTokens}}\text{FLOPsPerToken}(t+\text{NumPromptTokens})*\text{NumCompletions}\right)
$$

> *（译者注）* 第一项是 prefill 阶段（对整个 prompt 做前向）的开销，第二项是 decode 阶段的开销乘以并行生成的完成数——这正是「重复采样」在算力账本上的体现：prompt 只算一次，decode 算 $N$ 遍。也正因如此，重复采样的边际成本远低于把同一个 prompt 发 $N$ 次独立请求。

> **图 4｜以推理 FLOPs 衡量的成本与覆盖率对比（Llama-3-8B-Instruct vs. Llama-3-70B-Instruct）。** 理想模型规模取决于任务、算力预算和覆盖率要求。注意 Llama-3-70B-Instruct 在 GSM8K 上未能达到 100% 覆盖率，原因是存在一个标注错误的标准答案：见附录 E。
>
> *图意解读*：四张子图分别对应 MiniF2F、CodeContests、MATH、GSM8K，横轴是推理 FLOPs（对数刻度），纵轴是覆盖率。在 MiniF2F / GSM8K / MATH 上，8B 曲线在同等 FLOPs 下始终高于 70B 曲线；而在 CodeContests 上，70B 几乎总是更划算——说明「小模型多采样」并非普遍最优。

我们在图 4 中给出 MiniF2F、CodeContests、MATH 和 GSM8K 的重画结果。有意思的是，**使覆盖率最大的模型随算力预算和任务而变化**。在 MiniF2F、GSM8K 和 MATH 上，固定 FLOP 预算时 Llama-3-8B-Instruct 的覆盖率始终高于更大（也更贵）的 70B 模型；但在 CodeContests 上，70B 模型几乎总是更划算。需要指出，只看 FLOPs 是一种粗糙的成本度量，忽略了系统效率的其他方面 [21]。特别是重复采样可以利用大批量和专门的优化，相对于单次尝试的推理负载提升系统吞吐 [34, 6, 66]。第 5 节会进一步讨论。

我们还按当前 API 定价考察了在 SWE-bench Lite 上使用重复采样的**美元成本**。固定 agent 框架（Moatless Tools），我们比较三种做法：用 Claude 3.5 Sonnet 和 GPT-4o 每题单次尝试，以及用 DeepSeek-Coder-V2-Instruct 做重复采样。表 1 给出每种方法的平均每题成本与 issue 解决率。DeepSeek 模型虽弱于 GPT 和 Claude，但便宜 10 倍以上。在此情形下，重复采样提供了一种比「花高价买强模型」更便宜的替代方案，同时还能取得更高的 issue 解决率。

## 3 刻画重复采样的收益

LLM 的损失与训练算力之间的关系已被训练缩放律很好地刻画 [27, 36, 28]。这些规律在大量数量级上经验成立，让模型开发者相信大规模训练投入会有回报。受训练缩放律启发，我们在此尝试更好地刻画**覆盖率与采样预算（即推理算力量）**之间的关系，给出两个有意思的观察：

1. 覆盖率与样本数之间的关系常常可以用**指数化幂律**建模。
2. 对给定任务，同一家族中不同模型的覆盖曲线形似 **S 形曲线**——斜率相近，但水平偏移不同。

### 3.1 重复采样的缩放律

> **图 5｜对大多数任务和模型，覆盖率与样本数的关系可用指数化幂律建模。** 我们也指出，某些曲线（如 Llama-3-8B-Instruct 在 MiniF2F-MATH 上）并不严格遵循该趋势。误差条表示在对数刻度上均匀采样的 100 个点上，覆盖率曲线与幂律拟合之间的误差均值与标准差。
>
> *图意解读*：横轴是样本数（对数），纵轴是覆盖率；实线是拟合出的 $\exp(ak^b)$ 曲线，散点是实测 pass@k。拟合在 CodeContests、GSM8K 上贴合得很好，在 MiniF2F-MATH 上偏差最大（尤其是低样本区间存在明显的「S 形起步」）。

这里我们显式地建模覆盖率与样本数的关系。GPT-4 技术报告 [46] 发现，模型在代码问题上的平均对数通过率与训练算力之间可以用幂律很好地建模。我们先采用同一函数族，但改为建模**覆盖率 $c$ 的对数与样本数 $k$** 的关系：

$$
\log(c) \approx ak^{b} \tag{2}
$$

其中 $a,b \in \mathbb{R}$ 为拟合参数。为了直接预测覆盖率，对两边取指数，得到最终模型：

$$
c \approx \exp(ak^{b}) \tag{3}
$$

图 5 给出拟合示例，更多曲线见附录 C.2。虽然这些规律不如训练缩放律那样精确（在 MiniF2F-MATH 上最为明显），但它们提供了令人鼓舞的早期证据：推理扩展的收益是可以被刻画的。

### 3.2 不同模型覆盖曲线的相似性

> **图 6｜将同一家族中不同模型的覆盖曲线叠加。** 做法是（横轴取对数后）水平平移每条曲线，使其都穿过点 $(1, c)$。这里 $c$ 取图中所有模型的最大 pass@1 分数。平移后曲线高度相似，说明在同一模型家族内，采样缩放曲线形状一致。
>
> *图意解读*：如果平移后多条曲线几乎重合，意味着家族内模型只在「起点」上不同（即单样本能力差异），而「随着样本数增加而变好的速率」几乎相同。对实践的含义是：换更强的同族模型 ≈ 把曲线整体左移，而不改变你需要付出的采样倍数。

有意思的是，比较同一家族不同模型在同一任务上的覆盖曲线（横轴取对数，见图 3）时，勾出的 S 形曲线似乎**斜率相同、水平偏移各异**。为深入考察，我们在图 6 中把同族模型的覆盖曲线叠在一起。具体做法是选定一个锚点覆盖率 $c$，把每条曲线（在对数空间）向左平移，使每条都穿过点 $(1,c)$。这相当于向左平移 $\log(\text{pass@}k^{-1}(c))$，其中 $\text{pass@}k^{-1}(c)$ 表示使 $\text{pass@}k = c$ 成立的最小自然数 $k$。这些相似性说明：在同一家族内，把覆盖率从 $c$ 提升到 $c'$ 所需的**对数采样预算增量**（等价地，采样预算的**倍数**）近似为常数。

## 4 用好重复采样需要精度

到目前为止我们只关注覆盖率，即在「总能识别出正确样本」的前提下刻画重复采样的收益。现在转向互补的问题——精度：给定一组模型样本，我们有多大概率识别出正确的那些？我们尤其关心**验证器在样本数扩大时的表现**。对某些问题，正确解被模型采样到的概率很低（例如 1% 或更低，见图 8）。随着样本数增加，越来越多问题开始出现稀有但正确的解，覆盖率随之提升。要把这些覆盖率提升转化为成功率提升，验证器必须能「大海捞针」，识别出那些不常出现的正确样本。

### 4.1 常见验证方法并非总能随样本预算扩展

> **图 7｜随样本数增加，覆盖率（oracle 验证器下的性能）与主流选答案方法（多数投票、奖励模型选择、奖励模型加权投票）的对比。** 尽管覆盖率接近完美，所有样本选择方法都无法达到覆盖率上界，并在不到 100 个样本时就饱和。对每个 $k$，我们在 100 个大小为 $k$ 的子集上计算指标，画出均值与一个标准差。
>
> *图意解读*：图中最上面那条持续上升的曲线是覆盖率上界（约 95%+），下面几条几乎水平的方法曲线停在 40% 附近——两者之间的剪刀差就是「验证瓶颈」。这张图是全文最重要的负面结论：算力能买到覆盖率，但买不到精度。

在我们评测的五个任务中，只有 GSM8K 和 MATH 缺少自动验证解答的工具。我们测试三种简单常用的验证方法，看它们能否从这两个数据集里识别出正确解答：

1. **多数投票（Majority Vote）**：选出最常见的最终答案 [60]。
2. **奖励模型 + Best-of-N**：用奖励模型 [17] 给每个解打分，取分数最高样本的答案。
3. **奖励模型 + 多数投票**：做多数投票，但每个样本的票数按其奖励模型分数加权。

我们复用第 2 节中用 Llama-3-8B-Instruct 与 Llama-3-70B-Instruct 生成的 10,000 样本集合。奖励模型使用 ArmoRM-Llama3-8B-v0.1 [57]，它在 RewardBench 排行榜 [39] 的推理部分得分很高。结果见图 7。三种方法在样本数增加初期成功率都上升，但在约 100 个样本附近进入平台期；与此同时覆盖率继续上升，最终超过 95%。就多数投票而言，这种饱和很直观：稀有正确解的出现不会影响「最常见的答案」。

鉴于这些验证器（尤其是奖励模型）表现不佳，很自然会问：验证一个候选解到底有多「难」？在 GSM8K 和 MATH 中，判定正确性只看样本的最终答案，中间的思维链被丢弃。如果模型是「毫无意义地推理一通、然后蒙对最终答案」，那么验证未必比解题本身容易。我们通过人工评阅 105 条 Llama-3-8B-Instruct 在 GSM8K 上正确样本的思维链来考察这个问题，结果见表 2。

我们发现，在被评阅的思维链中 **90% 以上是忠实的（faithful）**，即使在正确答案很少被采样到的问题上也是如此。这些正确的推理步骤说明：验证器在识别正确样本时**有信号可利用**。有意思的是，在这个过程中我们还发现了一道 GSM8K 题目的标准答案是错的（见附录 E）。这道错题也正是 Llama-3-70B-Instruct 在 10,000 次尝试中唯一没能生成「正确」样本的题。

| pass@1 区间 | 题目数 | 评阅 CoT 数 | 正确 CoT | 错误 CoT | 标准答案错误 |
| --- | --- | --- | --- | --- | --- |
| 0–10% | 5 | 15 | 11 | 1 | 1 题，3 条 CoT |
| 10–25% | 10 | 30 | 27 | 3 | 0 题 |
| 25–75% | 29 | 30 | 28 | 2 | 0 题 |
| 75–100% | 84 | 30 | 30 | 0 | 0 题 |

> **表 2｜对 Llama-3-8B-Instruct 在 GSM8K 上答案中思维链有效性的的人工评估。** 每题评阅 3 条思维链。即使对困难问题（模型正确率 ≤10%），思维链也几乎总遵循有效的逻辑步骤。模型生成与人工标注见原文链接。
>
> *表意解读*：把 105 条 CoT 汇总，正确 96 条、错误 6 条、标准答案错误 3 条，忠实率约 96/105 ≈ 91%。这直接支撑了作者的论点——正确答案虽然稀有，但伴随的推理是可信的，因此训练更好的验证器是有前途的方向。

### 4.2 验证器与软件任务：两个警示故事

软件开发任务在可用验证工具方面处于中间地带。一方面，代码可执行、可测试，能实现比非结构化语言任务更高程度的自动验证；另一方面，单元测试对代码采取黑盒验证，不如证明检查器那样全面。验证过程的不完美会产生假阳性和/或假阴性，这在应用重复采样时很重要。下面给出我们在生成 2.1 节结果时遇到的两个软件验证器缺陷的例子。

#### 4.2.1 SWE-bench Lite 中的不稳定测试（Flaky Tests）

在产出 SWE-bench Lite 结果时，我们发现 **11.3%** 的题目拥有不稳定测试套件——对同一个候选解重复运行时结果不一致。这些不稳定测试甚至偶尔会把数据集**标准答案**判为错误。此外，某些题目的测试套件会因候选解不同而表现出非确定性。例如，有两个 SWE-bench Lite 题目涉及操作 Python 集合（set），而集合本身是无序的。这些题目的标准解显式地对集合元素排序，因此能稳定通过测试；但一些模型生成的候选解没有施加这种排序，于是在某些「运气好」的运行中通过，另一些则不通过。

附录 B 列出了我们识别出的所有存在不稳定测试的题目 ID。我们也报告了剔除这些有问题的题目后的 SWE-bench Lite 结果，与全数据集评测结论一致。

#### 4.2.2 CodeContests 中的假阴性

CodeContests 数据集每道题都带一组输入输出测试用例，用于评估解答正确性。这些测试用例比 APPS [25] 等早期编程基准更全面，降低了「通过全部测试但并未真正解题」的假阳性频率。然而，CodeContests 测试套件的构造方式会导致**假阴性**：解答正确却无法通过测试。

对某些 CodeContests 题目，问题描述允许给定输入有多个不同的正确输出；但对应的测试用例并不处理这些情况，而是要求输出某个特定的正确结果。此外，许多 CodeContests 测试用例是通过**变异**原始测试用例程序化生成的，一些变异后的输入违反了题目的输入规范（例如描述承诺输入为正整数，变异后却是 0）。这些畸形测试用例会导致不同的正确解之间行为不一致。

我们通过把每道题的测试套件跑在 CodeContests 提供的正确解列表上，来评估这些问题的普遍程度。在测试集中 122 道有 Python3 解答的题目里，有 **35 道**存在「正确」解却无法通过对应测试。由于我们不允许模型查看题目的全部测试用例（及其怪异之处），对这些题目做重复采样就带有「掷骰子」的成分——不仅要求解正确，还要恰好输出能通过测试的那一种结果。

> **图 8｜柱状图：GSM8K 与 MATH 各题中正确样本所占比例（共 10,000 个样本）。** 每题一根柱子，柱高表示得出正确答案的样本比例。柱子为绿色表示自一致性（self-consistency）选到了正确答案，红色表示没有选到。我们特别指出：有许多题目存在正确解，但正确解被采样到的频率很低。
>
> *图意解读*：绝大多数柱子贴近 0（说明「能解出来」的概率极低），少数柱子接近 1。绿色柱子散布在整个区间，说明多数投票在低频率区间失效；而恰好是这些低频率、长尾的题目，贡献了覆盖率从 82.9% 到 98.44% 的全部增量。

## 5 讨论与局限

本文把重复采样作为推理时扩展算力的一条轴来探索，以提升模型性能。在一系列模型和任务上，重复采样能显著提高「被任意生成样本解决」的题目比例（即覆盖率）。当正确解可被识别时（无论是自动验证工具还是其他验证算法），重复采样能在推理阶段放大模型能力。这种放大可以使「弱模型 + 多样本」的组合比「强模型 + 少尝试」更高性能、更具成本效益。

**改进重复采样。** 在我们的实验中只探索了一个简单版本的重复采样：对同一问题用完全相同的 prompt 和超参数独立生成所有尝试。我们认为这一设置还有改进空间，尤其是在以下方向：

1. **解的多样性**：目前我们仅依赖正的采样温度来产生样本间差异。把这种 token 级采样与其他更高层的方法结合，可能进一步提升多样性。例如 AlphaCode 用不同的元数据标签来条件化不同样本。
2. **多轮交互**：尽管解 CodeContests 和 MiniF2F 时自动验证工具是可用的，我们只用了单轮设置——模型生成一个解，无法对其迭代改进。把工具的**执行反馈**提供给模型应当能提升解的质量。我们对多轮交互的权衡很感兴趣：每次尝试更贵，但成功的可能性也更高。
3. **从以往尝试中学习**：目前我们的实验把各次尝试完全隔离。若能访问已有样本（尤其当验证工具能对其给出反馈时），可能有助于生成后续尝试。

**重复采样与推理系统。** 重复采样是一种有别于聊天机器人服务的 LLM 推理负载。生产环境的聊天部署强调低响应延迟，为满足延迟目标可能被迫降低每设备批大小、降低硬件利用率。相反，对单个 prompt 采样大量完成时，可以更强调总吞吐与硬件利用率最大化。此外，重复采样还能受益于利用序列间 prompt 重叠的专门注意力优化 [34, 6, 66]。因此，重复采样推理的成本可以低于「向面向聊天的 API 朴素地发很多并行请求」。这些成本节省进一步支持「在便宜模型上多采样，而非在贵模型上少采样」的选择。

**验证器。** 第 4 节的结果凸显了在缺少自动验证工具时改进样本验证方法的重要性。让模型具备评估自身输出的能力，将使重复采样可以扩展到多得多的任务。特别值得关注的是把重复采样应用到创意写作这类**非结构化任务**——相比本文考虑的 pass-fail 任务，它需要对不同样本做更主观的比较。除发展基于模型的验证器外，另一条路是设计**转换器**，使非结构化任务变得可验证，例如把非形式化的数学命题形式化到 Lean 这样的语言中，从而可以应用证明检查器。

## 6 相关工作

**扩展推理算力**：在推理阶段做额外计算的方法在深度学习多个领域都取得了成功。在各种游戏环境中，SOTA 方法利用推理时搜索，在落子前考察许多可能的未来状态 [12, 50, 10]。类似的树搜索方法也可以与 LLM 结合使用，让模型更好地规划和探索不同方案 [63, 8, 53, 54]。另一条增加 LLM 推理算力的轴是让模型花更多 token 在问题上「思考」再给答案 [62, 61, 64]。此外，多个模型可以在推理时集成（ensemble）以结合各自优势 [58, 14, 45, 56, 31]。还有一类方法是用 LLM 批评并修正自己的回答 [43, 7]。

**重复采样**：已有工作表明重复采样能在多个领域提升 LLM 能力。最有效的用例之一是代码 [48, 15, 38]，性能可持续扩展到一百万样本，且通常有验证工具（如单元测试）自动为每个候选解打分。最近 Greenblatt [23] 表明重复采样在解 ARC 挑战 [16] 的谜题时有效，并观察到随样本数增加的对数线性扩展。在聊天应用中，重复采样配合奖励模型的 best-of-N 排序可以超过贪心地采样单个回答 [30]。在没有自动验证工具的领域，已有工作表明用多数投票 [60]、提示 LLM 判断 [19]、或训练基于模型的验证器 [18, 42, 29, 59, 35] 来决定最终答案，相对于单样本能提升推理任务性能。Nguyen 等人 [44] 发现在超过某长度阈值的答案上做多数投票，可以优于在所有答案上投票。与我们同期，Song 等人 [51] 发现使用可用的最佳样本能提升 LLM 在聊天、数学和代码任务上的性能（最多扫到 128 个样本）；Hassid 等人 [24] 发现在解代码任务时，从小模型多采样可能比从大模型少采样更有效。

**缩放律**：刻画缩放如何影响模型性能，有助于更明智地分配资源。LLM 训练缩放律发现损失与训练算力之间呈幂律关系，并给出固定算力预算下最优模型规模与数据规模的估计 [27, 36, 28]。Jones [33] 在棋类游戏 Hex 中发现缩放律，观察到性能随模型规模和问题难度可预测地变化；有意思的是他们还表明性能随树搜索所用的测试时算力而扩展。最近 Shao 等人 [49] 在用外部检索数据集增强 LLM 时观察到缩放律：检索任务上的性能随检索语料规模平滑扩展。

### A 采样实验设置

**A.1 Lean 形式化证明。** 我们在 lean4 MiniF2F 测试集中由 MATH 题目形式化而来的 130 道题上报告结果。该数据集源自 Zheng 等人 [65] 修正后的原始 MiniF2F 版本。采样温度 0.5，不使用 nucleus 采样，每题生成 10,000 个样本。我们用验证集中以下 5 条定理的证明作为 few-shot 示例：`mathd_algebra_116`、`amc12_2000_p5`、`mathd_algebra_132`、`mathd_algebra_11`、`mathd_numbertheory_84`。

我们的 prompt 由三部分组成：(1) few-shot 示例；(2) HuggingFace 数据集 `cat-searcher/minif2f-lean4` 中每题已有的 header imports；(3) 定理定义。为避免从定理名泄漏解题信息，我们把定理名替换为 `theorem_i`——few-shot 示例用 $i \in \{1,2,3,4,5\}$，当前题目用 $i=6$。

生成解的最大 token 长度为 200。评分使用 lean-dojo 1.1.2 库、Lean 版本 4.3.0-rc2，每个 tactic 步骤设置 10 秒超时。

**A.2 CodeContests。** 我们在问题描述中不含图片标签的 140 道测试题上报告结果。沿用 CodeLlama [48] 的实验设置，采样温度 0.6、top-p 0.95，每题生成 10,000 个样本。每题从训练集中随机取 2 条 few-shot 示例。生成解最大 token 长度 1024。我们使用与 [41] 相同的答案比较函数，并用 public、private 与 generated 测试的拼接来验证解的正确性。

**A.3 MATH。** 在 128 道随机选取的测试题上报告结果。温度 0.6，不使用 nucleus 采样，每题使用 [40] 的固定 5 条 few-shot 示例，生成 10,000 个样本，最大 token 长度 512。评分时用 LMEval [22] 的 `minerva_math` 函数抽取模型最终答案，若抽取结果与标准答案字符串完全一致，或 `minerva_math` 中的 `is_equiv` 函数为真，则判为正确。

**A.4 GSM8K。** 在 128 道随机采样的测试题上报告结果。温度 0.6，不使用 nucleus 采样，每题随机取 5 条训练集 few-shot 示例，生成 10,000 个样本，最大 token 长度 512。评分遵循 LMEval [22]，用正则抽取「####」之后的字符串；与 MATH 类似，通过字符串完全一致或 `is_equiv` 为真来判定正确。

### E GSM8K 中的错误答案

如 4.1 节所述，我们发现 GSM8K 测试集中有一道题（HuggingFace 上索引 1042）的标准解是错误的。

**题目**：Johnny 的爸爸带他去看赛马并下注。第一场他输了 5 美元。第二场他赢了「比之前输的钱的两倍还多 11 美元」。第三场他输的钱是第二场赢的 1.5 倍。那天他平均每场输多少钱？

**数据集给出的答案**：第二场赢了 11 美元，因为 $1+5\times2=11$（*原文此处算式已明显混乱*）；第三场输了 15 美元，因为 $10\times1.5=15$；第一场和第三场合计输 20 美元，因为 $15+5=20$；当天净输 9 美元，因为 $11-20=-9$；三场平均每场输 3 美元，因为 $9/3=3$。最终答案标注为 **3**。

**错误所在**：解答第二行就错了——第三场 Johnny 的爸爸输的是 **16.5 美元**，不是 15 美元。也就是说他赢了 11 美元、输了 $\$16.5+\$5=\$21.5$，因此平均每场亏损 **3.5 美元**，而非数据集标注的 3 美元。

> *（译者注）* 这个小节的意义不只是「数据集有 bug」。它同时解释了图 4 中 Llama-3-70B-Instruct 在 GSM8K 上为何无法达到 100% 覆盖率——因为「正确答案」本身是错的，模型答对反被判错。这也提示：当覆盖率逼近上界时，**评测集本身的噪声**会成为天花板。

## 术语与背景速览（译者整理）

| 术语 | 含义 |
| --- | --- |
| Repeated sampling（重复采样） | 对同一 prompt 以正温度独立采样多个候选解，再用验证器挑一个作为最终答案 |
| Coverage（覆盖率） | 被**至少一个**生成样本解出的题目比例；等价于代码领域的 pass@k，是成功率的**上界** |
| Precision（精度） | 从一堆（多为错误的）样本中识别出正确样本的能力；决定覆盖率能兑现多少 |
| Verifier（验证器） | 判定候选解对错的机制：单元测试、Lean4 证明检查器、奖励模型、多数投票等 |
| Oracle verifier（理想验证器） | 假设验证永远正确的上界设定，用来测覆盖率 |
| pass@k | $k$ 个样本中至少一个通过的比例，用无偏估计式 (1) 计算 |
| Exponentiated power law（指数化幂律） | $\log c \approx a k^b$，即 $c \approx \exp(ak^b)$，用于刻画覆盖率随采样数的增长 |
| Majority voting（多数投票 / 自一致性） | 在最终答案上投票取最常见者；样本数增大时对稀有正确解不敏感 |
| Reward model + Best-of-N | 用奖励模型打分，取最高分样本的答案 |
| Flaky test（不稳定测试） | 对同一份代码重复运行结果不一致的测试，会造成假阳性/假阴性 |
| False negative（假阴性） | 解本身正确，但因测试用例畸形（如要求某个特定正确输出）而被判错 |
| Moatless Tools | 开源 SWE-bench agent 框架，为模型提供检索、浏览、编辑代码库的工具 |
| Faithful CoT（忠实思维链） | 最终答案正确、且中间推理步骤逻辑有效的思维链 |

**核心数字速记**

- SWE-bench Lite（DeepSeek-Coder-V2-Instruct）：单样本 **15.9%** → 250 样本 **56%**，超单样本 SOTA **43%** 达 13 个百分点。
- CodeContests（Gemma-2B）：pass@1 **0.02%** → pass@10k **7.1%**，提升 **300 倍以上**。
- MATH（Pythia-160M）：pass@1 **0.27%** → pass@10k **57%**。
- MATH（Llama-3-8B-Instruct）：覆盖率 100 样本 **82.9%** → 10k 样本 **98.44%**；而多数投票/奖励模型仅 **40.50% → 41.41%**，约 100 样本即饱和。
- 成本对比（SWE-bench Lite，每 issue）：DeepSeek 采 5 次 $0.036 → 29.62%，总成本 10.8；GPT-4o 单次 0.13 → 24.00%，总成本 39；Claude 3.5 Sonnet 单次 0.17 → 26.70%，总成本 51。
- 数据缺陷：SWE-bench Lite 有 **11.3%**（34/300）题目测试套件不稳定，其中 30 例连标准解也不稳定；CodeContests 测试集 122 道 Python3 题中 **35 道**存在「正确解过不了测试」的假阴性。
- 思维链忠实度：人工评阅 105 条正确样本的 CoT，**90%+ 忠实**（正确 96 / 错误 6 / 标准答案错误 3）。
- 采样超参：MATH/GSM8K 温度 0.6、512 token；CodeContests 温度 0.6 + top-p 0.95、1024 token；MiniF2F 温度 0.5、200 token；SWE-bench 温度 1.6、250 次尝试。

**一句话结论**

算力可以买到覆盖率，但买不到精度：在可自动验证的领域（代码、形式化证明），重复采样是当下最便宜的一条「用算力换能力」的路径——弱模型 + 250 个样本即可反超前沿模型的单次尝试；而在缺少可靠验证器的领域，重复采样的收益会被验证瓶颈截断，瓶颈从「生成」转移到了「判断」。
