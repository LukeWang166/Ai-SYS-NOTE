## 摘要

编程是一种强大且无处不在的问题求解工具。开发能够辅助程序员、甚至独立生成程序的系统，有望让编程变得更高效、更易获得，但迄今为止，把 AI 领域的创新融入其中仍颇具挑战。近期的**大规模语言模型**展现出令人印象深刻的代码生成能力，已经能够完成简单的编程任务。然而，当被放置在更复杂、未曾见过的问题上——那些要求的解题能力超出"简单地把指令翻译成代码"——这些模型的表现依然糟糕。举例来说，需要理解算法和复杂自然语言的**竞技编程（competitive programming）**题目，至今仍然极其困难。为填补这一差距，我们提出 **AlphaCode**：一个代码生成系统，能够为这类需要更深推理的题目创造出新颖的解法。在 Codeforces 平台上近期编程竞赛的**模拟评测**中，AlphaCode 平均取得了**前 54.3%** 的排名（参赛者超过 5000 人的比赛）。我们发现，要实现良好且稳定的性能，有三个关键组件缺一不可：**(1)** 一个大规模且干净的竞技编程数据集，用于训练与评测；**(2)** 大型且**易于采样的** Transformer 架构；**(3)** **大规模模型采样**以探索搜索空间，随后基于**程序行为**进行过滤，收敛到一小组待提交解。

## 1. 引言

计算机编程已成为贯穿科学、工业与日常生活的一种通用问题求解工具。伴随这一发展，对"让程序员更高效"（Matsakis and Klock, 2014）或"让编程与编程教育更易获得"（Resnick et al., 2009）的工具，需求持续增长。开发能够有效建模并理解代码的 AI 系统，可以改变这类工具的面貌，以及我们与之交互的方式。能够生成代码的系统不仅有用，也是我们更深地理解 AI 及其与编程关系的垫脚石。

生成用于求解指定任务的代码，要求在巨大的、结构化的**可能程序空间**中进行搜索，而**奖励信号极为稀疏**。单个字符的改动就足以完全改变程序行为，即使它并不会导致崩溃；对同一个问题，解法的外观也可能天差地别；而判断一个不完整或不正确的程序是否有用，本身就是一个困难问题。因此，以往的大多数工作只能局限于**受限的领域专用编程语言**（Gulwani, 2011）或**简短的代码片段**（Bruch et al., 2009; Raychev et al., 2014）。

近期大规模 Transformer（Vaswani et al., 2017）语言模型在文本生成上取得了令人瞩目的表现（Brown et al., 2020），也成功把"求解简单编程问题的 Python 代码"生成了出来（Austin et al., 2021; Chen et al., 2021）。我们模型的一个**精简版**（去掉第 4 节所描述的各项改进）表现与 Codex 相近（见表 A3）。然而，Codex 论文及类似工作所用的题目，大多都是带有简短解的**简单任务描述**——远不及真实世界编程的完整复杂度。从一段冗长的自然语言任务描述出发，用 C++ 或 Python 这样的通用编程语言生成一个**完整程序**，至今仍是一个开放问题。

生成简短代码片段与生成完整程序之间的难度差异，可以类比**命令式（imperative）问题求解与声明式（declarative）问题求解**之间的差别。生成简短代码片段，通常相当于把任务规格直接翻译成代码，有时甚至退化成"调用正确的 API"。相比之下，生成完整程序往往依赖于**理解任务、并且想清楚如何完成它**，这需要更深层的算法推理。

竞技编程题目在上述所有方面都代表了一次显著的跃升。求解这类题目需要：理解复杂的自然语言描述；对从未见过的问题进行推理；掌握广泛的算法与数据结构；并精确地实现可能长达数百行的解法。解法的正确性通过在**一整套未知的测试**上执行来评判，既要检查边界情况上的行为是否正确，也要检查执行速度。而**用于评测的测试用例是隐藏的**，这一点本身构成了挑战的重要部分。这些复杂题目是为每场比赛**全新创作**的，同时默认参赛者可以借鉴以往题目的解法（隐式地，通过记住旧题；或显式地，通过搜索它们）。此外，竞技编程非常流行：像国际大学生程序设计竞赛（ICPC, 2021）和国际信息学奥林匹克（IOI, 2021）这样赛事，被广泛认为是计算机科学领域最负盛名的竞赛之一，吸引了来自世界各地的数十万参赛者。采用这些久经考验的竞赛中"人类也觉得难"的题目，可以确保系统无法走捷径，并为我们提供一个**衡量智能多个方面**的有意义基准。

早期把程序合成用于竞技编程的工作表明，大型 Transformer 模型可以达到**个位数的解题率**（Chen et al., 2021; Hendrycks et al., 2021），但还无法为绝大多数题目可靠地生成解法。并且，正如我们在第 3.2.1 节所示，现有竞技编程数据集中测试用例的不足，使得在其上定义的指标容易出现**高假阳性率**（有 30% 甚至更多的程序通过了所有测试但实际并不正确），因而不足以可靠地衡量研究进展。

> **图 1 | AlphaCode 在 10 场模拟 Codeforces 比赛中的排名，以及估测的评级（越靠右越好）。** AlphaCode 在 10 场比赛中平均排名进入参赛者的**前 54.3%**，估测的平均 Codeforces 评级为 **1238**。**(a)** 展示参赛者的评级（纵轴）与他们在每场比赛中的排名（横轴），以及 AlphaCode 在 10 场比赛各自的排名；横轴标注的 1591、1608、1613、1615、1617、1618、1619、1620、1622、1623 是 10 场比赛的 ID，纵轴 "%competitors rating" 表示比该评级更低的参赛者比例。**(b)** 展示 AlphaCode 在"过去 6 个月内至少参加过 1 场比赛的用户"中的估测评级——AlphaCode 的估测评级 1238 高于其中 **72%** 的用户。
> *（译者注）Codeforces 评级体系类似经典的 Elo 分：初始 1500，赢题加分、输题扣分。1238 大致处在 Codeforces 的 "Pupil/Specialist" 区间，远低于 Expert（1600+），但对当时的 AI 系统而言已是首次达到人类竞赛的中位数水平。*

本文中我们提出 **AlphaCode**，一个用于求解竞技编程题目的代码生成系统。我们使用大型 Transformer 语言模型生成代码：先在精选的 GitHub 代码上做**预训练**，再在我们自行整理的竞技编程题目集上做**微调**。对于每个未见过的题目，我们生成**大量的程序样本**，依据题目自带的样例测试执行结果进行**过滤**，然后把剩余样本**聚类**，得到一小组待提交评测的候选解。我们将在第 4 节详细描述 AlphaCode。

开发本系统的一个核心部分，是确保提交被**严格评估**、且评测题目在训练过程中**真正未出现过**，从而让难题无法通过从训练集复制来解决。为此，我们发布了一个新的竞技编程训练与评测数据集 **CodeContests**（第 3 节）。该数据集融合了多个来源的数据，按**时间**切分以使所有训练数据都早于评测题目，额外增加了生成的测试数据以确保正确性，并在一个模拟竞技编程设定下评估提交。在我们的评估中（第 3.2.1 节），CodeContests 把假阳性率从现有数据集的 30–60% 降低到**仅 4%**。我们的最佳模型在每道题最多提交 10 次（与人类相当）的设定下，解决了该数据集中 **34.2%** 的留出竞技编程题目；相比之下，此前在现有数据集上报告的解题率约为 1–5%（见第 5.4 节）。

为验证结果，我们还在流行的 Codeforces 平台举办的**模拟编程竞赛**上评测了 AlphaCode（第 5.1 节）。在每场超过 5000 名参赛者的 10 场近期比赛评测中，AlphaCode 平均取得了**前 54.3%** 的排名。基于这些结果，我们估计本系统的 Codeforces 评级为 **1238**，处在"过去 6 个月内参加过比赛的用户"的**前 28%** 以内（图 1）（Ebtekar, 2021）。这些评测只包含尝试过此类比赛的用户，而他们本身就是所有程序员中一个自我筛选出的子集。**这是计算机系统首次在编程竞赛中达到如此有竞争力的水平。**

我们还对系统进行了详细分析（第 6 节），表明 AlphaCode **并没有**通过重复训练集中的代码片段来解题，而是**高度依赖自然语言题目描述**来创造原创解法。我们进一步考察了模型能解与不能解的题目类型，并讨论了为什么**验证损失是解题率的不佳代理指标**。

## 2. 问题设定

编程竞赛始于 1970 年代，此后不断普及，如今在全球拥有数十万参与者。一年一度的国际大学生程序设计竞赛吸引了来自 3000 多所高校的近 6 万名学生（ICPC Factsheet, 2020），谷歌（Google Code Jam, 2021）和 Facebook（Facebook Hacker Cup, 2021）等公司也会定期举办比赛。本文通篇使用的 Codeforces 平台拥有超过 **50 万活跃用户**，每周举办的比赛吸引数以万计的参赛者（Mirzayanov, 2020）。

### 2.1 竞技编程

不同比赛的赛制细节各有差异，但一般而言，参赛个人或团队会拿到 **5 到 10 道题目描述**（图 2）和大约 **3 小时**时间，用来编写能正确求解尽可能多题目的程序（图 3）。提交的程序被送到服务器上，服务器会在一整套**穷尽的隐藏测试**（图 A1）上自动评测。参赛者只会被告知提交是否通过了全部测试，而不一定知道失败的确切原因。比赛设有罚时机制，依据每道题的错误提交次数和解题所花的时间（ICPC Rules, 2021）。提交可以用多种编程语言书写，其中 C++ 和 Python 目前最流行。题目通常带有表明难度的评级，越难的题目分值越高。

求解一道题涉及三个步骤。**第一**，参赛者必须阅读并理解一段跨越多个段落的自然语言描述，其中包含：通常与题目无关的叙述性背景；参赛者需要仔细理解并解析的"期望解法"的说明；输入与输出格式的规格说明；以及一组或多组示例输入/输出对（我们称之为**"样例测试"，example tests**）。

**第二**，需要创造出能求解该问题的**高效算法**。从"题目是什么"到"如何求解"，是一次巨大的跳跃，需要对问题进行理解与推理，也需要对各类算法与数据结构有深入的掌握。这一跳跃是与既往工作的一个显著不同——后者往往显式地指定了要实现什么。此外，算法的效率必须足以在题目规定的输入规模与时间限制内跑完，这通常排除了那些更简单、朴素的尝试。

**第三**，必须把算法**实现**出来。在有执行时间约束的情况下，实现效率很重要（更难的题有时只能用 C++ 这类更快的语言求解）；微妙的边界情况可能难以顾及；而解法本身可能有上百行精确的代码。参赛者会得到少量样例测试用例用来对拍，并且常常在正式提交（针对隐藏测试）之前，反复调试、修复并重跑他们的候选解法多次。图 3 给出了 AlphaCode 针对图 2 中的题目所生成的一个正确解的示例，更详尽的结果与分析见第 5 节和第 6 节。

> **图 2 | 竞技编程题目描述。** 这是 Codeforces 题目 **Backspace** 的题面（Mirzayanov, 2020）。这是一道中等难度的题，评分为 **1500**。题面内容为：给定两个由小写英文字母组成的字符串 $s$ 和 $t$，你将逐个字符输入 $s$；输入某个字符时，你可以选择按"退格键"代替——它会删除当前字符串中所有尚未被删除的字符里的最后一个（若当前无字符则什么也不做）。任务是判定能否通过"输入 $s$、并在若干字符位置改为按退格"得到字符串 $t$。输入首行为测试用例数 $q$（$1 \le q \le 10^5$），每个测试用例两行分别为 $s$ 和 $t$（长度均为 $1 \le |\cdot| \le 10^5$），且所有测试用例的字符总数不超过 $2 \cdot 10^5$；输出对每个测试用例打印 YES 或 NO（大小写均可）。图右侧展示了题面自带的**公开样例测试**：4 组用例的输入为 `ababa/ba`、`ababa/bb`、`aaa/aaaa`、`aababa/ababa`，对应输出为 YES、NO、NO、YES，并附带逐条解释。用于评测提交的**隐藏测试**见图 A1；AlphaCode 生成的解见图 3。**完整的题面（连同精确格式）会全部交给 AlphaCode**，模型实际看到的题目描述格式样例见附录 F。

> **图 3 | 图 2 中那道题由 AlphaCode 生成的解。** 模型成功地从自然语言描述中提取出了求解所需的信息：① 题目是要判断是否可以通过"在输入若干字符时改为按退格"把一个串变成另一个串，因此先读入这两个串（第 3–4 行）；② 如果两个串末尾的字符不匹配，那么末尾字符必须被删除；如果匹配，就可以移到倒数第二个字符并重复这一过程（第 11–18 行）；③ 退格会删掉两个字符——你本该输入却没有输入的那个字符，以及它前面的那个字符（第 19–20 行）；④ 如果每个字符都匹配上了，就说明可以从 $s$ 得到 $t$（第 23–26 行）。
> 右侧代码采用**逆向处理**思路：把 $s$、$t$ 都转成列表并反转，然后用一个 `while` 循环从尾到头比对——当两端当前字符相等时就同时弹出（匹配成功继续），不相等且 $s$ 还有 2 个以上字符就一次弹出 $s$ 的两个字符（模拟一次退格），只剩 1 个字符时弹出它；循环结束后若 $t$ 已被完全匹配则输出 YES，否则输出 NO。这段代码的逻辑本身是正确的。
> *（译者注）值得注意的是，这段实现用的是基于 `pop(0)` 的写法——对 Python list 而言每次弹出为 $O(n)$，整体最坏复杂度是 $O(n^2)$；但对 $|s|,|t| \le 10^5$ 且总字符数不超过 $2 \cdot 10^5$ 的约束而言，它仍然能在限时内跑完。这类"复杂度不优但侥幸过关"的现象说明：代码 benchmark 的时间限制设定会直接影响模型能否被判通过。*

### 2.2 评测

让一个系统去参加真实的现场编程竞赛固然是无偏的评测，但它引入了很高的复杂度，也并非一个稳定的基准。为缓解这一问题，我们提出了一个适合研究迭代的**代理指标**，类似于大多数监督学习数据集中的开发集。我们的指标在保留竞赛基本结构的同时，简化了那些偶然性的细节。我们使用的指标是"**用每题 $k$ 个样本、提交 $n$ 次所解出的题目百分比**"，记作 $n@k$。

该指标表示：若模型对每道题允许**先生成** $k$ 个样本，然后从中挑选 $n \le k$ 个样本提交给隐藏测试进行评测，能够解出的题目占比。只要这 $n$ 次评测中有任何一次通过了全部测试，该题即被计为已解出。**过滤方法由系统自行决定**，但只能基于参赛者可获得的信息（例如题面自带的样例测试，而**不能**使用隐藏测试）。$n$ 和 $k$ 均有限时，为降低不同运行之间的方差，我们报告的指标是基于一组通常**远大于** $k$ 的样本通过 **bootstrapping（自助采样）**计算出的期望（附录 A.3）。通过期望来降低方差，使得改进之处的比较更有意义——因为我们的验证集和测试集规模相对较小，而从单一模型采样时方差显著。

**限制提交次数为 $n$** 是为了模拟错误提交带来的罚时，并防止系统通过"把提交拿去对着隐藏测试跑不合理多次"来利用评测指标。固定 $k$ 则对不同评测之间的比较很重要，因为我们发现性能随样本数量单调上升（第 5 节）。我们使用 bootstrapping，确保依然能从"生成一组**远大于** $k$ 的 $K \gg k$ 样本"这一做法中获得降方差的好处，从而对 $n@k$ 指标做出估计。

我们用来建模编程竞赛的设定是 **$10@k$**——每题 $k$ 个样本、10 次提交。我们也使用 **$pass@k$**（用 $k$ 个样本的解题率），以与 Chen et al. (2021) 保持一致，其假设是所有样本都可以提交评测。$pass@k = k@k$，是使用 $k$ 个样本时的**上界指标**。我们会展示随不同 $k$ 值变化的解题率，因为"低采样预算下结果好"未必与"高采样预算下结果好"相关联。

## 3. 数据集

我们所有的模型都先在 GitHub 开源代码的集合上做**预训练**，随后在我们创建并开源的编程竞赛数据集 **CodeContests** 上做**微调**。预训练阶段帮助模型学到良好的代码表示、流畅地生成代码；微调阶段则帮助模型适配目标领域——竞技编程。

### 3.1 预训练数据集

我们的预训练数据集基于 2021 年 7 月 14 日拍摄的一份精选公开 GitHub 仓库快照。我们收录了数种流行语言的全部代码文件：C++、C#、Go、Java、JavaScript、Lua、PHP、Python、Ruby、Rust、Scala 和 TypeScript。遵循先前工作（Chen et al., 2021），我们过滤掉了所有超过 1 MB 的文件，以及含超过 1000 字符长行的文件，以排除自动生成的代码。我们还移除了同一文件的重复副本（比较时忽略空白字符）。过滤之后，最终的预训练数据集共包含 **715.1 GB** 代码。数据集的语言构成见附录（表 A1）。

### 3.2 CodeContests 微调数据集

在 GitHub 上预训练过的模型能够生成不错的代码、解决简单的编程问题，但正如附录 B.3 所示，它们能解决的竞技编程题目**非常少**。要在专用的竞技编程数据集上微调模型，对性能至关重要。

为便于微调与评测，我们整理了一个新的竞技编程题目数据集，命名为 **CodeContests**。该数据集包含我们从 Codeforces 平台抓取的**题目、题解与测试用例**，并混入了已有的公开竞技编程数据集。更具体地说，训练数据结合了：新抓取的 Codeforces 数据（Mirzayanov, 2020）、现有的 **Description2Code**（Caballero et al., 2016）以及 **CodeNet**（Puri et al., 2021）的数据。数据集的**验证集与测试集则完全由新抓取的 Codeforces 题目构成**。

为防范数据泄漏，我们采用了严格的**时间切分**：所有预训练与微调训练数据都出现在任何验证题之前，而所有验证题又都出现在测试题之前。与我们的 GitHub 预训练数据集快照日期相衔接，CodeContests 中的全部训练数据都是在 2021/07/14 或之前公开发布的。验证题出现在 2021/07/15 至 2021/09/20 之间，而测试集包含 2021/09/21 之后发布的题目。这种时间切分意味着，训练模型时可获得的信息**仅限于人类当时也能看到的信息**（更多细节与分析见附录 B.3）。该数据集的一些基本统计量见表 1。

我们从 Codeforces 抓取的数据包含类似图 2 所示的完整题目描述，以及每道题的**元数据**。元数据包括**难度评级**与**标签**（tags），标签指示求解该题可能需要用到的方法（例如 "greedy" 贪心或 "dp" 动态规划）。**难度评级与标签在比赛中都是不可见的**（因此不应在测试时使用）。我们的数据集还同时包含由最流行的提交语言（C++、Python 和 Java）书写的**正确与错误**人类提交。每道题都包含平台上可获取的全部测试用例：题干中的样例测试，以及比赛结束后在评测结果页面上公开的隐藏测试用例。为提升数据质量与一致性，并避免合并数据集时出现的重复问题，我们按照附录 B.2 中概述的流程对这些数据进行了清洗。

程序的正确性通过在测试用例上执行它、并将程序输出与期望的正确输出做比对来检查。关于该正确性检查流程的更多细节记录在附录 A.2 中。

#### 3.2.1 假阳性与额外生成的测试

我们希望测试用例尽可能地穷尽，从而防止提交因"测试用例覆盖不足"而被判为正确。不幸的是，高质量的测试用例并不容易获得。例如，Codeforces 平台在测试用例长度超过约 400 字符时就**不会完整显示**。测试覆盖不足会导致两类问题：**假阳性（false positives）**，即错误的提交被判为正确；以及**慢阳性（slow positives）**，即正确但算法上低效、不满足时间与内存约束的解被判为正确（例如复杂度阶数错误的解）。这些假阳性**不影响**第 5.1 节所述的 Codeforces 评测。

值得注意的是，这两个问题在既往数据集与程序合成文献中都很常见，因为输入/输出示例本身对程序行为是一种**欠规格化（under-specification）**（Gulwani et al., 2017）。表 2 展示了我们数据集与 **APPS**（Hendrycks et al., 2021）、**HumanEval**（Chen et al., 2021）的估测假阳性率对比——后两者都有大量假阳性。平均每题测试数量高，并不一定意味着测试是穷尽的，因为某些题的测试数可能远低于平均值，而某些测试也可能在考察相似的情形。

为了降低数据集的假阳性率，我们通过对已有测试输入做**变异（mutation）**来生成额外的测试用例。可能的变异包括：对二进制输入施加位翻转、对整数随机加一或减一、以及交换和改变字符串中的字符。变异后的输入会用 30 个正确解在其上运行、并检查所有解产生相同输出来验证。该过程针对每道题最多运行 10 个 CPU 小时，或生成至多 200 个测试。由于某些题目的输入格式复杂，有 **6.3%** 的题目我们未能生成完整的 200 个测试。

最后，我们过滤掉验证集与测试集中测试覆盖不足的题目，只保留那些拥有**至少 5 个隐藏或生成的测试用例、且这些用例能产生至少 2 种不同输出**的题目。这确保了模型不能通过"总是输出一个常量（如 YES 或 NO）"来平凡地解决题目。如表 2 所示，生成测试与过滤把我们数据集的假阳性率从 **62%** 降低到了 **4%**。尽管我们对 APPS 和 HumanEval 抽取的样本更少、且这两份数据集的题目相对不那么复杂（这两点都倾向于压低假阳性率），CodeContests 的假阳性率依然**显著优于**此前的工作。不过，仍有相当数量的题目会被那些"慢但语义正确"的解通过。

## 4. 方法

生成用于求解特定任务的代码，要求在巨大的、结构化的程序空间中进行搜索，而奖励信号极为稀疏。更棘手的是，包括竞技编程在内的许多领域，可用于学习的"任务—解"样本数量都十分有限。最后，由于我们限制了每道题的提交次数，每一次提交都必须被物尽其用。

我们的系统 AlphaCode 正是为应对上述所有挑战而设计的。图 4 给出了我们方法的高层视图。主要流程是：

1. **在 GitHub 代码上预训练**一个基于 Transformer 的语言模型，使用标准的语言建模目标。该模型可以合理地表示人类编程的空间，从而极大地缩小问题搜索空间。
2. **在我们自己的竞技编程数据集上微调模型**，以 GOLD（Pang and He, 2020）配合 **tempering（温度调节）**（Dabre and Fujita, 2020）作为训练目标。这进一步缩小搜索空间，并通过利用预训练来弥补竞技编程数据量小的问题。
3. 对我们的模型**为每道题生成极大量的样本**。
4. **过滤样本**以得到一小撮候选提交（**至多 10 个**）送去在隐藏测试用例上评测——做法是结合样例测试与**聚类**，依据程序行为来挑选样本。

在上述各点中，**大规模采样 + 过滤**是我们这套设置所独有的，而我们发现这一流程极大地提升了题目的解题率。因此，我们的许多设计决策都是为了服务于高效、有效的采样。

> **图 4 | AlphaCode 总览。** 系统分为训练与推理两条主线。训练侧：先在 GitHub 代码上做**预训练**，再在 CodeContests 上做**微调**，产出一族用于在推理时做**大规模采样**的模型。推理侧：针对给定题目，大规模采样生成海量候选解 → 用题面自带的**样例测试**进行**过滤**（剔除无法通过者和无法编译者）→ 基于**程序行为封装/聚类**（对程序在生成的测试输入上的输出做比较，把行为相同的归为同簇）→ 每个簇挑一个代表，形成**最终提交的候选集**（至多 10 个）。

### 4.1 模型架构

竞技编程的代码生成问题可以被看作一个**序列到序列（sequence-to-sequence）**（Sutskever et al., 2014）的翻译任务：给定自然语言的题目描述 $X$（例如图 2），产出对应的编程语言题解 $Y$（例如图 3）。这自然地引出了为 AlphaCode 选择**编码器—解码器（encoder-decoder）Transformer 架构**（Vaswani et al., 2017）的动机——它对 $p(Y|X)$ 建模。该架构把题目描述 $X$ 作为一个扁平的字符序列（包含元数据，已分词）送入编码器，并从解码器**自回归地**逐个 token 采样出 $Y$，直到产生一个"代码结束"token，此时代码即可被编译运行（$X$、$Y$ 对的示例见附录 F，交互式模型可视化见 https://alphacode.deepmind.com/ ）。

与常用于语言建模与生成的**纯解码器（decoder-only）**架构相比，编码器—解码器架构允许对描述做**双向表示**（描述开头的 token 可以注意到末尾的 token），并额外提供了"把编码器结构与解码器结构解耦"的灵活性。由于题目描述平均长度是其对应人类解法的**两倍**，我们采用了**非对称架构**：编码器为 **1536** 个 token，而解码器只有 **768** 个 token。我们还进一步发现，使用**浅编码器 + 深解码器**能在不损害解题率的前提下显著提升训练效率。我们各模型的确切架构列于表 3。9B 和 41B 模型使用了**模型并行**进行训练，每个分片（shard）一个 key head 和一个 value head。我们使用 JAX（Bradbury et al., 2018）与 Haiku（Hennigan et al., 2020）构建模型，并在 **TPUv4** 加速器上以 **bfloat16** 精度训练。

为了降低从模型采样的开销，我们利用了**多查询注意力（multi-query attention）**（Shazeer, 2019）。在每个注意力块中使用**完整的一组 query head**，但**共享 key 与 value head**，显著降低了内存占用与缓存更新成本——而后者正是采样时的主要瓶颈。这一内存削减还允许采样时使用更大的 batch size，进一步提升了效率。

分词方面，我们使用了一个 **SentencePiece 分词器**（Kudo and Richardson, 2018），词表大小为 **8,000** 个 token，在 GitHub 与 CodeContests 数据的混合语料上训练。这一混合训练确保了分词器既能有效切分多种语言编写的程序，也能处理题目的自然语言描述。模型中的编码器与解码器使用同一个分词器。

### 4.2 预训练

我们在第 3 节所述的 GitHub 数据集上预训练模型，解码器使用标准的**交叉熵 next-token 预测损失**，编码器使用**掩码语言建模（MLM）损失**（Devlin et al., 2018）。掩码语言建模损失对提升编码器的表示学习至关重要。我们通过均匀采样**枢轴点（pivot）**来切分 GitHub 文件：枢轴点之前的内容作为编码器输入，之后的内容用于解码器。

我们的基础 1B 参数模型训练了 **106 步**（注：原文如此，指特定设置下的步数），batch size 为 256。遵循 Kaplan et al. (2020)，我们针对其他模型规模调整训练量，使得**更大的模型训练更多、更小的模型训练更少**，以优化算力利用。然而，由于资源限制以及为了最优使用算力，我们最大的 41B 模型的训练被提前中止，因此该模型相对于其他规模的模型而言是**训练不足**的（表 3）。

我们使用 **AdamW**（Loshchilov and Hutter, 2017）——Adam 优化器（Kingma and Ba, 2014）的一个变体——来训练所有模型：$\beta_1 = 0.9$，{300M, 1B, 3B} 模型取 $\beta_2 = 0.999$，{9B, 41B} 模型取 $\beta_2 = 0.95$。我们使用 0.1 的权重衰减以增强正则化。训练初始学习率为 $10^{-4}$，到预训练结束时余弦衰减到 $10^{-5}$。在前 1,000 个训练步上，学习率从 $10^{-9}$ **线性预热**到 $10^{-4}$，并对全局梯度范数做裁剪使其低于 1.0。

### 4.3 微调

我们在 CodeContests 数据集上微调模型。微调期间，编码器使用自然语言的问题描述，解码器使用程序解。与预训练类似，我们同时使用标准的 next-token 预测损失与掩码语言建模损失。

我们还采用了若干额外的条件化手段与改动，它们提升了整体解题率：下文所述的 **tempering（温度调节）**、**value conditioning & prediction（值条件化与值预测）**和 **GOLD**，以及附录 C.2 中描述的**元数据条件化（metadata conditioning）**。我们将初始学习率设为 $10^{-5}$，并在微调结束时余弦衰减到 $10^{-6}$。学习率的前 1,000 个训练步采用同样的线性预热阶段。

#### Tempering（温度调节）

**Tempering** 由 Dabre and Fujita (2020) 提出，是一种正则化技术：在训练时于 softmax 层之前，用标量温度 $T$ 去除模型的输出 logits，从而**人为地把 token 概率分布变得更平滑或更尖锐**。我们观察到，当使用 $T = 0.2 < 1$ 时，tempering 通过让**训练分布更尖锐**（相应地让**推理分布更平滑**）来帮助模型避免对我们的微调数据集过拟合。值得注意的是，这与 Dabre and Fujita (2020) 提出的"用 $T > 1$ 以获得更尖锐的推理分布"的建议**相反**。在采样时，我们用另一个温度 $T'$ 去除 logits，该温度在验证集上调参（仅使用 tempering 的模型取 $T' = 0.12$；同时使用 tempering 与 GOLD 的模型取 $T' = 0.25$）。

> *（译者注）这里容易混淆，值得掰清楚：$T<1$ 是"锐化（sharpening）"，$T>1$ 是"平滑（smoothing）"。训练时用 $T=0.2$ 锐化分布 = 迫使模型对训练 token 更"自信"；结果是推理时用 $T'=0.12$ 或 $0.25$（同样远小于 1）锐化，得到的采样分布比常规训练的模型反而更平缓多样。原文的措辞 ("sharper training distribution → smoother inference distribution") 表达的正是这种"训练锐化反而在采样时换来了更多多样性"的经验现象。*

#### 值条件化与值预测（Value conditioning & prediction）

CodeContests 同时包含**正确与错误**的问题提交。我们使用值条件化与值预测来区分这两类提交，既提供了额外的训练信号，也让我们能够利用那些否则可能误导模型的数据。类似的做法可见于，例如 Vinyals et al. (2019)。在**值条件化**中，我们把"该提交是否正确"这一信息插入到题目描述中，使模型可以条件化于此信息，如图 5 所示。在采样时，模型**总是**被条件化为"该样本是正确的"。【在**值预测**中，我们在训练时加入了一个辅助的值预测任务：把投射到 logits 之前的最后一层 token 表示，也送入一个小型 Transformer，用于分类该提交是否正确。值预测在采样时不使用。】

> **图 5 | 附加元数据信息的格式示例。** 这段元数据被添加到题目描述的顶部，与题目描述本身以相同方式处理。示例格式为：`RATING: 1200` / `TAGS: dp, implementation` / `LANGUAGE IS python3` / `CORRECT SOLUTION`，其后才是题面正文（本例中的 Polycarp 付款题的剩余描述）。附录 F 给出了解码器实际使用的完整示例。

#### GOLD（Pang and He, 2020）

从描述出发求解竞技编程题目，本质上是一个**一对多（one-of-many）**任务（Nandwani et al., 2021）：每一个独特的题目都允许许多取决于算法选择、实现方式等的不同解法。CodeContests 包含的**解法数量比描述数量多出好几个数量级**（表 1）。标准的**最大似然目标**是通过给训练集中的每个解法都分配一些概率质量来最小化损失（**类似召回率**），而我们的指标衡量的是模型能否在提交预算内**找到一个**正确解（**类似精确率**）。为了解决这一错配，我们采用了 **GOLD**（Pang and He, 2020）的一个变体——一种**离线强化学习算法**，它使模型既能从它已经赋予高似然的 token 上学习，也能忽略那些不在其分布内的 token（从而让其专注于精确率）。为了把 GOLD 与 tempering 结合起来，我们在预训练与微调之间**引入了一个短训练阶段**。关于 GOLD 及该组合的完整细节见附录 C.3。

### 4.4 大规模采样

从 Transformer 模型采样可以轻易并行化，这使我们能够扩展到**每题数百万个样本**——这是性能提升的关键驱动力。为确保如此大量的样本具有足够多样性，我们使用**单个已训练模型**，并：(i) 一半样本用 Python 生成、一半用 C++ 生成；(ii) 在自然语言 prompt 中**随机化题目的标签与评级**（示例见图 5，更多细节见附录 C.2）；(iii) 使用**相对较高的采样温度**。这单个模型借助我们所条件化的附加元数据，就可以生成具有不同语言、标签与评级的解。为了最有效地利用我们的样本，我们随后应用**过滤**（第 4.5 节）与**聚类**（第 4.6 节），得到少量候选提交。

对于题目标签与评级的条件化，我们从**最流行的 50 个标签**中随机挑选标签供模型条件化，并在 **800 到 3500** 的区间内均匀采样评级——因为对于比赛中新出现、未见过的题目，这些元数据是不可见的。我们发现条件化于随机标签与评级能够提升性能，其机制可能是增加了样本的多样性。

最优采样温度取决于样本总数（一般而言样本越多，最优温度越高）。然而，**较宽范围内**的不同温度并不会显著改变解题率（图 A5）。因此，在所有同时使用 tempering 与 GOLD 的实验中我们固定使用 $T' = 0.25$；仅使用 tempering 时用 $T' = 0.12$；其余情况下单独调节采样温度。

我们还实验了 **top-k**（Fan et al., 2018）与**核采样 nucleus sampling**（Holtzman et al., 2019）。正如图 A5 所示，尽管我们进行了穷尽的超参数扫描，这些方法并未带来显著的性能提升。因此，我们在实验中使用的是**带温度的常规采样**。模型 prompt 与样本的一些完整示例见附录 F。

### 4.5 过滤

为了准确代表竞技编程竞赛及其罚时机制，我们的公式设定限制每道题**无论抽取多少样本都只能提交 10 次**。选择这些提交的一个有力工具，是把样本过滤为**仅保留那些通过题干中样例测试的样本**。过滤会剔除**约 99%** 的模型样本，尽管确切比例取决于题目与模型，而且过滤之后对许多题目仍可能留下数以万计的候选样本。找到能通过样例测试的解本身就是一个困难问题，在**约 10%** 的题目上，我们的模型找不到任何一个这样的程序。事实上，我们这一设定的简化版本就是经典的程序合成公式：任务由一组给定的输入/输出对来规定（Gulwani et al., 2017）。

### 4.6 聚类

用样例测试进行过滤之后，每道题仍可能留下数千个候选程序。从这个池子里随机挑选，会把本就有限的提交预算浪费在那些**语法不同但语义等价**的程序上。如果我们有**额外的测试输入**，就可以检出语义等价的程序——办法是在这些输入上执行所有剩余程序，并把产生相同输出的程序归为一簇。随后我们就**可以避免重复地从同一个簇中挑选**。

我们训练了一个**独立的测试输入生成模型**，它使用与我们主模型相同的架构，并从同一个 GitHub 预训练检查点初始化。该模型被训练成从题目描述预测测试输入，使用样例测试、隐藏测试与生成的测试输入作为训练数据。训练完成后，该模型被用于为未见过的题目创建新的测试输入。请注意，尽管这些被创建出来的测试输入**并不保证有效**（尤其是当题目具有复杂约束时），不完美甚至无效的输入对于"把采样出的程序分组"这件事仍然有用。

这个**学到的**测试输入生成模型，与第 3.2.1 节中用于增广数据集的**基于变异**的测试生成过程不同。后者需要正确解（而这在测试时是不可用的）来过滤掉坏的测试用例。

在依据程序行为聚类之后，我们发现**按簇从大到小依次选取一个解**的做法最佳，原因或许是：程序出错的方式有很多种，而正确的解往往行为一致，因此会被归入较大的簇。如果某道题的候选解形成不足 10 个簇（或在超过 10 次提交的情况下超过 10 个），在到达最小的簇之后，我们会从第一个簇重新开始，跳过那些已经提交过的样本。

### 5.1 Codeforces 竞赛评测

在本数据集上评测之外，在编程竞赛上评测能更彻底地检验程序正确性——我们的数据集存在已知缺陷，包括假阳性、接受算法上低效的解、以及处理"存在多个可接受输出"的题目。此外，在真实环境中评测让我们得以在此项任务上** benchmark 最强者：人类参赛者**。

我们在 2021/12/01 至 2021/12/28 期间、**每场参赛者超过 5000 人**的所有 Codeforces 比赛上评测了我们的最佳系统，共计 **10 场**比赛。该系统是一个带聚类的 **41B 与 9B 模型的集成（ensemble）**——它在我们的验证集上表现最好，但事后发现略逊于单独使用带聚类的 41B 模型（关于集成的更多内容见附录 C.1）。对于每场比赛，我们**模拟真实地进行 AlphaCode 的现场运行**：为每道题生成样本、用样例测试过滤、然后聚类得到候选提交。我们把这些选出的候选提交到 Codeforces 平台，并计算 AlphaCode 在每场比赛中的名次。首次运行之后，我们将这一流程**又重复了两次**，以衡量方差，以及"允许超过 10 次提交"时的表现。方差来源包括：题目分布、模型训练、采样、过滤与聚类。精确的评测流程见附录 D，完整结果见表 A5 与表 A6。

### 5.2 CodeContests 评测

除 Codeforces 评测外，我们还在 CodeContests 的验证集与测试集上评测了模型。测试集是第 5.1 节所用比赛的**超集**。由于不涉及向外部站点提交，我们数据集上的指标方差更低、也更易测量。对于 CodeContests（此处及第 5.3 节），我们聚焦于第 2.2 节讨论的两个主要指标：

- **$pass@k$**：当我们对每道题从模型取 $k$ 个样本、并**将它们全部提交**给隐藏测试评测时，所解出的题目百分比。只要在指定的样本预算内有任何一个解解决了某题，该题即计为已解出。因此这个指标主要衡量采样过程中的**搜索**方面，用于第 5.3 节。
- **$10@k$**：当我们对每道题从模型取 $k$ 个样本、但**只能提交其中 10 个**给隐藏测试评测时，所解出的题目百分比。这衡量了包括过滤过程在内的多种因素，以及模型在样本数极大时的行为。

结果如表 5 所示。在每题最多一百万个样本的情况下，我们解决了验证集中 **34.2%** 的题目；而在每题十万个样本的情况下，我们解决了验证集中 **31.8%**、测试集中 **29.6%** 的题目。由于采用了时间切分，两个集合中没有任何一道题在训练期间被模型见过。鉴于这些题目的难度（它们是给"尝试竞技编程的自我筛选群体"做的题），这是数据集一个相当可观的比重。

#### 5.3.1 解题率随参数量、算力、样本数与数据集规模的缩放

正如所料，扩大模型参数量或数据集规模会显著提升模型性能（数据集规模的缩放见图 A6）。然而，**即使只能提交 10 个样本，扩大样本总数也会带来模型解题率的巨幅提升**。

图 6 展示了模型性能在 $10@k$ 与 $pass@k$ 指标上如何随样本增多（即增大 $k$）而缩放。两个指标之间的差距凸显了"选择哪些样本去提交"的重要性。图 7 展示了性能如何随训练与采样所用的算力而缩放。这些缩放曲线揭示了关于该问题领域与我们模型的几点有趣事实：

**解题率随样本数呈对数线性缩放。** $10@k$ 与 $pass@k$ 两者的解题率都随 $k$ 近似呈对数线性缩放，其中 $10@k$ 曲线在高样本预算处略微向下弯曲。采样数量远超 10 依然能改善 $10@k$ 解题率，这一事实说明了在锁定最终 10 次提交之前**充分探索搜索空间**是多么重要。然而，提升解题率需要指数级增长的样本量，而成本很快变得令人却步。

**更好的模型在缩放曲线上有更高的斜率。** 图 6 的另一个观察是，更大的模型往往具有更好的模型质量，体现为"相同样本数下解题率更高"以及"在这条对数线性曲线上斜率更高"。由于是对数线性缩放，斜率更高的好模型可以用**指数级更少的样本**达到与差模型相同的解题率。这指出了提升模型质量是对抗"达到更高解题率所需样本预算指数爆炸"的一条有效途径。

**解题率随算力呈对数线性缩放。** 如图 7(a) 所示，当我们在每种算力预算下选择接近最优的模型尺寸时，解题率也随训练算力近似呈对数线性缩放；曲线上的每个点对应一个模型尺寸。图 7(b) 展示了解题率如何随采样算力缩放，并突显出：更大的模型每抽取一个样本需要更多算力，但**随着来自更大模型的高质量样本成为性能的决定性因素，它们最终会超越更小的模型**。这些结果呈现了一个有趣的权衡：可用算力中应有**多大比例用于训练模型**、又有多少用于**从模型采样**。两种利用更多算力的方式都展现了对数线性缩放。

> **图 7 | 解题率随算力的缩放。** **(a) 解题率 vs. 训练算力**：横轴为训练 TPU-days（$10^2$ 到 $10^4$，对数刻度），纵轴为 $10@k$；四条曲线分别对应 $10@1K$、$10@10K$、$10@100K$、$10@1M$ 四种样本预算，每条曲线上的每个点对应一个模型尺寸。在每种算力配置下选择接近最优的模型尺寸时，解题率随训练算力近似对数线性增长；且样本预算越大，整条曲线的位置越高——说明"训练算力"与"采样数"是可以相乘的两个杠杆。
> **(b) 解题率 vs. 采样算力**：横轴为每题采样所耗的 TPU-秒（$10^{-1}$ 到 $10^6$，对数刻度），纵轴为 $10@k$；曲线簇为 300M、1B、3B、9B、41B。**随着分配给采样的算力增加，最优模型尺寸也会随之增大**——即小模型在极低采样算力下占优，而在高采样算力下被大模型反超。

#### 5.3.2 提升采样速度的架构改动

由于**抽取更多样本**对提升性能很重要，那些提高采样速度的架构改动在一定的算力预算内也会提升整体解题率。因此，我们做了两个架构决策：使用 (1) 带**非对称编码器与解码器**结构的编码器—解码器架构；(2) 来自 Shazeer (2019) 的**多查询注意力**设置——每个块使用一组用于 key、一组用于 value 的共享注意力头。

为研究这两个决策的效果，我们将我们的基础 1B 参数模型与"分别移除其中一项改动"的两个替代方案做对比。我们以完全相同的方式预训练并微调了标准的**多头注意力**模型。decoder-only 模型以**相同的算力**训练。然而，由于其解码器序列长度显著更长（2304 个 token），在相同训练算力下，它消耗的 loss token 比训练编码器—解码器模型多 50%。

#### 5.3.5 过滤与聚类

为了在现实的评测预算内解题，我们依赖过滤与聚类，从我们生成的大量模型样本中挑选出少量样本去做评测。

**用样例测试过滤。** 表 9 展示了通过样例测试的模型样本百分比，以及"至少有一个样本通过样例测试"的题目百分比。请注意，这些百分比是基于**全集样本**计算的，没有预先剔除存在语法错误的程序（关于样本的句法正确性详见第 6.2 节）。总体上，我们模型**不足 1%** 的样本能通过样例测试，尽管该百分比在不同题目间差异极大——这意味着用样例测试过滤会剔除**超过 99%** 的模型样本。在我们的模型确实找到正确解的那些题目上，通过样例测试的样本比例大约翻倍，但依然处在很低的水平。$p_{pass\ example\ tests}$ 在不同题目间的非均匀分布，在附录 C.4 中有更突出的展示。

表 9 的另一个观察是：**更大、质量更好的模型**产生的样本更可能通过样例测试，并且在显著更多的题目上通过样例测试。在每题 $10^6$ 个样本下，我们最大的 41B 模型能够为**超过 90%** 的题目生成通过样例测试的解——考虑到"寻找满足 I/O 示例约束的程序"本身仍是一个极具挑战性的问题，这是一个了不起的成功。

**聚类。** 一个解除了要通过样例测试之外，还必须通过隐藏测试，因此我们必须从那些通过所有公开测试的样本中进一步挑选出正确的样本。把一百万个样本过滤掉 99% 之后，每道题仍有数千个样本可供选择。我们依据剩余样本在**生成的测试输入**上的行为对其进行聚类，以充分利用评测预算。

图 8 对比了以下四种方式：(i) 不做过滤随机挑选模型样本；(ii) 过滤后从过滤出的样本中随机选择；(iii) 过滤后使用聚类选择样本；(iv) 允许无限次评测尝试——这给出了"完美样本选择方法"所能达到的性能上界。**过滤与聚类显然使缩放成为可能**，否则解题率将保持平坦。然而它们与理论上限之间仍存在巨大差距。

> **图 8 | 不同样本选择方法的对比。** 横轴为样本预算（$10^1$ 到 $10^6$，对数刻度），纵轴为解题率（0 到 0.35），四条曲线从下到上依次为：**"10@k 无过滤"**（随机选择，曲线几乎平坦且贴近 0）、**"10@k 带过滤"**、**"10@k 带过滤 + 聚类"**、以及作为上界的 **$pass@k$**（完美样本选择）。可以看到：不做过滤的那条曲线几乎不随样本预算增长——**没有过滤与聚类，再多采样也无法转化为更高的解题率**；而最上面的两条曲线（"过滤+聚类" vs 作为上界的 $pass@k$）之间仍有明显差距，说明"如何挑出那 10 个解"仍是有待解决的开放问题。

## 6. AlphaCode 的能力与局限

我们对模型的能力与局限进行了详细分析。特别是，我们发现我们的模型**并非简单地从训练集复制**（第 6.1 节），并且我们的模型对题目描述、以及用于条件化的元数据的各种改动**都很敏感**（第 6.3 与 6.4 节）——这两点都表明，我们**并不是**通过在任务结构上钻明显的空子来解题的。

我们还分析了模型所找到解的特征，包括句法正确性、死代码（dead code），以及它能解的题目类型（第 6.2 节）。我们进一步表明，把**验证损失**当作模型性能的代理指标存在若干问题（第 6.5 节）。关于我们模型与方法的更多分析包含在附录 E 中，注意力可视化以及模型生成的示例题目与解可在 https://alphacode.deepmind.com/ 查看。除特别说明外，所有分析结果均在**不使用聚类**的情况下报告。

### 6.1 从训练数据复制

对于在大量数据上训练的大型语言模型，一个常被提出的担忧是：它们可能通过简单地**记忆训练集**来求解下游问题（例如 Albert Ziegler (2021); Carlini et al. (2021)）。要让竞技编程成为对解题能力的良好测试，我们期望模型必须为新的题目想出新颖的解法。

基于附录 B.3 中的结果，**简单地从训练集复制完整解**是不足以解决未见验证集中的任何一道题的。然而，如果题目与既往题目足够相似，那么通过复制既往解的大段或关键部分来解题，仍有可能。为研究这一点，我们找到了"模型生成的正确验证题解"与"整个训练数据集"（GitHub + CodeContests，忽略空白）之间的**最长公共子串（longest common substrings）**，并把这些匹配长度的分布与人类解的分布做对比。图 9 包含了这些结果，使用了来自 16 道验证题的 50 个 C++ 解与 50 个 Python 解（这些题各有如此多的解）。

该图显示，模型解与人类解以**相近的比率**与训练数据共享子串，尽管模型解的平均最长公共子串略高一些，而人类解的尾部更重。模型解与训练数据之间的公共子串，大多包含用于**读取和解析输入数据格式的样板代码**，而非求解问题的关键逻辑（例如，一个 FastIO Python 类的长度为 805，出现在 1.66% 的所有人类 Python 解中）。因此，AlphaCode **似乎并未通过复制大段代码来解题**。

为了超越"只看解与训练数据之间最长公共子串"的层面，我们对 50 个模型生成的解做了更细致的定性分析。我们对每个解**迭代地移除其中的最长公共子串**，从而把每个解划分为一组"来自微调训练数据"的子串。图 10 给出了一个示例。我们**没有发现**我们的模型从训练数据复制核心逻辑的证据。更多示例见附录 F.1。

### 6.3 对问题描述的敏感性

为了衡量描述对模型性能的重要程度，我们对模型对问题描述的敏感性做了详细分析。总体而言，AlphaCode 似乎**对题目描述中的重要改动做出了恰当的响应**，并且会利用描述中提供的额外信息。这表明，例如，系统并没有忽略描述的大部分内容、然后暴力尝试所有符合该题类别的解法（比如当描述中出现 "prime" 一词时，就枚举所有与素数相关的算法）。

### 6.4 对提供元数据的敏感性

如第 4.4 节所述，在采样时我们向 AlphaCode 提供**随机化的元数据**以增加样本多样性。这包括标签（例如该题是否属于 "binary search" 或 "brute force" 类型）、评级（题目有多难）、编程语言，以及正在生成的解是否正确。

有两个自然的问题值得探索：模型是否确实**对这些元数据条件化**并做出恰当响应？以及在测试时（当它们不可用时）生成这些元数据的最佳策略是什么？我们发现模型**确实条件化于**这些元数据——提供不同的标签会改变模型生成的算法。我们还发现，对于标签与评级我们应该**随机采样**，并条件化于解是 **CORRECT**。这里我们给出关于标签条件化的分析，关于评级与正确性条件化的额外结果见附录 E.4。

我们在验证集的一道例题上检验了模型的标签条件化行为：Codeforces 题目 **1549A，Gregor and Cryptography**（图 A8）。在这道题中，给定一个质数 $P$，要求找出两个整数 $a$ 和 $b$，使得 $P \bmod a = P \bmod b$ 且 $2 \le a < b \le P$。人们很容易用暴力法去解它，但存在一个简单的数论解法：$P$ 必然是奇数，因此 $P \bmod 2$ 和 $P \bmod (P-1)$ 都等于 1。

我们从模型采样：先用标签 "brute force"，再用标签 "number theory"。这些标签改变了样本分布——两次采样运行中第一个成功样本如图 12 所示。

> **图 12 | 对标签的敏感性。在把不同标签作为 prompt 的一部分提供时，尝试 Gregor and Cryptography 所得到的第一个成功样本。**
>
> **用标签 "brute force" 生成的代码：**
> ```python
> t = int(input ())
> for _ in range(t):
>     p = int(input ())
>     for a in range (2, p):
>         b = p - a + 1
>         if p % b == p % a:      # 原图此处被截断，语义为：枚举 a 并检验条件
>             print(a, b)
>             break
> ```
> **用标签 "number theory" 生成的代码：**
> ```python
> t = int(input ())
> while t:
>     p = int(input ())
>     print('2', p - 1)           # 直接给出答案
>     t -=1
> ```
> *（译者注）两组代码按原图还原。前者真的写了一个从 2 枚举到 $p$ 的循环（尽管实际上它在第一轮迭代就必然跳出循环），后者则直接输出 `2` 和 $p-1$，完全不带循环。这个对比堪称全文最优雅的定性证据：模型**真的读懂了 prompt 里的语义标签**，而不只是把它当作噪声。*

"brute force" 的做法名副其实——尽管在实际中它保证会在第一轮迭代就跳出自己的循环——而 "number theory" 的做法则简单地输出答案、完全不带循环结构。这一模式在接下来的 2048 个样本中持续存在。在使用 "number theory" 标签时，模型解决该题的频率**提高了三倍**（29 个解 vs 9 个解），并且输出"除读入输入外完全无循环"的完美解的频率**提高了四倍**（12 个解 vs 3 个解）。

标签条件化提升模型解题率可能有两种途径：**随机标签增加了样本多样性**，或者**采样正确的标签提供了有用的提示**。为区分二者，我们对比了三种采样方式下的解题率：为每个样本采样一组随机标签（默认）、提供真实题目标签、以及为每道题采样一组随机标签（并对同一题的所有样本复用这组标签）。结果如表 13 所示。在测试时提供真实标签是不可能的，但它优于提供一组固定的随机标签。然而**最佳结果来自于按样本采样随机标签**，表明**样本多样性的增加**对提高解题率很重要。

### 6.5 损失是解题率的不佳代理指标

在微调 AlphaCode 模型时，我们观察到：对于 1B 模型的一次早期训练，**验证集的语言建模损失在约 50k 步之后开始上升**，而训练损失仍在下降。这通常指示过拟合。然而，与验证损失相反，我们的**目标指标——解题率——在远超 50k 步之后仍在持续改善**，如图 13 所示。

正如第 4.3 节所讨论的，解一道题是一个**一对多**任务，即只要众多样本中的某一个解决了问题，该题即算是被解决。我们的微调数据集 CodeContests 对每道题包含许多解。我们的主要解题率指标 $10@k$ 也使用了 $k$ 个样本，而非单个样本。我们假设：**模型把概率质量从某些非典型解重新分配到了更典型的解上**，导致整体上验证损失变差，但生成更典型解的概率变高，因而解题率更好。

尽管解题率是终极指标，它的**高方差与高计算成本**使其难以被用于诸如"训练多少步"这类决策。改进验证损失以使其与性能更好地相关，可以更好地指导决策过程。我们将验证损失与解题率之间关系的完整探究留待未来工作。

> **图 13 | 随微调步数变化的验证损失与解题率（$10@1024$）。** 横轴为微调步数（0k 到 800k），左纵轴为解题率（6%–9%），右纵轴为验证损失（0.44–0.60）。两条曲线分别是带拟合的解题率（Solve rate (fit)）与验证损失（Validation loss）。**验证损失在微调早期就开始上升，指示过拟合；而解题率持续改善。**
> *（译者注）这一现象在今天的 RLHF / 后训练语境下已成常识：**困惑度（perplexity）与下游 pass rate 可以背道而驰**。当时的解释是"一对多"任务下模型在做概率质量的重新分配——把质量从罕见解挪到常见解，反而使"至少一个样本正确"变得更可能。至今它仍是解释"为什么 loss 不能当北极星指标"的经典案例。*

## 7. 相关工作

### 7.1 程序合成（Program synthesis）

程序合成指的是自动生成一个满足任务规格说明的程序。表达任务的方式可以是自然语言描述、一组输入/输出样例，或一系列约束。作为一个研究课题，程序合成历史悠久。大多数经典方法把该问题形式化为：在由底层编程语言所定义的搜索空间中搜索程序，且这些程序必须满足定义该任务的所有约束。一个著名的例子是**演绎式合成（deductive synthesis）**方法（Green, 1969; Manna and Waldinger, 1971）——它把任务规格转换为约束，使用定理证明器找到一个满足所有约束的证明，并从证明中提取出程序。后来，基于输入/输出的任务规格变得更流行，著名例子如 **FlashFill**（Gulwani, 2011）。最后，**基于 sketch 的方法**（Solar-Lezama, 2008）从给定的目标程序骨架来合成程序，大幅缩小了搜索空间。Gulwani et al. (2017) 对这些程序合成方法做了出色的综述。

近年来，深度学习已成为程序合成的有用工具。Yin and Neubig (2017) 使用带注意力的循环网络把文本映射为抽象语法树，再转换为代码。Ling et al. (2016) 使用了类似的模型，配合指针网络，从混合的自然语言与炉石传说的结构化规格生成复杂的类结构。如今，学习得到的模型可以被用来**引导程序搜索**（Balog et al., 2016）、**生成程序草图**（Guo et al., 2021; Murali et al., 2017）、**把伪代码转换为代码**（Kulal et al., 2019）、**直接生成目标程序**（Devlin et al., 2017），甚至在强化学习设定下**生成程序化策略**（Trivedi et al., 2021）。

**自动代码补全**也与我们的工作相关，并已成为大多数代码编辑器和集成开发环境（IDE）不可或缺的一部分。在输入时，这些工具会建议可能的续写，大幅提升了编程生产力。最早的代码补全系统纯粹基于句法。Hindle et al. (2012) 提供了经验证据表明代码可以被统计的 $n$-gram 语言模型所建模，并借此为 Java 开发了一个简单的代码补全引擎。更近期的智能代码补全系统可以从历史记录（Robbes and Lanza, 2008）与大量既有代码数据（Aye et al., 2021; Svyatkovskiy et al., 2020）中学习。然而，直到不久之前，大多数代码补全系统**至多只能为一单行**生成建议。类似的趋势贯穿整个程序合成领域：要么局限于窄义领域专用语言中的短程序，要么局限于通用编程语言的简短代码片段。**把规模放大**——它同时增加了搜索问题的深度与宽度——已被证明是一项困难的挑战。

### 7.2 用于程序合成的 Transformer

近期，大型 Transformer 在自然语言建模上的成功（Brown et al., 2020）引发了对"把 Transformer 模型用于代码检索、翻译与生成"的极大兴趣（Chen et al., 2021; Clement et al., 2020; Feng et al., 2020），使程序合成难题取得了显著进展。这些模型在覆盖互联网上广泛文本的海量数据集上训练，能够以空前的流畅度生成文本。与我们最相关的工作是最近的 **Codex** 系统（Chen et al., 2021）——一个在 GitHub 公开代码上训练的 GPT 语言模型（Radford et al., 2019）。该模型展现出令人印象深刻的性能：在给定函数签名与 docstring 的情况下，它能以很高的成功率正确补全人工指定的 Python 函数，尤其是在类似的数据集上微调之后。Codex 被用于构建交互式程序合成系统，能够求解大学水平的线性代数与概率统计题目（Drori and Verma, 2021; Tang et al., 2021），并被进一步用于创建 GitHub Copilot 中的高级自动补全系统。Austin et al. (2021) 训练了一个与 Codex 类似的模型，他们也展示了在编程任务数据集的一部分上微调，可以提升相似任务上的成功率。

然而，这些工作所处理的编程任务，相较竞技编程题目的完整范畴而言是**简单**的——后者无论任务规格还是解都复杂得多。举例来说，在我们的数据集中，题目描述长度的中位数是 **1,628 个字符**、解长度的中位数是 **606 个字符**；而 HumanEval 基准（Chen et al., 2021）的描述长度中位数是 **396 个字符**、解长度为 **148.5 个字符**——两者都大约短了 **4 倍**。HumanEval 的题目也倾向于包含"具体要实现什么"的指示，而竞技编程题目则是提出一个问题、**不给出**任何建议的实现。最后，这些"未见过"的任务究竟有多未见并不清楚。尽管它们是手写的而非从现有来源复制的，但像"数组排序"或"判断一个数是否为素数"这类任务，其解是可以从训练数据集中复制的。我们的工作使用 Transformer，但把模型性能向前推进了显著的一大步：**从生成函数补全，推进到为留出的竞技编程题目创造完整的解**。

### 7.3 规模化采样

与我们的采样与过滤类似，但规模小得多的是，Chen et al. (2021)、Austin et al. (2021) 与 Cobbe et al. (2021) 发现**在同一道题上重复采样**会显著提高找到正确解的概率。Cobbe et al. (2021) 进一步引入了一种通过**多数投票（majority voting）**从多个样本中选出少量最终提交的方法。他们还展示了使用**验证器（verifiers，即价值函数）**来判断模型样本的正确性，以此对样本进行**重排序（reranking）**。

### 7.4 评测指标

评测指标随着模型本身的进步而演进。早期工作通过衡量生成代码与 ground truth 参考代码在 **token 级、语法树级或完整程序级**的匹配程度来评估性能（Ren et al., 2020）。这些指标判定的是"代码是否吻合"而非"程序是否正确"（句法上不同的程序可以在功能上完全相同），因此随着模型进步到能够完整求解编程问题，那些**执行程序并衡量功能正确性**的评测流程（Chen et al., 2021; Hendrycks et al., 2021; Kulal et al., 2019）变得更流行。然而，Chen et al. (2021) 与 Hendrycks et al. (2021) 作为基准都有一定局限，因为我们发现由于测试覆盖有限，**不正确的程序被判为正确是很常见的**（表 2）。

### 7.5 竞技编程

最后，要开发能够求解竞技编程题目的模型，离不开用于训练与评测的竞技编程数据集。Caballero et al. (2016) 发布了一个包含数千道竞技编程题目及相应 Python 与 C++ 解的数据集，采集自流行的竞技编程平台。Zavershynskyi et al. (2018) 引入了另一个竞技编程题目与解的数据集，但他们把解转换成了一种中间编程语言，这使得使用预训练模型变得困难。Puri et al. (2021) 发布了包含大量多语言解的数据集，含正确与错误的解，以及丰富的元数据。最后，Hendrycks et al. (2021) 引入了 **APPS** 数据集——10,000 道编码竞赛题目的集合，并且是首个在竞技编程上评测大型 Transformer 语言模型的工作。作者发现，在 interview 或 competition 级别的题目上，使用大语言模型的整体解题率**接近 0%**。然而，他们的评测形式并不能代表竞技编程，并且如上所述，由于缺乏测试覆盖导致假阳性，这个解题率是**一个上界**（表 2）。我们的数据集建立在 Caballero et al. (2016) 与 Puri et al. (2021) 之上，并加入了我们自己从 Codeforces 平台的额外抓取。

## 8. 更广泛的影响

优秀的代码生成模型有潜力对社会产生积极、变革性的影响，应用范围广泛，包括计算机科学教育、开发者工具，以及让编程更易获得。然而，与大多数技术一样，这些模型也可能使某些应用对社会造成危害，我们需要对此加以防范；而"希望产生积极影响"这一愿望本身并不是对危害的缓解。

### 8.1 应用

尽管这项工作除竞技编程之外少有直接应用，但改进"人类可读代码的生成"为许多具有巨大现实影响的未来应用打开了大门。所有这些应用都需要不同程度的后续工作。

**自动化代码生成**可以让现有程序员更高效，潜在应用范围从建议扩展的代码补全，到优化代码块。更长远地看，先进的代码生成模型可以让开发者在**更高的抽象层级**上工作，从而隐去细节——这在很大程度上类似于当今的软件工程师通常已不再用汇编语言编写程序。

派生出的工具可以让编程更易获得，或帮助教育新的程序员。模型可以建议更高效的、或更符合惯用法的实现方式，从而使人们能够改进自己的编码风格。一个**代码转文档（code-to-documentation）**工具（Feng et al., 2020）会让理解一段复杂代码的功能变得更容易。更极端的、完全在自然语言中运作的系统（如 Codex（Chen et al., 2021）所提议的），则可能让人们在创建软件时**完全不需要编码知识**。

然而，代码生成工具也可能被恶意行为者使用。更好的工具可能让**创建新版本恶意软件**变得更容易，从而帮助它们规避安全软件的检测（后者通常依赖文件指纹数据库）。那些提升开发者生产力的工具，同样也会提升编写恶意代码的开发者的生产力（Chen et al., 2021; Weidinger et al., 2021）。此外，竞技编程代码生成模型尤其可能让使用者在编程竞赛或技术面试中**获得不公平的优势**。

### 8.2 潜在风险与收益

**可解释性（Interpretability）。** 代码生成模型的一个主要优势在于**代码本身相对可解释**。理解神经网络的行为是困难的，但代码生成模型输出的代码是**人类可读的**、可以用传统方法进行分析（因而更容易信任）。证明一个排序算法是正确的，通常比证明一个网络在所有情况下都能正确排序数字要容易。

可解释性使得代码生成在真实世界环境中更安全，也有利于更公平的机器学习。我们可以检查一个人类可读的代码生成系统所写的代码是否存在偏见，并理解它所做的决策。

**泛化性（Generalisation）。** 代码生成模型生成的代码倾向于泛化；**通过足够多的测试**会使代码更可能也通过那些分布外的测试。这种覆盖完整输入输出域的泛化水平，用神经网络通常很难获得，因此可以让代码生成模型在真实世界的分布外应用中更加可靠。

**偏见、公平性与代表性（Bias, fairness, and representation）。** 与自然语言模型（Brown et al., 2020）类似，代码生成模型容易复现其训练数据中的缺陷与偏见。在被训练于多样化的人类语料时，这些模型可能强化并延续社会刻板印象，对边缘化社群造成不成比例的影响。例如，程序中可能包含对于姓名（McKenzie, 2010）、地址（Tandy, 2013）或时间（Sussman, 2017）的文化与地域特定的假设，从而排除代表性不足的用户。

偏见也可能导致低质量的代码，延续 bug 或使用过时的 API，从而带来性能与安全问题。这可能降低新库或新编程语言的采用率。（这一对人类程序员同样存在——他们也会复制旧代码。）

**安全性（Security）。** 如上所述，代码生成既可能带来安全风险也可能带来收益。模型可能生成带有可被利用弱点的代码——无论是由过时代码导致的意外漏洞，还是由恶意行为者注入训练集的故意漏洞（Pearce et al., 2021）。此外，代码生成会**同时赋能**攻击方与防御方——既提升生产力，也开启新技术。例如，多态恶意软件会改变自身实现以躲避检测（Chen et al., 2021）。

**环境影响（Environmental impact）。** 与大规模语言模型一样，训练基于 Transformer 的代码生成模型需要大量算力。此外，由于我们发现**大规模采样**对提升性能至关重要，与传统语言模型相比，我们**相对更多的算力被花在了执行模型上**。我们的训练与采样总共需要**数百 petaFLOPS-days**。（实验运行在 Google 数据中心进行，其购买的可再生能源等同于其消耗量（Hölzle, 2018）。）

然而，代码生成模型的一个比较优势是：**一旦某个程序被合成出来，它通常可以被任何计算机廉价地执行**，这不同于通常需要跑在加速器上的神经网络模型。因此，代码生成模型有可能更容易地被扩展到许多应用中。

**知识产权（Intellectual property）。** 使用大规模训练语料训练代码生成模型存在知识产权方面的担忧。在某些系统上，基于公开可用数据训练是否构成合理使用是一个开放问题（Gershgorn, 2021），尽管这与 AlphaCode 关系较小——它会根据许可证过滤其数据集。即便使用宽松许可证，关于如何**署名与使用人们的代码**，仍然存在决策空间。

**自动化（Automation）。** 随着编程变得更容易获得、生产力更高，并且代码生成可以自动化一些简单任务，程序员的**供给可能增加、需求可能减少**。这一点被部分缓解——因为编写代码只是工作的一部分，而且以往部分自动化编程的例子（例如编译器与 IDE）都只是把程序员推向更高的抽象层级，并让更多人进入这个领域。

**先进 AI 风险（Advanced AI risks）。** 更长远地看，代码生成可能导致先进 AI 风险。编码能力可能导致系统能够**递归地编写并改进自己**，迅速地产生越来越先进的系统。

## 9. 结论

在这项工作中，我们提出了 **AlphaCode**——一个应用于竞技编程代码生成的系统，能够为未曾见过的编程题目生成新颖的解。在 Codeforces 上评测时，AlphaCode 的表现大致相当于**参赛者的中位数水平**。我们发现，**大规模地扩展采样、然后把样本过滤与聚类到一小组**，再加上为支持大规模采样而设计的**采样高效的 Transformer 架构**，对实现良好性能至关重要。我们干净的数据集与稳健的评测流程也为引导研究进展做出了重要贡献。我们还通过详细分析表明：**没有证据表明 AlphaCode 复制了既往解的重要部分，或利用了题目结构上的弱点**。这表明我们的模型确实能够求解它从未见过的问题，即便这些问题需要大量的推理。最后，我们给出了多种**模型探测（model probing）**的结果，并讨论了这类代码生成模型的更广泛影响与危害。

## 术语与背景速览（译者整理）

| 术语 | 含义 |
| --- | --- |
| Competitive programming（竞技编程） | 限时解答开放式算法题的竞赛形式；Codeforces 是代表性平台，难度用 Elo 式 rating（800–3500）表示 |
| $n@k$ | 每题采 $k$ 个样本、只提交其中 $n$ 个时的解题率；本文用来建模竞赛的主设定是 $10@k$ |
| $pass@k$ | $n=k$，即全部 $k$ 个样本都可提交；是 $k$ 个样本能达到的**上界指标** |
| False positive（假阳性） | 错误的程序因测试覆盖不足而被判为正确；CodeContests 把该率从 62% 降到 4% |
| Slow positive（慢阳性） | 语义正确但复杂度不达标（超时）的解被判为正确 |
| Tempering（温度调节） | 训练时以 $T=0.2<1$ 锐化分布做正则化；采样时再用 $T'=0.12/0.25$ 处理 logits |
| Value conditioning / prediction | 把"该提交是否正确"作为条件插入题面（条件化）；并在训练时加一个辅助二分类头（预测） |
| GOLD | Pang & He (2020) 的离线 RL 目标：允许模型忽略不在自身分布内的 token，从"召回"转向"精确率" |
| Metadata conditioning | 把 RATING / TAGS / LANGUAGE / CORRECT 拼在题面顶部作为可控条件 |
| Multi-query attention（多查询注意力） | 保留完整 query 头，共享一组 KV 头；显著降低采样时 KV cache 开销，**~13× 采样吞吐** |
| Large-scale sampling（大规模采样） | 每题最多 $10^6$ 个样本；一半 Python / 一半 C++，随机化标签与评级以提升多样性 |
| Filtering（过滤） | 用题面样例测试执行样本，剔除约 **99%** |
| Clustering（聚类） | 用另一个"测试输入生成模型"造新输入，按输出签名把行为相同的样本归簇，每簇挑一个 |
| Bootstrapping 估计 | 用一个 $K \gg k$ 的样本池通过自助采样估计 $n@k$，以降低小验证集上的方差 |

## 与 AlphaCode 2 的对照（译者整理）

本文是 2022 年的初代系统，你此前翻译的 **AlphaCode 2 技术报告（2023-12）** 是它的后继。两者的方法骨架几乎一致，差别集中在骨干模型与细节：

| 维度 | AlphaCode（本文） | AlphaCode 2（2023） |
| --- | --- | --- |
| 骨干模型 | 自研 **encoder-decoder Transformer**，最大 41B | **Gemini Pro**（微调） |
| 目标函数 | next-token + MLM + GOLD + tempering | **GOLD**（两轮微调） |
| 一族模型 | 单一模型（或 ensemble） | **一族微调模型**，采样预算均分以提升多样性 |
| 目标语言 | Python + C++ 各一半 | **只用 C++**（认为质量更高） |
| 解题率 | CodeContests 10@1M **34.2%**；Codeforces 前 54.3% | Codeforces 每题 10 次尝试内**43%** |
| 排名 | 前 54.3%（约中位数） | **第 85 百分位**（介于 Expert 与 Candidate Master 之间） |
